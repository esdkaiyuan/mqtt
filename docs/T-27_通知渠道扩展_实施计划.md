# T-27 通知渠道扩展 实施计划

> 版本：v1.0　创建日期：2026-10-07　最后更新：2026-10-07
> 上游依据：[T-27 通知渠道扩展 设计文档](./T-27_通知渠道扩展_设计文档.md)（v1.0）
> 交付原则：端到端可用，渠道投递与升级分派两侧同时落地，不以「仅后端通过」为完成。
> 主题策略：按阶段主题拆分提交（`feat(notification): …` / `test(notification): …` / `docs(notification): …`），不合并提交。

## 计划概览

- **Goal**：把告警通知从「单一 Webhook 出口」扩为「站内信 + 邮件 + 短信 + 既有 Webhook」多渠道并行投递，并补齐告警超时升级与处理人分派；既有告警评估与 Webhook 投递行为零回归。
- **Architecture**：新增 `NotificationChannel` 渠道抽象与 `NotificationDispatcher` 统一分发；`INAPP` 与 `WEBHOOK` 为内置通道（后者经适配器复用既有 `WebhookDispatcher`），`EMAIL` / `SMS` 为用户配置型渠道；投递留痕与重试、升级巡检各自独立线程池与巡检器，锚点全部落库。
- **Tech Stack**：Java 17 + Spring Boot 4.1.1 + MyBatis-Plus 3.5.17 + Flyway + spring-boot-starter-mail + JUnit 5 + Mockito + ArchUnit；Vue 3 控制台。
- **Spec**：`docs/T-27_通知渠道扩展_设计文档.md` v1.0。
- **Global Constraints**：
  - 不改 `MqttMessageHandler`、`IngestPipeline` / `IngestDispatcher` / `IngestPersistenceService`、`emqx-init.sh`。
  - 不改 `webhook_config` 表与 `WebhookController`，`WebhookDispatcher` 的投递语义、签名与重试行为保持原样。
  - 不改 T-17 告警评估四步与抑制窗口逻辑，`AlertNotifierImpl` 对外契约不变。
  - 错误码自 6261 起，追加时把 `ResultCode` 第 124 行末项 `DEVICE_SUBDEVICE_LIMIT_EXCEEDED(6260, …)` 的分号改为逗号。
  - 迁移文件为 `V15__notification_channel.sql`，`V1`~`V14` 零改动；四张新表加 `alert_record` 三列，只加不改。
  - 渠道配置的敏感字段（SMTP 密码、短信密钥、自定义请求头）响应一律脱敏为 `******`，更新时留空表示保留原值。
  - 站内信、渠道、策略、投递记录一律按 `user_id` 隔离，越权返 `403`。
  - ArchUnit 既有规则不得放松，通知服务接口不得直接依赖 Mapper。
  - `app.notification.enabled=false` 时 `/notification-channels/**` 与 `/alert-escalations/**` 返 `404`、站内信不再新增、邮件与短信不投递、升级巡检不注册；`/notifications/**` 读取与已读保留，既有 Webhook 告警通知不受影响。
