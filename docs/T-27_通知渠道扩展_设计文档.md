> 版本：v1.1　日期：2026-10-07　状态：已交付
> 上位文档：`docs/平台功能链路路线图.md`（L14）　前置链路：L4 / T-17 告警中心

## 1. 背景与目标

能力域 7（告警中心）在 T-17 之后余两项差距 ——「缺告警升级 / 分派」与「缺短信 / 邮件 / 站内信等扩展通知渠道（现仅 Webhook）」。现状是 `AlertNotifierImpl` 把告警触发 / 恢复事件序列化后交给 `WebhookDispatcher`，出口只有用户自建的回调地址一个。这在「平台自己就是告警接收方」的场景下够用，但两类真实诉求无法满足：

- **人要看得到**。值班人员不会为了收告警去搭一个回调服务；平台应当自带站内信，登录即在顶栏看到未读告警；同时允许把告警推到邮箱与手机短信。
- **没人处理要往上顶**。一条 `CRITICAL` 告警触发后若长时间无人确认，应当自动升级（提高级别、指派处理人、扩大通知范围），而不是静默躺在列表里。

本链路目标：把告警通知从「单一 Webhook 出口」扩为「多渠道并行投递 + 投递留痕 + 超时升级分派」，同时**不改变既有 Webhook 出口的行为**，使 T-17 的告警评估链路与既有配置零回归。

## 2. 范围

### 2.1 在范围内

- 站内信通道：`notification` 表与用户级未读 / 已读管理端点，顶栏通知中心由「告警未读数」升级为站内信中心。
- 外部渠道配置：`notification_channel` 表与 CRUD、连通性测试端点，支持 `EMAIL`（SMTP）与 `SMS`（HTTP 供应商）两类。
- 渠道抽象层：`NotificationChannel` 接口与注册表，`NotificationDispatcher` 按事件匹配渠道并异步投递。
- 投递留痕：`notification_delivery` 表、指数退避重试巡检与保留清理。
- 告警升级与分派：`alert_escalation_policy` 表、升级巡检、手动指派 / 解除指派端点。
- `alert_record` 追加 `assignee_id` / `escalation_level` / `last_escalated_at` 三列，迁移 `V15__notification_channel.sql`。
- 错误码 `6261`~`6267`、`app.notification` 配置组、单元测试与验收项。
- 前端：通知渠道配置页、站内信中心、告警升级策略配置、告警列表指派操作。

### 2.2 不在范围内

| 事项 | 归属 |
|------|------|
| 第三方短信服务商的具体协议适配（阿里云 / 腾讯云 SDK） | 本期以通用 HTTP 供应商（URL + 方法 + 请求头 + 请求体模板 + 成功关键字）覆盖，厂商 SDK 另立任务 |
| 通知模板的可视化编辑器与多语言文案 | 本期标题 / 正文由后端按固定结构拼装，模板引擎另立任务 |
| 站内信的实时推送（SSE 主动推送未读数） | 本期沿用既有 30s 轮询口径，实时通道改造归 R2 后续 |
| 告警升级的分级值班表（排班、轮值） | 本期策略只支持固定 `after_seconds` 与固定处理人 |
| 通知渠道的全局（跨用户）共享配置 | 渠道配置按登录用户隔离，与既有 Webhook 口径一致 |

## 3. 术语表

| 术语 | 含义 |
|------|------|
| 通知事件 | 触发一次分发的业务事件名，本期为 `alert.triggered` / `alert.recovered` / `alert.escalated` |
| 渠道类型 `channel_type` | 通知出口的种类，本期配置型取 `EMAIL` / `SMS`；`INAPP` 与 `WEBHOOK` 为内置通道 |
| 内置通道 | 不需要用户配置行的通道：`INAPP`（站内信，落库即达）与 `WEBHOOK`（既有 `webhook_config`，经适配器纳入） |
| 投递记录 | 一次「事件 × 渠道」的投递尝试留痕，含状态、尝试次数与错误摘要 |
| 升级策略 | 用户级规则：告警未确认超过 `after_seconds` 时提高 `escalation_level`、指派处理人并扩大通知 |
| 分派 | 把告警指派给具体处理人，写 `alert_record.assignee_id` |
| 敏感字段 | 渠道配置中用于鉴权的口令类字段（SMTP 密码、短信密钥、自定义请求头），响应一律脱敏 |

## 4. 渠道模型

### 4.1 复用既有 Webhook 而非另起一套

`webhook_config` 表与 `WebhookController` 已稳定服务设备事件与告警事件，且其 `events` 过滤、签名、自定义请求头、失败计数均已就位。本期**不改该表、不改该控制器、不改 `WebhookDispatcher` 的投递语义**，而是新增一个适配器把「既有 Webhook 出口」注册为内置通道 `WEBHOOK`。

为什么不让 `notification_channel` 也支持 `WEBHOOK` 类型：同一件事会有两张表、两个配置页、两条投递路径，用户无法判断改哪一处生效，且既有用户的告警 Webhook 会突然「失联」。以适配器纳入统一投递记录，既保住存量行为，又让所有出口在 `notification_delivery` 里可见。

### 4.2 站内信作为内置必达通道

站内信不需要外部端点，落库即达，因此不做成配置行，由全局开关 `app.notification.inapp-enabled` 控制。它的作用有两个：给值班人员一个零配置的兜底出口；给升级与分派一个不会因外部端点不可达而丢失的留痕。

站内信写入与投递记录**同事务边界外**：先落 `notification`（必达），再异步写 `notification_delivery`（尽力而为），后者失败不影响前者。

### 4.3 外部渠道统一为「配置行 + 事件订阅」

`EMAIL` 与 `SMS` 各为一行配置，行上带 `events` 过滤（JSON 数组，语义与 `webhook_config.events` 一致）。这样渠道与事件的对应关系由配置自身表达，不引入第三张路由表。

- `EMAIL` 的 `config` 字段：`host` / `port` / `username` / `password` / `from` / `ssl` / `to`（可选，逗号分隔）。
- `SMS` 的 `config` 字段：`url` / `method` / `headers`（对象）/ `bodyTemplate` / `successKeyword` / `phones`（可选，逗号分隔）。

收件人默认取当前登录用户的 `sys_user.email` 与 `sys_user.phone`，`to` 与 `phones` 给出时覆盖默认值，用于把告警发到值班组邮箱或值班号码；两者都缺失时投递记 FAILED，错误摘要写明「无收件人」。

短信之所以不做成厂商 SDK：自建站点常见做法是走企业已有的短信网关，其协议多为「HTTP POST + 模板参数」。通用 HTTP 供应商让部署方零改代码即可接入，代价是模板与签名规则需部署方自行在 `bodyTemplate` 中表达。

### 4.4 投递语义

一次事件分发的顺序固定为：站内信落库 → 匹配渠道 → 逐渠道异步投递 → 写投递记录。

- 逐渠道隔离：任一渠道抛异常只记 WARN 并写 FAILED 记录，不影响其他渠道，也不冒泡到告警评估链路。
- 投递失败不阻塞：初次失败即写 `status=FAILED` 与 `next_attempt_at`，由巡检重试；重试达上限后置终态 `FAILED` 并停止。
- 事件未匹配的渠道不写记录，避免表被无关事件撑大。
- 内置 `WEBHOOK` 通道的投递不受 `app.notification.enabled` 影响，该开关只作用于本链路新增的站内信、邮件、短信与升级能力，保证 T-17 既有行为在任何配置下都原样成立。

## 5. 升级与分派

### 5.1 升级判定

`AlertEscalationSweeper` 定时拉取候选告警：`status='TRIGGERED'`（未确认、未恢复）且命中启用中的升级策略（按 `severity` 过滤，`ALL` 表示不限）。

对每条候选，基准时间取「`last_escalated_at` 为空时用 `first_triggered_at`，否则用 `last_escalated_at`」；当基准时间距今 ≥ 策略 `after_seconds` 时执行一次升级：`escalation_level + 1`、写 `last_escalated_at`、按策略写 `assignee_id`（策略未指定则保持原值），并向策略 `channel_ids` 指定的渠道投递 `alert.escalated`。

`escalation_level` 达到 `app.notification.max-escalation-level` 后不再升级，只刷新 `last_escalated_at`，避免无限循环通知。

### 5.2 为什么升级锚点落库

升级锚点写 `alert_record.last_escalated_at`，与 T-23 场景的 `scheduled_at` / `next_attempt_at` 同思路：进程重启后判定不丢、多副本并发时以条件更新（`WHERE escalation_level = ?`）保证同一级只升级一次。

### 5.3 手动分派

`POST /alerts/{id}/assign` 支持指定处理人（须为同租户用户）或置空解除指派。手动指派同样写 `assignee_id`，并可选择是否投递一次 `alert.escalated` 通知（请求体 `notify` 布尔，默认不通知，避免与自动升级重复轰炸）。

## 6. 数据模型

迁移 `V15__notification_channel.sql` 新建四张表，并对 `alert_record` 追加三列。**只加表与列、不改既有列**，`V1`~`V14` 零改动，应用版本可安全回滚。

### 6.1 `notification`（站内信）

| 列 | 类型 | 说明 |
|----|------|------|
| `id` | BIGINT PK | 自增 |
| `user_id` | BIGINT NOT NULL | 归属用户，外键 `sys_user(id) ON DELETE CASCADE` |
| `event_type` | VARCHAR(64) NOT NULL | 来源事件名 |
| `level` | VARCHAR(16) NOT NULL | 展示级别：`INFO` / `WARNING` / `CRITICAL` |
| `title` | VARCHAR(200) NOT NULL | 标题 |
| `content` | TEXT | 正文 |
| `ref_type` | VARCHAR(32) | 关联对象类型，本期为 `ALERT` |
| `ref_id` | BIGINT | 关联对象主键 |
| `read_at` | DATETIME | 已读时间，NULL 表示未读 |
| `created_at` | DATETIME | 创建时间 |

索引 `idx_user_read (user_id, read_at, created_at)` 支撑「未读数」与「按时间倒序分页」。

| 列 | 类型 | 说明 |

| `id` | BIGINT PK | 自增 |

| 列 | 类型 | 说明 |

| `user_id` | BIGINT NOT NULL | 归属用户，外键 `sys_user(id) ON DELETE CASCADE` |
| `name` | VARCHAR(100) NOT NULL | 策略名称 |
| `severity` | VARCHAR(16) NOT NULL | 适用级别：`ALL` / `INFO` / `WARNING` / `CRITICAL` |
| `after_seconds` | INT NOT NULL | 未确认时长阈值 |
| `assignee_id` | BIGINT | 升级时指派的处理人，可为空 |
| `channel_ids` | JSON | 升级时额外通知的渠道 ID 数组，可为空 |
| `enabled` | TINYINT | 是否启用，默认 1 |
| `deleted` | TINYINT | 逻辑删除，默认 0 |
| `created_at` / `updated_at` | DATETIME | 审计列 |

### 6.5 `alert_record` 追加列

| 列 | 类型 | 说明 |
|----|------|------|
| `assignee_id` | BIGINT NULL | 处理人用户 ID |
| `escalation_level` | INT NOT NULL DEFAULT 0 | 已升级次数，0 表示未升级 |
| `last_escalated_at` | DATETIME NULL | 最近升级时间，作为下一级升级的基准 |

三列均可空或有默认值，存量行回退为「无处理人、未升级」，既有查询与状态机不受影响。

## 7. 参数校验

| 对象 | 规则 |
|------|------|
| 渠道 `channel_type` | 仅接受 `EMAIL` / `SMS`，其余返 `6263` |
| 渠道 `config` | 按类型必填校验：`EMAIL` 要求 `host` / `port` / `from`，`SMS` 要求 `url` / `method`（`POST` / `PUT`）；缺失或 `port` 越界返 `6262`；`to` 与 `phones` 给出时须为逗号分隔的合法邮箱 / 号码，非法返 `6262` |
| 渠道 `events` | 元素须在事件白名单内，非法返 `6262` |
| 渠道数量 | 单用户不超过 `max-channels-per-user`，超出返 `6263` |
| 渠道名称 | 单用户内唯一，重复返 `6262` |
| 升级策略 `after_seconds` | 须为正整数且不小于 60，非法返 `6266` |
| 升级策略 `severity` | 须在 `ALL` / `INFO` / `WARNING` / `CRITICAL` 内，非法返 `6266` |
| 升级策略 `assignee_id` | 若给出须为同租户存在的用户，非法返 `6266` |
| 升级策略数量 | 单用户不超过 `max-escalation-policies-per-user`，超出返 `6266` |
| 指派处理人 | 须为同租户存在的用户，非法返 `6267` |

## 8. 处理流程

### 8.1 告警触发与恢复

`AlertNotifierImpl` 保持对外契约不变（`notifyTriggered` / `notifyRecovered`），内部改为委托 `NotificationDispatcher.dispatch(userId, eventType, device, alertRecord, payload)`：

1. 受 `app.notification.enabled` 与既有 `app.alert.notify-enabled` / `recover-notify-enabled` 双重控制：后者关闭即返回（保持 T-17 语义）；前者关闭时跳过站内信、邮件与短信，但仍投递内置 Webhook 通道。
2. 站内信通道（若 `inapp-enabled`）写 `notification` 一行并写一条 `SUCCESS` 投递记录。
3. 内置 `WEBHOOK` 通道复用 `WebhookDispatcher` 既有分发，行为与 T-17 一致，并按投递结果写记录。
4. `EMAIL` / `SMS` 渠道按 `events` 匹配后异步投递，逐渠道写记录。

### 8.2 投递重试

`NotificationSweeper` 定时扫描 `status='FAILED'` 且 `next_attempt_at <= now` 的记录，重投对应渠道；成功置 `SUCCESS` 并清空 `next_attempt_at`，失败则 `attempt_count + 1` 并按 `backoff-seconds × 2^(attempt_count-1)` 顺延，达 `max-attempts` 后置 `next_attempt_at = NULL` 停止重试。同一巡检按 `retention-days` 清理过期记录。

### 8.3 升级巡检

`AlertEscalationSweeper` 按 §5.1 判定并执行升级；每条候选的条件更新以 `WHERE id = ? AND escalation_level = ?` 保证多副本下同一级只升级一次，更新影响行数为 0 即跳过。异常逐条隔离，不冒泡。

### 8.4 与既有链路的关系

不新增 MQTT 主题、不改 ACL、不改 `emqx-init.sh`；`IngestPipeline` / `IngestDispatcher` / `MqttMessageHandler` 一行不改；`webhook_config` 表与 `WebhookController` 一行不改。

## 9. 交互边界

| 边界 | 约定 |
|------|------|
| 与 T-17 告警评估 | 只消费 `AlertRecord`，不改评估四步与抑制窗口逻辑 |
| 与既有 Webhook | 经适配器纳入统一投递记录，投递语义、签名与重试行为保持原样 |
| 与 T-23 场景 / T-19 规则 | 无耦合；本期不提供「通知作为场景动作」 |
| 与用户体系 | 渠道、策略、站内信、投递记录一律按登录用户隔离；指派处理人须为同租户用户 |
| 与前端顶栏 | 既有告警未读角标改为站内信未读角标，数据源由 `/alerts/unread-count` 换为 `/notifications/unread-count` |

### 10.2 错误码

| 码 | 枚举 | HTTP | 含义 |

## 13. 安全与边界

- 渠道配置中的 `password` / `secret` / `headers` 在响应中一律以 `******` 返回；更新时字段为空字符串表示保留原值，避免前端回填脱敏串导致凭据被覆盖。
- 站内信、渠道、策略、投递记录全部按 `user_id` 隔离，越权返 `403`。
- 短信 `bodyTemplate` 中的手机号与邮件 `from` 在投递记录 `target` 中脱敏（保留前 3 后 4）。
- 投递记录不落完整请求体，只落错误摘要，避免把凭据写入日志表。
- 新增依赖 `spring-boot-starter-mail`（版本由父 POM 托管），用于 SMTP 投递；短信走既有 `RestTemplate`，不新增依赖。

## 附：设计自审

1. **是否动到底层架构**：否。告警评估四步与抑制窗口不变，既有 Webhook 投递语义不变，改动面为「四张新表 + 三列 + 一组通知服务与巡检」，符合「先补齐功能缺口，再动底层架构」。
2. **是否新增第二套写路径**：否。告警仍由 `AlertNotifierImpl` 单一入口触发，投递统一经 `NotificationDispatcher`，Webhook 经适配器复用既有分发器。
3. **是否引入跨租户越权面**：否。渠道、策略、站内信、投递记录全部按 `user_id` 隔离；指派处理人与升级策略处理人均校验同租户存在性。
4. **回滚是否安全**：物理层只加表与列，`enabled=false` 可停用全部新行为；既有 Webhook 告警通知不依赖新表，停用后仍照常投递。
5. **凭据存储口径**：SMTP 密码与短信密钥需可逆使用，沿用既有 `webhook_config.secret` 的明文存储口径，但补上响应脱敏与「留空保留原值」两项约束，避免前端回填把凭据写坏；若后续要求落库加密，另立任务统一处理告警 Webhook 与本链路三类凭据。
6. **遗留待定**：`alert_record.assignee_id` 未加外键约束（用户删除后保留历史指派痕迹），与 `acknowledged_by` 同口径；若需强一致另立任务。
