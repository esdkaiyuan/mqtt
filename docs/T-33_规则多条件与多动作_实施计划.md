# T-33 规则多条件与多动作 实施计划

> 版本：v1.0　创建日期：2026-10-11　最后更新：2026-10-11　状态：**已交付**
> 上游依据：[`头部平台对标_尚未补齐功能项清单.md`](./头部平台对标_尚未补齐功能项清单.md)（v1.7）§7 追赶段第一优先
> 对应缺口：**G-6-7**「规则模型目前每条规则只有一个触发条件与一个动作；扩展为多条件 / 多动作需改后端模型与评估链路」

---

## 1. 计划概览

- **Goal**：让一条规则能表达「条件 A **且** 条件 B」或「条件 A **或** 条件 B」，并能一次命中执行多个动作。
- **Architecture**：**JSON 可选列 + 旧列回落**，不改既有列、不删列、不新建子表。
  - 规则评估是「按 `user_id` 拉全量规则 → 内存匹配」（`RuleDefinitionMapper.selectEnabledByUser`），**从不按条件 / 动作做 SQL 过滤** —— 这正是选 JSON 而非子表的依据：JSON 在本架构下不损失任何查询能力，却省掉整套 JOIN 与一致性维护。
  - 多条件规则走**独立的求值分支**，单条件规则的代码路径**一行未改**。
- **Tech Stack**：Spring Boot 4.1.1 + MyBatis Plus + Flyway（V20）+ Vue 3 + Element Plus；后端为主。
- **Global Constraints**：
  - **零回归红线**：T-19 既有 106 项规则域测试与全量后端测试必须保持全绿；单条件规则的单值提交体、触发次数、触发值语义全部不变。
  - **不建 `rule_condition` / `rule_action` 子表**：条件与动作永远整条规则一起读写、从不单独查询，子表只增成本不增收益。
  - **存量行零改写**：V19（V20）新列全部带 DEFAULT，存量行 `conditions_json` / `actions_json` 为 NULL → 自动走旧列路径。
  - **不静默截断**：条件 / 动作超出上限一律拒绝保存。悄悄丢掉多余条件等价于悄悄改了规则语义。

## 2. 现状基线（实施前已核实）

| 事实 | 结论 |
|---|---|
| 规则表 | `rule_definition` 单值列：`source_type` + `identifier` + `operator` + `threshold_value` + `event_type`（一个条件）、`action_type` + `action_config`（一个动作） |

| 迁移版本 | V1~V19 已占，V20 可用 |

## 3. 设计决策

### 3.1 为什么是「JSON 可选列 + 旧列回落」而不是子表

规则引擎的读取路径固定为 `selectEnabledByUser(userId)` → 内存逐条匹配。条件与动作**从不作为查询条件**。
子表能带来的唯一收益是「将来若要按条件反查规则」这种**尚不存在的需求**，代价却是：写入要事务保证两张表一致、
评估要多一次批量查询、删除要做孤儿清理、现有序列化逻辑要重写。

而 JSON 列的代价几乎为零：多两个 TEXT 列 + 一次解析。**存量行保持 NULL 时连解析都跳过**，与改造前逐位一致。

写入策略是「**多值优先、单值回填**」：数组非空时以数组为准，同时把**首个元素回填到旧列**。
这样任何仍读 `identifier` / `action_type` 的存量路径（列表筛选、导出、旧版前端、执行记录展示）继续拿到合理值。

### 3.2 多条件求值：三条语义决策

求值范围是**一次上报批**而非单个样本 —— 「温度 > 30 且 湿度 < 60」天然需要设备同时报两个属性。

1. **同一条件多次上报取「任一满足」**：设备一批里重复上报同一属性，只要有一次越限就应触发；取交出会漏报偶发尖峰。
2. **`AND` 下缺值 = 直接判不满足并终止求值**：本批没带的属性就是没上报。
   ⚠️ 实现陷阱：最初写成「缺值 `continue`」，结果另一个条件满足时 `anySatisfied=true` 就整体命中了 —— 测试抓到。
   `AND` 下缺值必须**终止**求值，不能只是跳过。
3. **`OR` 下缺值不贡献命中**，但若所有条件都缺值则整体不命中 —— 否则一条永不被满足的规则会被别的条件的缺值误触发。

### 3.3 多动作：执行粒度 = 动作粒度

一次命中按动作数落 **N 条独立 `rule_execution`**，各自携带 `action_type` 与 `action_config_snapshot`。

- **为什么不是一个 execution 多动作**：重试 / 巡检重放 / 手动重试三条路径共用单记录入口。
  一个 execution 多动作时，整条重试会把已成功的动作重复投递 —— `FORWARD_HTTP` 重复发有外部副作用。
  按动作拆记录后，一个动作失败只重试它自己，且**执行器一行都不用改**。
- **为什么需要快照列**：执行器按 ID 回查规则，读到的永远是 `actions_json` 之外那个单动作列 ——
  第 2 个动作会执行成第 1 个。把配置随触发写进执行记录，重试时读快照而非规则当前值。
- **快照分派判据**：`action_config_snapshot` 非空 = 多动作（按记录分派）；为空 = 单动作（**保持按规则分派**）。
  存量执行记录的 `action_type` 只是触发当时的快照，规则后来被改过时以规则为准 —— 这是 T-19 既有语义，改它会让存量行为漂移。
  同一判据同时控制 `readConfig` 与 `switch` 分派，两处不会分叉。

### 3.4 冷却只占一次

`acquireCooldown` 保持在 `trigger()` 里判一次，**不放进动作循环**。
若放进循环，第二个动作会被刚占的锚点直接挡掉，多动作退化成单动作 —— 这是最容易被忽略的一处。

### 3.5 试运行的诚实降级

多条件规则的试运行只提供「一个标识符 + 一个取值」，无法完整判定。
因此：多条件规则下即使首个条件满足也判 `matched=false`，并在 `reason` 里写明「仅该条件满足，其余条件缺值 → 按 AND 判不命中」与条件总数；
多动作规则的诊断只覆盖首个动作，`summary` 追加「共 N 个动作，试运行只诊断了第一个」。
**宁可显示未命中，也不给出「已命中」这种误导性结论。**

## 5. 踩坑记录

- **`AND` 缺值写成 `continue` 是真 bug**：注释写的是「缺值不算命中」，代码却是跳过继续，结果另一个条件满足时整条规则误命中。
  `RuleMultiMatcherTest.missing_value_is_not_a_hit_under_and` 抓到。教训：多条件求值的短路分支要逐个想清楚「AND / OR 各自该不该终止」。
- **执行器不能无脑改成「按执行记录分派」**：`RuleActionExecutorImplTest` 的 `pendingExecution()` 把 `action_type` 硬编码为 `UPDATE_PROPERTY`，
  而规则是 `SEND_COMMAND` —— 8 个用例因此失败。这说明**单动作形态下以规则为准**是 T-19 既有语义，不能动。
  最终判据改为「快照非空 = 多动作，按记录分派；快照为空 = 单动作，按规则分派」。
- **Vue 的 `v-model` 不能绑定表达式**：`v-model="action.url || action.topic"` 报 `vue/valid-v-model`，必须按动作类型拆成多个 `v-input`。
- **样式块插入易产生 `</style scoped>`**：脚本做 `replace('<style scoped>', …)` 时若新内容也以 `<style scoped>` 收尾，闭合标签会带上属性。
