## 1. 背景与目标

T-19 已交付**消息规则 / 规则引擎**，把上行数据的下游出口从「写死」变成「可配置」。但 T-19 的规则模型刻意收敛为**「一条规则 = 单触发源 + 单条件 + 单动作」**，其 §2.2「不在范围内」明确把以下能力**归属本任务（L10 / T-23）**：

- 「多动作编排 / 动作流 / 动作间延时」；
- 「多条件 AND / OR 组合」；
- 「定时触发 / 场景触发（多设备联动）」。

因此当前的欠缺是：**能做「一条数据 → 一个动作」，但做不了「一个事件 → 延时 → 多个动作 → 多台设备」**。典型业务诉求 —— 「门磁打开 → 延时 5s → 客厅灯下发开灯命令，同时把事件转发到第三方 MQTT」—— 用 T-19 需要配置三条互不相关的规则，且**无法表达先后与延时**；「温度 > 30 且 湿度 < 40 才开加湿器」这种**多条件组合**同样无法表达。

产品路线图 §2 能力域 12「自动化 / 场景联动」现状为「无」，差距为「零代码可视化编排、多触发条件、时序动作流」，标注为 **缺失**；能力域 6「消息规则 / 规则引擎」残余差距「缺可视化拖拽编排与多条件时序动作流（**归 L10**）」。路线图 §1 对标表中 ThingsCloud 行取用重点含「**零代码自动化**」。

本任务引入**自动化 / 场景联动**，在 T-19 规则引擎之上补上「时序 + 多条件 + 多设备」三个维度：

- **场景模型**：一个场景 = 触发源 + 条件组（0..N 个条件，`AND` / `OR` 组合）+ 动作流（有序步骤，每步可带延时）；
- **触发源**：`PROPERTY`（属性上报）/ `EVENT`（事件上报）/ `TIMER`（定时触发，5 字段 cron，分钟级）；
- **动作流**：步骤按 `seq` 顺序执行，`delay_seconds` 表示「相对前一步完成时刻」的延时；单步动作类型复用 T-19 的四类（`UPDATE_PROPERTY` / `SEND_COMMAND` / `FORWARD_MQTT` / `FORWARD_HTTP`）；
- **多设备联动**：动作目标支持 `TRIGGER`（触发设备）与 `FIXED`（固定目标集合：手选设备 / 产品 / 分组含子分组 / 标签），复用 T-18 的 `DeviceBatchService.resolveTarget`；
- **执行记录**：一次触发落一条 `scene_execution`，每个步骤落一条 `scene_step_run`，可查「执行到第几步、每步耗时与结果」；
- **前端表单式编排**：先做「触发 → 条件 → 步骤流」三段式表单，暂不做可视化拖拽（与 T-19 §2.2 口径一致）。

目标：

1. **时序可编排**：不改代码即可配置「A 上报某事件 → 延时 5s → B 下发命令」并自动执行（路线图 L10 验收项）。
2. **多条件可组合**：条件组支持 `AND` / `OR`，条件值取自目标设备当前云端属性（`device_property_latest`）。
3. **多设备可联动**：单步可作用于「触发设备」或「固定目标集合」，目标解析复用 T-18 批量链路（上限 `500` 台）。
4. **可追溯**：执行记录 + 步骤明细双级记录（状态 / 尝试次数 / 重试锚点 / 转发载荷快照 / 每步起止时刻），支持手动执行与手动重试。
5. **可恢复**：延时与重试锚点**全部落库**，由 `SceneSweeper` 巡检拉取，支持进程重启恢复与多副本安全（不依赖进程内定时器）。
6. **不破坏主链路**：触发评估挂在 `ThingModelInterpretService` 内的**第四条旁路**（**不新增 `IngestDispatcher` fan-out 路**），全程 `try/catch` 隔离、异常只记 WARN；步骤执行走独立线程池 `sceneExecutor`，**场景动作失败绝不影响主摄取链路**。

## 3. 术语

| 术语 | 含义 |
| --- | --- |
| 场景（SceneDefinition） | 用户私有的一条「触发源 + 条件组 + 动作流」配置 |
| 触发源（TriggerType） | 场景监听的来源：`PROPERTY`（属性上报）/ `EVENT`（事件上报）/ `TIMER`（定时） |
| 触发条件（TriggerCondition） | 触发源自身的比较条件（标识符 + 可选比较符 + 阈值）；`TIMER` 源用 cron 表达 |
| 条件组（ConditionGroup） | 0..N 个**附加条件项**的组合，`AND` / `OR` 连接；与触发条件分离 |
| 条件项（ConditionItem） | 单条附加判定：目标设备（缺省触发设备）+ 标识符 + 比较符 + 阈值 |
| 步骤（SceneStep） | 动作流中的一环：`seq` + `delay_seconds` + 目标 + 动作配置 |
| 步骤延时（delay_seconds） | 本步骤执行前等待的时长，**相对前一步完成时刻**（首步相对触发时刻） |
| 目标（TargetType） | 步骤作用对象：`TRIGGER`（触发设备）/ `FIXED`（固定目标集合） |
| 场景执行（SceneExecution） | 一次触发（自动 / 手动）的落库记录，含进度与终态 |
| 步骤执行（SceneStepRun） | 执行记录下单个步骤的落库记录，含状态 / 尝试次数 / 重试锚点 / 载荷快照 |
| 冷却窗口（cooldown） | 场景级节流：窗口内重复命中只触发一次，防止动作风暴 |
| 试运行（dry-run） | 用给定的设备 / 标识符 / 取值判定触发与条件组是否命中，返回步骤摘要但**不产生任何副作用、不落库** |
| 中止（abort） | 某步骤重试耗尽后置 `FAILED`，**后续步骤置 `SKIPPED`**，整条执行置 `FAILED` |

## 4. 主题方案

### 4.1 不新增自有 MQTT 主题、不改 ACL

场景引擎的输入输出**都不经过平台自有 Broker 的新主题**：

- **输入**：触发评估复用 T-14 已归一化的上行样本（`ThingModelInterpretService` 内的第四条旁路），数据来源是**已在处理中的**上行消息，不新增订阅；
- **步骤出口 1「更新云端属性」**：写 `device_property_latest`，纯服务端写库；
- **步骤出口 2「下发命令」**：复用 T-15 的 `device/{deviceKey}/cmd/down`（逐台调用既有 `DeviceCommandService.invoke`），**不新增主题**；
- **步骤出口 3「转发外部 MQTT」**：是**出站到第三方 Broker** 的独立连接，不经过自有 EMQX，因此**不涉及自有 ACL / 主题 / 共享订阅**；
- **步骤出口 4「转发 HTTP」**：出站 POST，与 MQTT 无关；
- **定时触发**：纯服务端扫描，不涉及任何 MQTT 主题。

因此自有 ACL、QoS、保留消息策略**均无变化**（继续 QoS 1、不保留，沿用 T-15 §4）；`emqx-init` 的认证 / 授权配置**零改动**。

### 4.2 权限与隔离

- 场景与执行记录全部按 `user_id` 隔离；接口层用 `SecurityUtils.requireUserId()` 取当前用户。
- 场景的 `trigger_device_id` 非空时必须属于当前用户（越权 → `2003`）；执行记录按 `user_id` 过滤，跨用户访问返回 `403`（沿用 `RuleController` / `AlertController` 的 `FORBIDDEN` 处理方式，不新增同义码）。
- **动作目标的「设备」在解析时按当前用户过滤**（复用 `DeviceBatchService.resolveTarget` 的既有归属校验：分组 / 标签归属非法抛 `6212` / `6214`），并在**执行时**再次校验设备仍属该用户（设备被删除 / 转移后不再执行，置该步骤 `FAILED` 并记原因）。
- 转发目标地址（HTTP URL / MQTT Broker）由用户配置，属于**出站请求**：出站前校验协议白名单（HTTP 动作仅允许 `http://` / `https://`；MQTT 动作仅允许 `tcp://` / `ssl://`），拒绝 `file://` / `ftp://` 等，避免 SSRF 面扩大（见 §13）。
- **多设备动作的爆炸半径受控**：单步目标设备数上限复用 `DeviceBatchService.MAX_BATCH_SIZE`（`500`），并在保存期按 `app.scene.max-target-devices` 二次校验。

### 4.3 为什么触发评估挂在 `ThingModelInterpretService` 内旁路，而非 `IngestDispatcher` 第 6 路

- **T-17 / T-19 已验证该路径**：告警评估与规则评估均以内部旁路形式挂在 `ThingModelInterpretService` 内，T-19 §4.3 已完整论证「不新增 `IngestDispatcher` fan-out 路」；场景触发与二者**完全同构**（都需要「已归一化的属性 / 事件样本」），沿用同一位置风险最低。
- **零成本复用归一化结果**：`interpretProperties` 内已逐个 upsert 并同时收集了 `applied`（T-16 影子）、`samples`（T-17 告警）、`ruleSamples`（T-19 规则）；场景样本可在**同一循环内**一并收集，无需二次解析 JSON、无需二次查物模型定义。
- **`IngestDispatcher` 契约代价高**：其类注释明确「逐条隔离失败，绝不让异常冒泡（否则 worker 会整批重试导致消息重复落库）」，新增第 6 路意味着要在逐批循环后再加一路 fan-out，并同步维护「独立 try/catch + 不进死信 + 不影响其余路」的契约；而场景条件判定**必须**依赖物模型归一化结果（上游拿不到标识符语义），第 6 路反而要自己再解析一遍。
- **代价**：场景引擎只对**已建模**设备生效（`definition.isEmpty()` 的 `UNMODELED` 分支在调用前即返回）。这是**预期边界**：未建模设备没有标识符语义，无法配置触发条件与条件组。

### 4.4 为什么新建独立 `scene` 域，而不是扩展 `rule_definition`

- **语义不同**：T-19 规则是「单触发 + 单条件 + 单动作」，其表结构（`identifier` / `operator` / `threshold_value` / `action_type` / `action_config` 单列）**无法承载**「条件组 + 步骤流」；强行在 `rule_definition` 上加 `steps` / `conditions` 列并让两种语义共存，会让 T-19 已交付的「一条规则一个动作」契约在数据层被打破（既有查询、校验、执行路径都要分支）。
- **演进风险最低**：新建 `scene_definition` / `scene_step` / `scene_execution` / `scene_step_run` 四表，T-19 的 `rule_definition` / `rule_execution` **零改动**，其单测与 A 项验收不受影响；场景后续扩展（分支、并行）也不会回头污染规则域。
- **代价是两套并行**：用户会同时看到「消息规则」与「场景联动」两个入口。这是**有意为之**：消息规则面向「一条数据的过滤 → 转发」（轻量、高频、单动作），场景联动面向「事件驱动的多设备时序编排」（重量、低频、多步骤）。两者的编排范式、执行模型、记录结构都不同，合并只会让两边都变难用。
- **复用而非复制**：场景**不重写**任何出站能力 —— 命令走 `DeviceCommandService.invoke`、属性写 `DevicePropertyLatestMapper`、MQTT / HTTP 转发走 T-19 的 `RuleMqttForwarder` / `RuleHttpForwarder`、模板渲染走 `RuleTemplateRenderer`、目标解析走 `DeviceBatchService.resolveTarget`。场景引擎只新增「触发 → 条件 → 步骤调度」这一层。

### 4.5 为什么延时步骤走「落库 + 巡检拉取」，而不是进程内定时器

- **重启可恢复**：`ScheduledExecutorService` / `Timer` 的待执行任务在进程重启后**全部丢失**，用户配置的「延时 1 小时」会静默消失；把 `next_attempt_at` 落库后，`SceneSweeper` 在任意副本上重启即可继续推进，语义是「**至少推进一次**」而非「恰好一次」。
- **多副本安全**：延时锚点在库中，多副本各自巡检、靠**条件更新**（`status='PENDING'` 守卫）抢占，天然不会重复执行；进程内定时器在多副本下会重复触发。
- **与既有范式一致**：T-19 §4.6 已论证「落库 + 巡检」优于「进程内状态」，`RuleSweeper` / `ShadowRetrySweeper` / `OtaDispatchSweeper` 都是同一范式；场景延时本质就是「更短的巡检间隔」。
- **代价是精度**：延时精度受 `app.scene.sweep-interval-ms`（默认 `1000`）约束，即实际延时 = 配置延时 + [0, 1s)。对「延时 5s 开灯」这类业务完全够用；秒级以下精度不在范围内（§2.2）。
- **首步零延时仍走线程池**：触发落库后，若首步 `delay_seconds == 0`，立即投递 `sceneExecutor` 执行，避免固定 1s 空转延迟；与巡检路径共用同一把**条件更新锁**，不会重复执行。

### 4.6 为什么步骤失败「中止后续」而不是「继续执行」

- **时序语义确定**：动作流表达的是「先做 A，再等 N 秒做 B」。若 A 失败仍继续 B，B 的前提条件往往已不成立（如「先关阀再停泵」中关阀失败却停泵），会产生**业务上更危险**的状态。
- **可解释**：执行记录上 `FAILED` 的语义清晰（「第 k 步失败，第 k+1..n 步未执行」），前端步骤时间线可直接展示；「部分成功」需要用户自己判断哪几步做了、哪几步没做，排障成本高。
- **保留补偿路径**：中止后用户可手动重试（`POST /scenes/executions/{id}/retry`），重试从**失败步骤**继续（已 `SUCCESS` 的步骤不重放，避免重复下发命令）。
- **代价**：不支持「尽力而为」型编排。这属于分支 / 容错编排范畴，明确不在本期范围（§2.2）。

### 5.2 触发源与条件组形状

| `triggerType` | 必填字段 | 可选字段 | 说明 |
| --- | --- | --- | --- |
| `PROPERTY` | `triggerIdentifier` | `triggerDeviceId`（空=全部设备）、`triggerOperator` + `triggerThreshold`（同时为空=任意上报即触发） | 比较口径同 T-19 §8.3 |
| `EVENT` | `triggerIdentifier` | `triggerDeviceId`、`triggerEventType`（空=不限事件类型） | 事件标识符精确匹配 |
| `TIMER` | `timerCron`（5 字段） | — | 分钟级；`triggerDeviceId` / `triggerIdentifier` 必须为空 |

条件组（`condition_config`，JSON 数组）：

```json
[
  { "deviceId": null,  "identifier": "temperature", "operator": "GT", "threshold": "30" },
  { "deviceId": 33,    "identifier": "humidity",    "operator": "LT", "threshold": "40" }
]
```

- `conditionLogic` ∈ `AND`（缺省）/ `OR`；条件数组为空（或全为 `null`）表示**无附加条件**，触发即执行。
- `deviceId` 为空表示取**触发设备**当前云端属性；非空表示取该指定设备（须属当前用户）。`TIMER` 源下 `deviceId` **必填**（无触发设备可缺省）。
- 比较口径与 T-17 / T-19 **完全一致**：`GT` / `GTE` / `LT` / `LTE` 走 `BigDecimal.compareTo`，`EQ` / `NE` 走 `trim()` 后文本比较；任一侧不可解析为数值 → 该条件项判为**不满足**（跳过，不报错）。

### 5.3 步骤动作配置（`action_config`）各类型形状

形状与 T-19 §5.2 **完全一致**（复用同一套解释逻辑与校验规则）：

| `actionType` | `action_config` 字段 | 目标语义（`target_type`） |
| --- | --- | --- |
| `UPDATE_PROPERTY` | `identifier`（必填）、`value`（必填，支持占位符） | `TRIGGER` 单台 / `FIXED` 多台，**逐台**写 `device_property_latest` |
| `SEND_COMMAND` | `commandType`（`property_set` / `service`）、`identifier`（必填）、`params`（JSON 字符串，支持占位符） | `TRIGGER` 单台 / `FIXED` 多台，**逐台** `invoke`（强制 `async`） |
| `FORWARD_MQTT` | `topic`（必填，支持占位符）、`qos`（0/1/2）、`payloadTemplate`（可空） | 仅 `TRIGGER`：**单次**出站，载荷取触发上下文；`target_config` 必须为空 |
| `FORWARD_HTTP` | `url`（必填，`http(s)://`）、`method`（`POST` / `PUT`）、`headers`（可空对象）、`payloadTemplate`（可空） | 仅 `TRIGGER`：**单次**出站；`target_config` 必须为空 |

- `payloadTemplate` 为空时使用**默认载荷**（见 §5.4）；非空时按占位符渲染（见 §8.9），渲染结果必须是合法 JSON。
- 多设备目标（`FIXED`）下，`params` / `value` 中的占位符**按目标设备逐台渲染**（`${targetDeviceKey}` 等取该台设备）。
- 步骤保存时只做语法与大小校验，占位符在**执行时**渲染。

>

## 8. 场景匹配与动作流执行

### 8.1 挂载点（`ThingModelInterpretServiceImpl` 内第四条旁路）

在既有的属性 / 事件旁路位置追加场景判定，与 T-16 / T-17 / T-19 完全同构：

```java
// interpretProperties：同一循环内并行收集场景样本
List<String> applied = new ArrayList<>();
List<AlertEvaluationService.PropertySample> samples = new ArrayList<>();
List<RuleEvaluationService.PropertySample> ruleSamples = new ArrayList<>();
List<SceneEvaluationService.PropertySample> sceneSamples = new ArrayList<>();
for (Map.Entry<String, JsonNode> entry : params.properties()) {
    // …既有：spec 命中校验 → normalize → upsertIfNewer → metrics → applied.add
    samples.add(new AlertEvaluationService.PropertySample(identifier, valueText, record.receivedAt()));
    ruleSamples.add(new RuleEvaluationService.PropertySample(identifier, valueText, record.receivedAt()));
    sceneSamples.add(new SceneEvaluationService.PropertySample(identifier, valueText, record.receivedAt()));
}
applyReported(device, applied);       // T-16
evaluateProperties(device, samples);  // T-17
evaluateRules(device, ruleSamples);   // T-19
evaluateScenes(device, sceneSamples); // T-23

/** 场景触发旁路（T-23 设计文档 §8.1）；异常只记 WARN，不冒泡到解析链路。 */
private void evaluateScenes(Device device, List<SceneEvaluationService.PropertySample> samples) {
    if (samples.isEmpty()) {
        return;
    }
    try {
        sceneEvaluationService.onProperties(device.getId(), device.getProductId(), samples);
    } catch (Exception e) {
        log.warn("场景触发评估失败，跳过: deviceId={}", device.getId(), e);
    }
}
```

事件侧同构：`flushEvents` **批量写库成功后**才调 `evaluateScenes(deviceId, eventSamples)`（沿用 T-17「未落库不评估」纪律），按设备分组后逐设备调用、逐设备 `try/catch`。

> 四处旁路（影子 / 告警 / 规则 / 场景）各自独立 `try/catch → log.warn`，互不影响；任一异常都不冒泡到 `IngestDispatcher`，**不触发 worker 整批重试**。

### 8.2 场景加载与匹配（`SceneEvaluationServiceImpl`）

1. **取用户场景**：`device.ownerId` → `selectEnabledByUser`，经**短 TTL 缓存**（`app.scene.cache-ttl-seconds`，默认 60s，`0` 关闭）返回；缓存键为 `userId`，值为场景定义列表（**不承载任何执行态**），保存 / 启停 / 删除时**主动失效本副本**，多副本收敛窗口 = TTL（与物模型 / 规则缓存同一范式）。
2. **作用域过滤**：`triggerDeviceId == null`（全部设备）或 `triggerDeviceId == 本次设备`。
3. **来源过滤**：`triggerType == PROPERTY`（属性样本）或 `EVENT`（事件样本）；`TIMER` 不参与样本匹配。
4. **标识符过滤**：`triggerIdentifier` 精确匹配样本标识符（`EVENT` 源额外比对 `triggerEventType`：场景为空则不限，非空则必须相等）。
5. **触发条件判定**：`triggerOperator` 为空 → 直接命中；非空 → 按 §8.3 比较口径判定。
6. **命中后进入条件组判定**（§8.3）→ 全部通过则进入触发流程（§8.4）。

> 单用户场景数上限 100，且已在内存中，逐样本内存匹配成本可忽略；不引入场景索引表。

### 8.3 条件组判定（复用 T-17 / T-19 比较口径）

**比较口径**（与 T-17 / T-19 完全一致）：

| `operator` | 判定 |
| --- | --- |
| `GT` / `GTE` / `LT` / `LTE` | 两侧 `BigDecimal` 数值比较（`compareTo`）；任一侧不可解析为数值 → **该条件项不满足**（跳过，不报错） |
| `EQ` | 两侧 `trim()` 后文本相等 |
| `NE` | 两侧 `trim()` 后文本不等 |

**条件组求值**：

1. 条件组为空 → 视为**满足**（无附加条件）。
2. 逐项取「条件值」：`deviceId` 非空 → 该设备；为空 → 触发设备（`TIMER` 源下必填，故不会走到此分支）。
3. **批量读取**：把条件项按设备分组，对每台设备调用 `DevicePropertyLatestMapper.selectByIdentifiers(deviceId, identifiers)` **一次**取回（避免逐项查库）；`TIMER` 源逐场景按条件项设备分组读取。
4. 条件项的值不存在（设备无该属性最新值）→ 该条件项**不满足**。
5. `conditionLogic == AND` → 所有项满足才满足；`OR` → 任一项满足即满足。
6. 条件组不满足 → **本次不触发**（记 DEBUG 日志，不落执行记录，不占用冷却锚点）。

### 8.4 触发与冷却

命中后：

1. **冷却检查**：`cooldownSeconds > 0` 且距**本副本上次触发**不足 `cooldownSeconds` → **本次不触发**（记 DEBUG 日志，不落执行记录）。冷却锚点为进程内 `ConcurrentHashMap<Long, Instant>`（场景 ID → 上次触发时刻），**不在摄取线程读写数据库**。
2. **占用冷却锚点**：更新进程内锚点为 `now`（**先占用再执行**，避免同一批内连续命中重复触发）。
3. **落执行记录 + 初始化步骤**（§8.5）。**整体 `try/catch`**：落库失败只记 WARN + 指标，不触发本次动作（宁可丢一次触发，也不影响摄取链路）。这是场景引擎在摄取线程上的**唯一一次落库事务**（每次命中一组，且已被冷却节流）。
4. **投递异步执行**：若首步 `delaySeconds == 0`，`sceneExecutor.execute(() -> sceneActionExecutor.executeStep(firstStepRunId))`；`RejectedExecutionException` → 记 WARN + 指标，并把该步骤置 `FAILED`（原因「执行队列已满」）且整条执行置 `FAILED`。

**定时触发（`TIMER`）**由 `SceneTimerSweeper` 独立驱动（不在摄取链路上）：

1. `selectEnabledTimers()` 取全部启用的定时场景；
2. 用 `app.scene.timer-zone`（默认 `Asia/Shanghai`）取当前分钟；
3. 对每个场景用 Spring `CronExpression.parse(timerCron).next(上一分钟) == 当前分钟` 判定是否命中；
4. 命中后调用 `touchLastTriggeredOnce(id, now, minuteFloor)` —— **数据库级分钟去重**：返回 `0` 表示本分钟已被其他副本触发，直接跳过（多副本安全）；
5. 去重通过则走与自动触发**完全相同**的落库 + 投递流程（`trigger_source=AUTO`），并同样受冷却约束。

### 8.5 执行记录与步骤流初始化

在**同一事务**内完成：

1. 插入 `scene_execution`：`status=PENDING`、`trigger_source`（`AUTO` / `MANUAL`）、`total_steps` = 启用步骤数、`finished_steps=0`；触发快照字段（`scene_name` / `trigger_type` / `trigger_device_key` / `trigger_device_name` / `trigger_identifier` / `trigger_value` / `trigger_event_type`）取自当前上下文。
2. 为该次执行的**每个启用步骤**插入 `scene_step_run`（快照 `step_id` / `seq` / `action_type` / `delay_seconds`）：
   - **首步**：`status=PENDING`、`next_attempt_at = now + delay_1`、`scheduled_at = now + delay_1`；
   - **其余步骤**：`status=PENDING`、`next_attempt_at = NULL`、`scheduled_at = NULL`（**尚未排期**，待前序步骤成功后由 §8.6 排期）。
3. `total_steps == 0`（全部步骤被禁用）→ 直接置 `SUCCESS` 并返回，不建步骤行。

### 8.6 步骤执行与延时排期（`SceneActionExecutor`）

**执行单个步骤**（`executeStep(stepRunId)`）：

1. **抢占**：`claimPending(id)` —— `UPDATE ... SET status='RUNNING', started_at=now WHERE id=? AND status='PENDING'`；返回 `0` 表示已被其他线程 / 副本抢占，**直接返回**（并发保护唯一入口）。首次执行时同时 `markRunning(executionId, startedAt)` 把执行记录从 `PENDING` 迁到 `RUNNING`。
2. **加载上下文**：读 `scene_step_run` → `scene_step`（取 `target_config` / `action_config`）→ `scene_definition`（取场景名等）；若场景 / 步骤已被删除 → 置该步 `FAILED`（原因「场景或步骤已不存在」）并中止。
3. **解析目标设备**：
   - `target_type=TRIGGER` → 触发设备（`TIMER` 源下 `FORWARD_*` 动作不需要目标设备，见下）；
   - `target_type=FIXED` → `DeviceBatchService.resolveTarget(execution.userId, targetConfig)`（复用归属过滤与 `MAX_BATCH_SIZE` 校验）；解析为空 → 置 `FAILED`（原因「目标设备为空」）并中止。
4. **分派动作**（§8.7）：
   - `UPDATE_PROPERTY` / `SEND_COMMAND`：**逐台**渲染并执行，单台失败只记该台 `error`，**全部成功才算成功**（部分失败视为步骤失败，错误信息汇总 `M/N 成功`）；
   - `FORWARD_MQTT` / `FORWARD_HTTP`：**单次**执行，载荷按触发上下文渲染。
5. **成功**：`markSuccess(id, finishedAt)` + `bumpFinishedSteps(executionId, +1)`；随后**排期下一步**：
   - 存在下一步 → `scheduleNext(nextStepRunId, scheduledAt = now + delay_{k+1}, nextAttemptAt = now + delay_{k+1})`；若 `delay_{k+1} == 0`，可立即投递 `sceneExecutor`（同样受 `claimPending` 保护）；
   - 无下一步 → `markSuccess(executionId, finishedAt)`（整条执行成功）。
6. **失败**：进入重试判定（§8.8）。
7. 转发类步骤在**渲染成功后**回填 `forward_payload` 快照（无论发送成功与否），便于排障。

> **`TIMER` 源的 `TRIGGER` 目标**：定时触发没有触发设备，因此 `TIMER` 源下 `UPDATE_PROPERTY` / `SEND_COMMAND` 步骤的 `target_type` **必须为 `FIXED`**（保存期校验，失败码 `6241`）；`FORWARD_*` 步骤不受影响（载荷取触发上下文，`triggerDevice*` 占位符渲染为空串）。

### 8.7 四类步骤动作实现

| `actionType` | 实现 | 复用 |
| --- | --- | --- |
| `UPDATE_PROPERTY` | 逐台取产品物模型 → 校验 `identifier` 存在且可写 → `DevicePropertyLatestMapper.upsertIfNewer(deviceId, identifier, spec.type(), renderedValue, now)` | 既有 Mapper（时间戳守卫） |
| `SEND_COMMAND` | 逐台 `DeviceCommandService.invoke(new CommandInvoke(deviceId, productId, commandType, identifier, renderedParams, CALL_TYPE_ASYNC, SOURCE_SCENE, null))` | 既有命令链路（含物模型校验、影子写入、离线入队、超时巡检） |
| `FORWARD_MQTT` | 渲染 topic / payload → `RuleMqttForwarder.publish(topic, payload, qos)` | T-19 独立出站组件（**直接复用，不改**） |
| `FORWARD_HTTP` | 渲染 URL / payload → `RuleHttpForwarder.send("scene.triggered", "X-Scene-Id", sceneId, method, url, headers, body, executionId)` | T-19 出站组件（**新增重载**，见下） |

- **`SOURCE_SCENE`**：在 `DeviceCommandService` 中**新增常量** `SOURCE_SCENE = "SCENE"`（与既有 `SOURCE_CONSOLE` / `SOURCE_OPEN_API` / `SOURCE_RULE` / `SOURCE_OTA` 并列），使场景触发的命令在 `device_command_record.source` 上可区分、可追溯（**只加常量，不改既有方法签名**）。
- **`RuleHttpForwarder` 新增重载**：`send(String eventType, String sourceIdHeader, Long sourceId, String method, String url, Map<String,String> customHeaders, String body, Long executionId)`，把「事件类型 / 来源头名 / 来源 ID」参数化；**既有 6 参 `send(...)` 委托到本重载并固定 `eventType=rule.triggered`、`sourceIdHeader=X-Rule-Id`，签名与行为完全不变**（T-19 调用方与单测零改动）。场景传 `eventType=scene.triggered`、`sourceIdHeader=X-Scene-Id`、`sourceId=场景 ID`、`executionId=执行记录 ID`；`X-Step-Seq` 由 `customHeaders` 传入（§5.4）。
- **`operatorId` 传 `null`**：场景触发无操作人。
- **`callType` 强制 `async`**：步骤执行在异步线程内，同步等待回执会长时间占用 `sceneExecutor` 线程；与 T-18 批量下发、T-19 规则动作同一理由。
- 执行入口先 `touchLastTriggered(sceneId, now)` 回填 `last_triggered_at`（**仅供前端展示「最近触发」**，失败只记 WARN 不阻断）。

### 8.8 步骤失败重试、中止与执行终态

- **重试判定**：失败时 `attempt_count < app.scene.retry-max-attempts`（默认 3）→ `markRetry(id, attemptCount+1, nextAttemptAt, errorMessage)`，其中
  `nextAttemptAt = now + min(retry-base-delay-ms × 2^(attemptCount-1), retry-max-delay-ms)`；状态回到 `PENDING`，由巡检再次拾取。
  否则 → **中止**：
  1. `markFailed(id, errorMessage, finishedAt)`；
  2. 该执行下所有仍为 `PENDING` 的后续步骤 `markSkipped`（并 `bumpFinishedSteps` 计入进度）；
  3. `markFailed(executionId, "第 k 步失败：" + errorMessage, finishedAt)`。
- **手动重试**（`POST /scenes/executions/{id}/retry`）：仅允许 `status=FAILED`（`PENDING` / `RUNNING` 返回 `409` + `6241`）。
  - 把**失败步骤**重置为 `PENDING`、`attempt_count=0`、`next_attempt_at=now`；
  - **已 `SUCCESS` 的步骤不重放**（避免重复下发命令）；
  - 执行记录置 `RUNNING`、清空 `error_message`，交由 `sceneExecutor` 立即执行。
- **执行终态**：所有步骤终态后（无 `PENDING` / `RUNNING`）→ 全部 `SUCCESS`/`SKIPPED` 且至少一个 `SUCCESS` 则 `SUCCESS`；存在 `FAILED` 则 `FAILED`（`error_message` 已在中止时写入）。

### 8.9 巡检（`SceneSweeper`）

`SceneSweeper implements SchedulingConfigurer`，`configureTasks` 先判 `!enabled || interval <= 0` 则 log + return，再 `addFixedDelayTask(this::sweep, Duration.ofMillis(interval))`；`sweep()` 各子任务**各自 `try/catch`**（「巡检异常不得中断调度线程」），内部：

1. **拾取到期步骤**：`selectDueSteps(now, sweepBatchSize)` —— 条件为 `status='PENDING' AND next_attempt_at IS NOT NULL AND next_attempt_at <= now`（**`next_attempt_at IS NULL` 的未排期步骤不被拾取**，避免前序未完成时抢先执行）；逐条投递 `sceneExecutor`（**只投递不执行**，巡检线程不阻塞），逐条 `try/catch`。
2. **恢复卡死步骤**：`selectStaleRunning(now - step-timeout-ms, sweepBatchSize)` —— 进程中途退出或动作卡死导致长期 `RUNNING` 的步骤，`resetStale` 复位为 `PENDING`（`attempt_count+1`、`next_attempt_at=now`）；次数已耗尽则置 `FAILED` 并走 §8.8 中止流程。
3. **保留策略**：`execution-retention-days > 0` 时，按批 `deleteFinishedBefore(now - days, limit)` 物理清理**终态**执行记录（`PENDING` / `RUNNING` 永不清理）；步骤明细随 `ON DELETE CASCADE` 一并清理。

> 巡检间隔默认 `1000` ms，保证「延时 5s」的实际延时误差 < 1s。`SceneSweeper` 与既有巡检共用 `ScheduleConfig` 的调度池（`poolSize=3`）；本巡检单轮为「两次索引查询 + 逐条投递」，**不做实际动作**，单轮耗时应 < 10ms，不阻塞其余巡检。

### 8.10 载荷模板渲染（复用 `RuleTemplateRenderer`）

- **直接复用** T-19 的 `RuleTemplateRenderer.render(template, values)`（单次扫描、JSON 转义、未知名保留原样、不递归），**不新增渲染器**；
- 支持的占位符（在 T-19 十二个占位符基础上新增场景维度）：

| 占位符 | 取值 |
| --- | --- |
| `${sceneId}` `${sceneName}` | 场景 ID / 名称快照 |
| `${executionId}` `${stepSeq}` | 执行记录 ID / 步骤序号 |

## 9. 与既有链路的交互边界

- **摄取管线（T-14 / `IngestDispatcher`）**：**零改动**——不新增 fan-out 路、不改逐条 / 逐批结构；场景判定位于 `ThingModelInterpretServiceImpl` 内，与影子 / 告警 / 规则并列的**第四个内部旁路**。
- **物模型解析（T-14）**：场景只处理**已建模**设备的上行（`UNMODELED` 分支提前返回，不进入场景判定）；触发与条件判定复用已归一化的 `valueText` 与 `device_property_latest`，**不二次解析 JSON、不二次查物模型定义**（条件组只查属性最新值）。
- **消息规则（T-19）**：**并存且互不干扰**——独立表（`scene_*` vs `rule_*`）、独立旁路、独立冷却锚点、独立执行记录、独立线程池（`sceneExecutor` vs `ruleExecutor`）。删除 / 禁用场景不影响规则，反之亦然；同一份上行样本可同时被规则与场景使用，比较口径一致（§8.3）。场景**不扩展** `rule_definition`。
- **命令链路（T-15）**：`SEND_COMMAND` 复用 `DeviceCommandService.invoke`，参数校验 / 影子写入 / 离线 `QUEUED` / 超时巡检全部沿用；新增 `source=SCENE` 仅用于可区分来源，**不改既有语义**。
- **设备影子（T-16）**：场景下发 `property_set` 时，在线设备直接发布、离线设备照常入 `QUEUED` 并由既有 `ShadowDeliveryService` 补发，**场景引擎不感知影子**。
- **告警中心（T-17）**：三条旁路**互不干扰**（各自独立 `try/catch`、各自独立规则 / 场景表、各自独立通知出口）；比较口径一致。
- **设备分组与标签（T-18）**：场景**目标解析**复用 `DeviceBatchService.resolveTarget`（手选 ∪ 产品 ∪ 分组含子分组 ∪ 标签，去重 + 归属过滤 + `MAX_BATCH_SIZE`）；**触发作用域**不按分组 / 标签（仅「指定设备 / 全部设备」，与 T-19 一致）。
- **T-19 出站组件**：`RuleMqttForwarder.publish` **直接复用**；`RuleHttpForwarder` **新增重载**（既有方法委托，行为不变，见 §8.7）。
- **`MqttClientManager`**：**不共用**——它只连平台自有 Broker；场景转发沿用 T-19 的独立出站客户端。
- **定时触发**：独立 `SceneTimerSweeper`，与既有巡检共用 `ScheduleConfig` 调度池；不新增线程池、不改既有巡检。
- **未建模设备 / 原始报文转发**：仍由既有 `WebhookDispatcher` 覆盖，场景引擎不介入。

## 13. 安全与边界

- **归属隔离**：场景 / 执行记录全部按 `user_id` 过滤；`SecurityUtils.requireUserId()` 取当前用户；越权资源返回 `403`，越权设备返回 `2003`。
- **执行期二次校验**：步骤执行时重新校验场景归属、目标设备归属（设备删除 / 转移 → 该步 `FAILED`）；**不信任触发时刻的快照**。
- **出站协议白名单**：HTTP 动作仅允许 `http://` / `https://`；MQTT 动作仅允许 `tcp://` / `ssl://`；拒绝 `file://` / `ftp://` 等，避免 SSRF 面扩大（与 T-19 §4.2 一致）。
- **爆炸半径受控**：单步目标设备数 ≤ `min(max-target-devices, MAX_BATCH_SIZE)`；单场景步骤数 ≤ `max-steps-per-scene`；单步骤延时 ≤ `max-step-delay-seconds`；单用户场景数 ≤ `max-scenes-per-user`。
- **线程池隔离**：步骤执行走独立 `sceneExecutor`（有界队列），慢动作不占用摄取 worker，也不占用 `ruleExecutor`；队列满时拒绝投递并置步骤 `FAILED`，**不阻塞触发链路**。
- **主链路隔离**：触发评估全程 `try/catch → log.warn`，**绝不冒泡**到 `IngestDispatcher`；场景引擎在摄取线程上的唯一写库操作是「落执行记录 + 初始化步骤」（已冷却节流），失败只丢一次触发。
- **并发保护**：步骤执行以 `claimPending` 条件更新为**唯一抢占入口**，终态迁移均带 `status` 守卫；多副本巡检不会重复执行同一步骤（语义为「至少推进一次」）。
- **定时触发去重**：以 `last_triggered_at` 的**数据库级条件更新**做分钟去重，多副本不会重复触发。
- **不做越权能力**：场景无开放 API（`/external/v1`）；执行记录只读 + 手动重试，不提供「修改步骤后重放历史」能力。
- **载荷大小**：`actionConfig` / 渲染后载荷受 `app.rule.max-payload-bytes` 约束，超限即失败，防止打爆下游。
- **模板注入防护**：占位符替换为**单次扫描**（不递归替换替换结果），复用 `RuleTemplateRenderer` 的既有防注入设计。
- **不新增自有 MQTT 主题、不改 ACL**：场景引擎零 MQTT 订阅 / 发布改动；转发为出站第三方连接。
- **迁移安全**：`V12` 只加四表，不改既有表；回滚应用版本**不需要回滚 `V12`**（旧代码忽略新表）。
- **不触碰 R5 边界**：不写 `message` 分区 / Kafka / 时序库（路线图 §6 R5）。

### 14.3 回归门禁

- 后端 `mvn -B verify` 全绿（含既有 693 项 + 新增场景测试）；`LayeringRulesTest` 四条 ArchUnit 规则**零新增违规**：
