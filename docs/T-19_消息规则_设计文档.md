## 1. 背景与目标

T-14 ~ T-18 已交付「物模型 → 命令 → 影子 → 告警 → 分组」闭环，但**上行数据的下游出口是写死的**：

- 唯一的下行出口是 `WebhookDispatcher`：固定事件名（`webhook.test` / `alert.triggered` / `alert.recovered`）、固定载荷结构、固定目标地址（`app.webhook.*`），用户无法按自己的业务规则决定「什么数据、在什么条件下、发到哪里、发成什么样子」；
- 想做到「温度 > 40 就把这条数据转给我的 ERP」「收到 `fault` 事件就给设备下发一条复位命令」，当前只能改代码；
- 产品路线图 §2 能力域 6「消息规则 / 规则引擎」现状为「静态 Webhook 转发（无规则编排）」，能力域 4「命令下发与服务调用」残余缺口明确写着「**缺命令作为规则动作（归 L6）**」。

本任务引入**消息规则 / 规则引擎**，把上行数据的下游出口从「写死」变成「可配置」：

- **规则模型**：一条规则 = 触发源 + 条件 + 动作；
- **触发源**：`PROPERTY`（属性上报）/ `EVENT`（事件上报），复用 T-14 已归一化的上行样本；
- **条件**：属性源为「标识符 + 比较符 + 阈值」，事件源为「事件标识符（+ 可选事件类型）」；
- **动作**：至少覆盖路线图要求的四类 —— 「更新云端属性 / 下发命令 / 转发外部 MQTT / 转发 HTTP」；
- **执行记录与失败重试**：每次触发落 `rule_execution`，动作失败按指数退避重试，由巡检兜底；
- **前端表单式编排**：先做「三段式表单」（触发源 → 条件 → 动作），暂不做可视化拖拽。

目标：

1. **可配置**：不改代码即可新增 / 修改 / 启停一条「过滤 → 变换 → 转发」规则；同一用户规则数上限 `200`。
2. **四类动作可用**：更新云端属性（复用 `DevicePropertyLatestMapper.upsertIfNewer`）、下发命令（复用 `DeviceCommandService.invoke`，强制异步）、转发外部 MQTT（独立出站 Paho 客户端）、转发 HTTP（独立出站 POST + HMAC 签名）。
3. **可追溯**：每次触发落一条执行记录（规则 / 设备 / 触发值快照 + 状态 + 尝试次数 + 失败原因 + 转发载荷快照），可按规则 / 设备 / 状态分页查询，支持手动重试。
4. **可重试**：动作失败按指数退避重试，`RuleSweeper` 定时巡检兜底；重试耗尽置 `FAILED` 并保留失败原因。
5. **不破坏主链路**：条件判定挂在 `ThingModelInterpretService` 内的旁路（**不新增 `IngestDispatcher` fan-out 路**），全程 `try/catch` 隔离、异常只记 WARN；动作投递走独立线程池，**规则动作失败绝不影响主摄取链路**。

## 3. 术语

| 术语 | 含义 |
| --- | --- |
| 规则（RuleDefinition） | 用户私有的一条「触发源 + 条件 + 动作」配置 |
| 触发源（SourceType） | 规则监听的上行数据类型：`PROPERTY`（属性上报）/ `EVENT`（事件上报） |
| 条件（Condition） | 属性源为「标识符 + 比较符 + 阈值」，事件源为「标识符 + 可选事件类型」 |
| 动作（ActionType） | 命中后执行的操作：`UPDATE_PROPERTY` / `SEND_COMMAND` / `FORWARD_MQTT` / `FORWARD_HTTP` |
| 动作配置（action_config） | 动作的 JSON 参数体，形状随 `action_type` 变化（见 §5.2） |
| 执行记录（RuleExecution） | 一次规则触发的落库记录，含状态 / 尝试次数 / 重试锚点 / 载荷快照 |
| 冷却窗口（cooldown） | 规则级节流：窗口内重复命中只触发一次，防止动作风暴 |
| 试运行（dry-run） | 用给定的设备 / 标识符 / 取值判定条件是否命中，返回动作摘要但**不产生任何副作用** |
| 转发载荷（forward payload） | 转发 HTTP / MQTT 动作实际发出的报文（渲染模板后），落 `forward_payload` 快照 |

## 4. 主题方案

### 4.1 不新增自有 MQTT 主题、不改 ACL

规则引擎的输入输出**都不经过平台自有 Broker 的新主题**：

- **输入**：条件判定复用 T-14 已归一化的上行样本（`ThingModelInterpretService` 内的旁路），数据来源是**已在处理中的**上行消息，不新增订阅；
- **动作出口 1「更新云端属性」**：写 `device_property_latest`，纯服务端写库；
- **动作出口 2「下发命令」**：复用 T-15 的 `device/{deviceKey}/cmd/down`（逐条调用既有 `DeviceCommandService.invoke`），**不新增主题**；
- **动作出口 3「转发外部 MQTT」**：是**出站到第三方 Broker** 的独立连接，不经过自有 EMQX，因此**不涉及自有 ACL / 主题 / 共享订阅**；
- **动作出口 4「转发 HTTP」**：出站 POST，与 MQTT 无关。

因此自有 ACL、QoS、保留消息策略**均无变化**（继续 QoS 1、不保留，沿用 T-15 §4）；`emqx-init` 的认证 / 授权配置**零改动**。

### 4.2 权限与隔离

- 规则与执行记录全部按 `user_id` 隔离；接口层用 `SecurityUtils.requireUserId()` 取当前用户。
- 规则的 `device_id` 非空时必须属于当前用户（越权 → `2003`）；执行记录按 `user_id` 过滤，跨用户访问返回 `403`（沿用 `AlertController` / `DeviceGroupController` 的 `FORBIDDEN` 处理方式，不新增同义码）。
- 动作目标的「设备」在**执行时**再次按规则归属校验（设备被删除 / 转移后不再执行，置 `FAILED` 并记原因）。
- 转发目标地址（HTTP URL / MQTT Broker）由用户配置，属于**出站请求**：出站前校验协议白名单（HTTP 动作仅允许 `http://` / `https://`；MQTT 动作仅允许 `tcp://` / `ssl://`），拒绝 `file://` / `ftp://` 等，避免 SSRF 面扩大（见 §13）。

### 4.3 为什么条件判定挂在 `ThingModelInterpretService` 内旁路，而非 `IngestDispatcher` 第 6 路

- **T-17 已验证该路径**：告警评估以 `onProperties` / `onEvents` 作为 `ThingModelInterpretService` 内的旁路调用，路线图 L4 交付记录原文明确「**不新增 `IngestDispatcher` fan-out 路**」；规则引擎与告警评估同构（都需要「已归一化的属性 / 事件样本」），沿用同一位置风险最低。
- **零成本复用归一化结果**：`interpretProperties` 内已逐个 upsert 并同时收集了 `applied`（T-16 影子）与 `samples`（T-17 告警）；规则样本可在**同一循环内**一并收集，无需二次解析 JSON、无需二次查物模型定义。
- **`IngestDispatcher` 契约代价高**：其类注释明确「逐条隔离失败，绝不让异常冒泡（否则 worker 会整批重试导致消息重复落库）」，新增第 6 路意味着要在逐批循环后再加一路 fan-out，并同步维护「独立 try/catch + 不进死信 + 不影响其余路」的契约；收益仅是「位置更靠上游」，而规则条件判定**必须**依赖物模型归一化结果（上游拿不到标识符语义），因此第 6 路反而要自己再解析一遍。
- **代价**：规则引擎只对**已建模**设备生效（`definition.isEmpty()` 的 `UNMODELED` 分支在调用前即返回）。这是**预期边界**：未建模设备没有标识符语义，无法配置条件；其「原样转发」需求由既有 `WebhookDispatcher` 覆盖（见 §9）。

### 4.4 为什么与 `WebhookDispatcher` 并存、规则引擎优先

- **并存**：`WebhookDispatcher` 承载的是**平台级事件通知**（`alert.triggered` / `alert.recovered` / `webhook.test`），载荷与目标由部署方在 `app.webhook.*` 统一配置，语义是「平台告诉运维方发生了什么」；规则引擎承载的是**用户级业务转发**（按规则把业务数据发到用户自己的系统），语义、作用域、配置主体都不同。二者强行合并会同时破坏「平台通知统一配置」与「用户规则私有」两条线。
- **规则引擎优先**：新增的转发需求一律走规则引擎；`WebhookDispatcher` 保持现状只服务告警通知，不再新增事件类型。后续若确需收敛，可在 T-2x 把告警通知也建模为内置规则（本期不做，避免动 T-17 已交付链路）。
- **复用而非复制**：规则 HTTP 转发的签名方案（`X-Signature: sha256=<hex>`）与 `WebhookDispatcher` **保持一致**，用户侧验签逻辑只需实现一次；但转发器本身独立（目标地址、载荷模板、超时都按规则配置），不共用 `WebhookDispatcher` 的固定载荷与固定地址。

### 4.5 为什么「转发外部 MQTT」需要独立 Paho 组件

- `MqttClientManager` 是**连平台自有 Broker 的全局单例**（`clientId=mqtt_backend`，订阅 `device/+/up` 等，`@PreDestroy shutdown()`），它的连接参数、订阅集合、共享订阅组都是平台自身运行的一部分；
- 若复用其 `publish(topic, payload, qos)` 转发到第三方 Broker，必须把第三方 Broker 加进同一个客户端——这在 Paho 中**不可行**（一个 `MqttClient` 只能连一个 Server URI），且会污染自有连接的连接态与重连策略；
- 因此新建 `RuleMqttForwarder`：独立 `clientId`（`mqtt-rule-forwarder`）、独立连接 / 重连 / 关闭生命周期、独立开关（`app.rule.mqtt.enabled`），**不订阅任何主题**（纯出站），连接失败不影响平台自身 MQTT 连接；
- 关闭 `app.rule.mqtt.enabled` 时，MQTT 类动作直接置 `FAILED`（原因「外部 MQTT 转发未启用」），不影响其余三类动作与主链路。

### 4.6 为什么动作统一走「异步线程池 + 落库重试」

- **隔离**：条件判定在摄取线程内同步完成（必须快，且必须拿到归一化样本）；动作投递走独立 `ruleExecutor`，慢动作（HTTP 超时、外部 Broker 不可达）**不占用摄取 worker**；
- **可追溯**：每次命中先落一条 `rule_execution`（`status=PENDING`），再投递执行——保证「命中过」这件事不因线程池拒绝 / 进程重启而丢失；
- **可重试**：重试锚点（`attempt_count` / `next_attempt_at`）落在库中，`RuleSweeper` 定时**拉**取到期的 `PENDING` 记录重放，天然支持多副本（任一副本巡检即可）与重启恢复（不依赖进程内状态）；
- **统一**：四类动作走同一套「落库 → 投递 → 重试 → 终态」流程，避免「属性动作同步、转发动作异步」的双模型带来的复杂度；代价是「更新云端属性」的落库时刻略晚于触发时刻（毫秒级），因它写的是**另一个**标识符，与触发值无顺序冲突。

## 5. 载荷格式

### 5.1 规则返回体 / 请求体

统一走既有 `Result<T>` 信封。规则返回 `RuleDefinition` 实体字段（`actionConfig` 为**已解析对象**，非 JSON 字符串，见 §10）。

```json
// GET /rules/7
{
  "code": 200,
  "data": {
    "id": 7,
    "name": "高温转发",
    "description": "温度超过 40 转发给 ERP",
    "deviceId": null,
    "sourceType": "PROPERTY",
    "identifier": "temperature",
    "operator": "GT",
    "thresholdValue": "40",
    "eventType": null,
    "actionType": "FORWARD_HTTP",
    "actionConfig": { "url": "https://erp.example.com/hook", "method": "POST", "headers": { "X-Tenant": "acme" } },
    "cooldownSeconds": 60,
    "lastTriggeredAt": "2026-10-03 10:00:00",
    "enabled": true,
    "createdAt": "2026-10-03 09:00:00",
    "updatedAt": "2026-10-03 09:30:00"
  }
}
```

### 5.2 动作配置（`action_config`）各类型形状

| `actionType` | `action_config` 字段 | 说明 |
| --- | --- | --- |
| `UPDATE_PROPERTY` | `identifier`（必填）、`value`（必填，支持占位符） | 写入目标设备 `device_property_latest`；`identifier` 必须在该设备产品物模型中定义且**可写** |
| `SEND_COMMAND` | `commandType`（`property_set` / `service`）、`identifier`（必填）、`params`（JSON 字符串，支持占位符） | 复用命令链路；参数按目标设备物模型逐台校验 |
| `FORWARD_MQTT` | `topic`（必填，支持占位符）、`qos`（0/1/2，缺省取 `app.rule.mqtt.qos`）、`payloadTemplate`（可空） | 出站到 `app.rule.mqtt.broker-url` 配置的第三方 Broker |
| `FORWARD_HTTP` | `url`（必填，`http(s)://`）、`method`（`POST`/`PUT`，缺省 `POST`）、`headers`（可空对象）、`payloadTemplate`（可空） | 出站 POST/PUT；签名头 `X-Signature` |

- `payloadTemplate` 为空时使用**默认载荷**（见 §5.3）；非空时按占位符渲染（见 §8.7），渲染结果必须是合法 JSON。
- `params` / `payloadTemplate` 中的占位符在**执行时**渲染，规则保存时只做语法与大小校验。

### 5.3 转发 HTTP 默认载荷与请求头

```json
// 默认载荷（payloadTemplate 为空时）
{
  "event": "rule.triggered",
  "ruleId": 7,
  "ruleName": "高温转发",
  "executionId": 1024,
  "deviceKey": "dev-001",
  "deviceName": "温控器-1",
  "deviceType": "thermostat",
  "sourceType": "PROPERTY",
  "identifier": "temperature",
  "value": "42.5",
  "reportedAt": "2026-10-03 10:00:00",
  "timestamp": "2026-10-03 10:00:01"
}
```

请求头：

| 头 | 值 |
| --- | --- |
| `Content-Type` | `application/json;charset=UTF-8` |
| `X-Event-Type` | `rule.triggered` |
| `X-Rule-Id` | 规则 ID |
| `X-Execution-Id` | 执行记录 ID（幂等键，重试时不变） |
| `X-Signature` | `sha256=<hex>`，HMAC-SHA256（密钥 `app.rule.http-secret`，报文为原始 body 字节） |

> `X-Execution-Id` 在**重试时保持不变**，接收方可用它做幂等去重（与 `WebhookDispatcher` 的签名方案一致，但多了执行 ID）。

### 5.4 转发 MQTT 载荷

- **不设置** retained 标志（沿用「不保留」策略）。

## 6. 数据模型（Flyway `V9`）

> 迁移原则：**只加表**，不改既有表；应用版本可安全回滚（回滚后新旧表共存，旧代码忽略新表）。

### 6.1 新表 DDL


## 8. 规则匹配与动作执行

### 8.1 挂载点（`ThingModelInterpretServiceImpl` 内旁路）

在既有的属性 / 事件旁路位置追加规则判定，与 T-16 / T-17 完全同构：

```java
// interpretProperties：同一循环内并行收集规则样本
List<String> applied = new ArrayList<>();
List<AlertEvaluationService.PropertySample> samples = new ArrayList<>();
List<RuleEvaluationService.PropertySample> ruleSamples = new ArrayList<>();
for (Map.Entry<String, JsonNode> entry : params.properties()) {
    // …既有：spec 命中校验 → normalize → upsertIfNewer → metrics → applied.add
    samples.add(new AlertEvaluationService.PropertySample(identifier, valueText, record.receivedAt()));
    ruleSamples.add(new RuleEvaluationService.PropertySample(identifier, valueText, record.receivedAt()));
}
applyReported(device, applied);      // T-16
evaluateProperties(device, samples); // T-17
evaluateRules(device, ruleSamples);  // T-19

/** 规则引擎旁路（T-19 设计文档 §8.1）；异常只记 WARN，不冒泡到解析链路。 */
private void evaluateRules(Device device, List<RuleEvaluationService.PropertySample> samples) {
    if (samples.isEmpty()) {
        return;
    }
    try {
        ruleEvaluationService.onProperties(device.getId(), device.getProductId(), samples);
    } catch (Exception e) {
        log.warn("规则评估失败，跳过: deviceId={}", device.getId(), e);
    }
}
```

事件侧同构：`flushEvents` **批量写库成功后**才调 `evaluateRules(deviceId, eventSamples)`（沿用 T-17「未落库不评估」纪律），按设备分组后逐设备调用、逐设备 `try/catch`。

> 三处旁路（影子 / 告警 / 规则）各自独立 `try/catch → log.warn`，互不影响；任一异常都不冒泡到 `IngestDispatcher`，**不触发 worker 整批重试**。

### 8.2 规则加载与匹配（`RuleEvaluationServiceImpl`）

1. **取用户规则**：`device.ownerId` → `selectEnabledByUser`，经**短 TTL 缓存**（`app.rule.cache-ttl-seconds`，默认 60s，`0` 关闭）返回；缓存键为 `userId`，值为规则定义列表（**不承载任何执行态**），保存 / 启停 / 删除时**主动失效本副本**，多副本收敛窗口 = TTL（与物模型缓存同一范式）。
2. **作用域过滤**：`deviceId == null`（全部设备）或 `deviceId == 本次设备`。
3. **来源过滤**：`sourceType == PROPERTY`（属性样本）或 `EVENT`（事件样本）。
4. **标识符过滤**：`identifier` 精确匹配样本标识符（`EVENT` 源额外比对 `eventType`：规则为空则不限，非空则必须相等）。
5. **条件判定**（§8.3）→ 命中即进入触发流程（§8.4）。

> 单用户规则数上限 200，且已在内存中，逐样本内存匹配成本可忽略；不引入规则索引表。

### 8.3 条件判定（复用 T-17 比较口径）

| `operator` | 判定 |
| --- | --- |
| `GT` / `GTE` / `LT` / `LTE` | 两侧 `BigDecimal` 数值比较（`compareTo`）；任一侧不可解析为数值 → **不命中**（跳过，不报错） |
| `EQ` | 两侧 `trim()` 后文本相等 |
| `NE` | 两侧 `trim()` 后文本不等 |

- 口径与 T-17 告警**完全一致**（数值按 `BigDecimal.compareTo`、`EQ`/`NE` 按归一化文本、不可解析值跳过），避免同一份数据在「告警」与「规则」上得出不同结论；
- `NUMERIC_OPERATORS = {GT, GTE, LT, LTE}` 与阈值「必须可解析为数值」的保存期校验（§7.2）配对，保证数值比较路径不会因文本阈值而永远不命中。

### 8.4 触发与冷却

命中后：

1. **冷却检查**：`cooldownSeconds > 0` 且距**本副本上次触发**不足 `cooldownSeconds` → **本次不触发**（记 DEBUG 日志，不落执行记录）。冷却锚点为进程内 `ConcurrentHashMap<Long, Instant>`（规则 ID → 上次触发时刻），**不在摄取线程读写数据库**。
2. **占用冷却锚点**：更新进程内锚点为 `now`（**先占用再执行**，避免同一批内连续命中重复触发）。
3. **落执行记录**：插入 `rule_execution`，`status=PENDING`、`attempt_count=0`、`next_attempt_at=NULL`（NULL 表示「已投递待首次执行」，巡检不会重复拾取）、快照字段（`rule_name` / `device_key` / `device_name` / `source_type` / `identifier` / `trigger_value` / `action_type`）取自当前上下文；`forward_payload` 留空（执行时渲染后回填）。**整体 `try/catch`**：落库失败只记 WARN + 指标，不触发本次动作（宁可丢一次触发，也不影响摄取链路）。这是规则引擎在摄取线程上的**唯一一次写库**（每次命中一条，且已被冷却节流）。
4. **投递异步执行**：`ruleExecutor.execute(() -> ruleActionExecutor.execute(executionId))`；`RejectedExecutionException` → 记 WARN + 指标，并把该记录置 `FAILED`（原因「执行队列已满」）。

### 8.5 四类动作实现（`RuleActionExecutor`）

| `actionType` | 实现 | 复用 |
| --- | --- | --- |
| `UPDATE_PROPERTY` | 取目标设备产品物模型 → 校验 `identifier` 存在且可写 → `DevicePropertyLatestMapper.upsertIfNewer(deviceId, identifier, spec.type(), renderedValue, now)` | 既有 Mapper（时间戳守卫） |
| `SEND_COMMAND` | `DeviceCommandService.invoke(new CommandInvoke(deviceId, productId, commandType, identifier, renderedParams, CALL_TYPE_ASYNC, SOURCE_RULE, null))` | 既有命令链路（含物模型校验、影子写入、离线入队、超时巡检） |
| `FORWARD_MQTT` | 渲染 topic / payload → `RuleMqttForwarder.publish(topic, payload, qos)` | 新增独立出站组件 |
| `FORWARD_HTTP` | 渲染 URL / payload → 按 `method` 发送，附 `X-Signature` 等头，超时 `app.rule.http-timeout-ms` | 新增独立出站组件 |

- **`SOURCE_RULE`**：在 `DeviceCommandService` 中**新增常量** `SOURCE_RULE = "RULE"`（与既有 `SOURCE_CONSOLE` / `SOURCE_OPEN_API` 并列），使规则触发的命令在 `device_command_record.source` 上可区分、可追溯（**只加常量，不改既有方法签名**）。
- **`operatorId` 传 `null`**：规则触发无操作人。
- **`callType` 强制 `async`**：规则执行在异步线程内，同步等待回执会长时间占用 `ruleExecutor` 线程；与 T-18 批量下发同一理由。
- **执行入口**：先 `touchLastTriggered(ruleId, now)` 回填 `last_triggered_at`（**仅供前端展示「最近触发」**，失败只记 WARN 不阻断），再读记录、渲染、分派。
- 执行成功 → `markSuccess(id, finishedAt)`；执行失败（含渲染失败、目标不可达、物模型校验失败）→ 进入重试（§8.6）。
- 转发类动作在**渲染成功后**回填 `forward_payload` 快照（无论发送成功与否），便于排障。

### 8.6 失败重试与巡检（`RuleSweeper`）

- **重试判定**：失败时 `attempt_count < app.rule.retry-max-attempts`（默认 3）→ `markRetry(id, attemptCount+1, nextAttemptAt, errorMessage)`，其中
  `nextAttemptAt = now + min(retry-base-delay-ms × 2^(attemptCount-1), retry-max-delay-ms)`；
  否则 `markFailed(id, errorMessage, finishedAt)`。
- **巡检**：`RuleSweeper implements SchedulingConfigurer`，`configureTasks` 先判 `!enabled || interval <= 0` 则 log + return，再 `addFixedDelayTask(this::sweep, Duration.ofMillis(interval))`；`sweep()` 整体 `try/catch`（「巡检异常不得中断调度线程」），内部：
  1. `selectDueRetries(now, sweepBatchSize)` 取到期记录 —— 条件为 `status='PENDING' AND next_attempt_at IS NOT NULL AND next_attempt_at <= now`（**`next_attempt_at IS NULL` 的首次执行记录不被拾取**，避免与线程池内的首次执行并发重复执行）；
  2. 逐条调用 `ruleActionExecutor.execute(id)`（内部用 `markSuccess/markRetry/markFailed` 的 `status='PENDING'` 条件更新做**并发保护**，多副本巡检不会重复成功）；
  3. 逐条 `try/catch`，单条异常不影响其余；
  4. 保留策略：`execution-retention-days > 0` 时，按批 `deleteFinishedBefore(now - days, limit)` 物理清理**终态**记录（`PENDING` 永不清理）。
- **手动重试**：`POST /rules/executions/{id}/retry` 仅允许 `status=FAILED`（`PENDING` 返回 `409` + `RULE_INVALID`）。重置 `status=PENDING`、`attempt_count=0`、`next_attempt_at=NULL`，交由 `ruleExecutor` 立即执行。

### 8.7 载荷模板渲染（`RuleTemplateRenderer`）

- 支持占位符：`${ruleId}` `${ruleName}` `${executionId}` `${deviceId}` `${deviceKey}` `${deviceName}` `${deviceType}` `${sourceType}` `${identifier}` `${value}` `${reportedAt}` `${timestamp}`；
- 实现为**纯字符串替换**（占位符 → 转义后的 JSON 安全值），不引入表达式引擎；替换后对 `payloadTemplate` 结果做 JSON 合法性校验，非法 → 该次执行置失败并记原因；
- `headers` / `params` / `value` 同样支持占位符；替换采用**单次扫描**（不递归替换替换结果），避免用户构造的占位符注入。

## 9. 与既有链路的交互边界

- **摄取管线（T-14 / `IngestDispatcher`）**：**零改动**——不新增 fan-out 路、不改逐条 / 逐批结构；规则判定位于 `ThingModelInterpretServiceImpl` 内，与影子 / 告警并列的第三个内部旁路。
- **物模型解析（T-14）**：规则只处理**已建模**设备的上行（`UNMODELED` 分支提前返回，不进入规则判定）；条件判定复用已归一化的 `valueText`，**不二次解析 JSON、不二次查物模型定义**。
- **命令链路（T-15）**：`SEND_COMMAND` 复用 `DeviceCommandService.invoke`，参数校验 / 影子写入 / 离线 `QUEUED` / 超时巡检全部沿用；新增 `source=RULE` 仅用于可区分来源，**不改既有语义**。
- **设备影子（T-16）**：规则下发 `property_set` 时，在线设备直接发布、离线设备照常入 `QUEUED` 并由既有 `ShadowDeliveryService` 补发，**规则引擎不感知影子**。
- **告警中心（T-17）**：两条旁路**互不干扰**（各自独立 `try/catch`、各自独立规则表、各自独立通知出口）；同一份上行样本可同时被告警与规则使用，结论口径一致（§8.3）。删除 / 禁用规则不影响告警，反之亦然。
- **`WebhookDispatcher`**：**并存**——告警通知继续走它（`alert.triggered` / `alert.recovered`），规则 HTTP 转发走新的 `RuleHttpForwarder`；两者签名方案一致，目标地址与载荷各自独立（§4.4）。
- **`MqttClientManager`**：**不共用**——它只连平台自有 Broker；`RuleMqttForwarder` 为独立出站客户端（§4.5）。
- **分组与标签（T-18）**：规则作用域**不按分组 / 标签**（§2.2）；规则删除不影响分组，反之亦然。
- **未建模设备 / 原始报文转发**：仍由既有 `WebhookDispatcher` 覆盖，规则引擎不介入。

## 13. 安全与边界

- **归属隔离**：规则与执行记录严格按 `user_id` 校验；`device_id` 非空时必须属于当前用户；跨用户访问返回 `403`。
- **不阻塞主链路**：条件判定全程 `try/catch`，异常只记 WARN；动作投递走独立线程池，慢动作不占用摄取 worker；**规则动作失败绝不影响主摄取链路**（路线图 L6 验收项之一）。
- **出站白名单**：`FORWARD_HTTP` 仅允许 `http://` / `https://`；`FORWARD_MQTT` 仅允许 `tcp://` / `ssl://`；拒绝其他 scheme，避免 `file://` 等本地资源访问。
- **SSRF 收敛**：出站请求为**部署方自建系统**的显式配置（用户主动填写目标地址，与既有 `WebhookDispatcher` 同级信任模型）；不跟随重定向（`FOLLOW_REDIRECTS=false`），并对响应体只读不解析（不产生二次请求）。
- **载荷大小与超时**：`action_config` / `payloadTemplate` 保存期与执行期双重限制（`max-payload-bytes`）；出站 HTTP 设连接 / 读取超时（`http-timeout-ms`），避免线程长时间挂起。
- **签名**：`X-Signature: sha256=<hex>`（HMAC-SHA256，密钥 `app.rule.http-secret`）与 `WebhookDispatcher` 方案一致；密钥为空时不下发签名头并在响应 / 文档中提示。
- **模板渲染安全**：纯占位符字符串替换（**单次扫描**，不递归），替换值做 JSON 转义；不引入表达式 / 脚本引擎，杜绝模板注入执行。
- **动作风暴防护**：`cooldownSeconds` 规则级节流 + `executor-queue-capacity` 有界队列；队列满时拒绝投递并记 `FAILED`，不无限堆积。
- **重试不放大**：`retry-max-attempts`（默认 3）封顶 + 指数退避封顶；重试仅针对 `PENDING`，`markSuccess/markRetry/markFailed` 带 `status='PENDING'` 条件更新，多副本巡检不会重复执行成功。
- **冷却的尽力语义**：冷却锚点为**进程内状态**（`ConcurrentHashMap<Long, Instant>`），单副本内严格生效；多副本部署下同一窗口内最多触发 N 次（N = 副本数），属可接受的节流近似（换取摄取线程零额外读写）。
- **命令一致性**：`SEND_COMMAND` 复用同一 `DeviceCommandService.invoke`，参数校验、影子写入、离线入队、超时巡检全部沿用，无并行实现；强制 `async` 避免占用执行线程。
- **数据保留**：执行记录只增不删，由 `execution-retention-days` 按批物理清理**终态**记录；`PENDING` 永不清理（避免丢重试）。
- **MQTT 出站隔离**：`RuleMqttForwarder` 不订阅任何主题、不共用自有连接；其连接失败 / 重连不影响平台自身 MQTT 连接与摄取管线。
- **删除语义**：删除规则为逻辑删除，执行记录保留；删除设备由外键 `ON DELETE CASCADE` 兜底物理清理。

### 14.2 端到端验收（A 项）

| 编号 | 场景 | 预期 |
