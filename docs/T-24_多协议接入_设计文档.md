## 1. 背景与目标

当前平台的**唯一上行入口是 MQTT 直连**：设备以 `productKey.deviceKey` + `device_secret` 连接 EMQX，经共享订阅进入 `MqttMessageHandler.messageArrived` → `IngestPipeline.submit` → 摄取管线 → 物模型解析 → 全部下游 fan-out（影子 / 告警 / 规则 / 场景 / 历史 / 命令回执 / OTA）。路线图 §2 能力域 13「多协议接入」现状为「仅 MQTT 直连」，目标形态为「MQTT 网关、Modbus / HTTP / 边缘网关」，差距为「缺失」，标注为 **缺失**。

T-11 §3.2 的 YAGNI 论证曾**刻意**把「非 MQTT 协议适配（HTTP / CoAP / Modbus 网关）」列为不做项，指其归属后续链路 —— 本任务（L11 / T-24）正是兑现该承诺。

路线图 §3 L11 逐字：

- **目标**：MQTT 之外的接入方式（HTTP 上报 / Modbus 网关）。
- **范围**：HTTP 上报端点与鉴权；边缘网关协议适配方案（评估后定）；统一入摄取管线。
- **依赖**：L1（统一按物模型解析）。
- **验收**：HTTP 上报数据与 MQTT 上报在属性最新值上等价。

本任务的欠缺是明确的：**设备只要不是 MQTT 客户端，就无路可上报**。典型诉求 —— 一个只能发 HTTP 的低功耗表计、一个由边缘网关聚合后统一转发的 Modbus 子系统 —— 目前只能自建 MQTT 桥接，平台侧没有任何对等入口。

本任务在**不新增第二条摄取路径**的前提下，为平台补上 **HTTP 上报端点**，并给出**边缘网关协议适配的评估结论**：

- **HTTP 上报端点**：设备以既有设备凭据（HTTP Basic，用户名 `productKey.deviceKey`、密码 `device_secret`）向平台 POST 上行数据；
- **统一入摄取管线**：端点不做任何自有落库 / 解析，只构造与 MQTT 完全同形的 `IngestRecord` 并投递给既有 `IngestPipeline.submit`，从而**自动继承**与 MQTT 完全一致的分片、有序、落库、物模型解析与全部下游 fan-out；
- **边缘网关协议适配（评估后定）**：结论为「网关侧协议转换在边缘完成，经**既有 MQTT** 或**本期新增 HTTP 上报**接入平台；平台侧**不引入网关父子拓扑、不实现 Modbus 主站**」（§4.5）。

目标：

1. **HTTP 上报可用**：设备凭据鉴权通过后，POST 一条上行消息即可进入摄取管线（路线图 L11 验收项）。
2. **与 MQTT 等价**：同一设备同一份数据，无论经 MQTT 还是 HTTP 上报，`device_property_latest` 的更新结果一致（验收句「等价」）。
3. **统一管线**：HTTP 与 MQTT **共用** `IngestPipeline` / `IngestPersistenceService` / `ThingModelInterpretService`，无第二条落库或解析路径。
4. **零摄取改动**：`IngestPipeline` / `IngestDispatcher` / `IngestPersistenceService` / `ThingModelInterpretServiceImpl` **零改动**，不新增 `IngestDispatcher` fan-out 路。
5. **复用既有鉴权**：复用 `DeviceSecretService.parseUsername` / `DeviceAccessGuard.resolve` / `isPermitted` / `matches`，**不改** `EmqxAuthServiceImpl`。
6. **评估有结论**：网关 / Modbus 侧给出明确结论与不做清单，不引入半成品的父子设备模型。

## 3. 术语

| 术语 | 含义 |
| --- | --- |
| HTTP 上报 | 设备（或边缘网关代设备）以 HTTP POST 向平台投递一条上行消息的接入方式 |
| 设备凭据 | `productKey.deviceKey`（用户名）+ `device_secret`（密码），与 MQTT 接入、EMQX 认证回调完全同源（T-11） |
| 合成 topic | HTTP 无 topic 概念，为对齐既有下游对 `record.topic()` 的假设，按 `device/{deviceKey}/{messageType}` 合成 |
| messageType | 消息类型，取值 `data` / `heartbeat` / `lwt`，与 `MqttMessageHandler.TOPIC_*` 的常量值一致 |
| 等价 | 同一份数据经 HTTP 与经 MQTT 上报后，`device_property_latest` 的最终值与 `message` 落库语义一致 |
| 摄取管线 | `IngestPipeline`（有界队列 + 分片 worker）+ `IngestPersistenceService`（批量落库），T-14 交付 |
| 边缘网关 | 部署在设备侧、聚合多种现场协议（如 Modbus）并转成 MQTT / HTTP 上报的中间设备；本期**不建模**其拓扑 |

## 4. 主题方案

### 4.1 为什么复用「设备凭据」而非开放 API Key

- **验收句要求等价**：路线图 L11 验收为「HTTP 上报数据与 MQTT 上报在属性最新值上等价」。MQTT 侧设备身份是 `productKey.deviceKey` + `device_secret`（`EmqxAuthServiceImpl` 校验）。HTTP 上报要与之**等价**，最自然的方式是**同一套设备凭据** —— 设备已持有 secret，无需再申领任何新凭证。
- **凭据语义不错位**：开放 API 的 `ApiKey` 属于**用户（owner）维度**，一把 Key 可操作该用户名下**任意**资源（`ApiKeyAuthFilter` 注入 `UserPrincipal(userId, "EXTERNAL", …)`）。若让设备上报走 API Key，等于「以用户身份代设备上报」，鉴权粒度从设备级退化到用户级，越权面反而更大。
- **零新增凭据分发**：设备出厂 / 注册时已下发 `device_secret`（`DeviceSecretServiceImpl.generateSecret`），HTTP 上报**直接复用**，不需要第二套密钥生命周期、不需要控制台增删入口。
- **代价**：HTTP 上报不覆盖「平台账号 / 第三方应用」维度的上报（那属于开放 API，本期不做，§2.2）。这是**有意为之**：设备上报与第三方应用接入是两个正交的能力域。

### 4.2 为什么新增 `DeviceCredentialAuthFilter`，而不是扩 `ApiKeyAuthFilter` / `JwtAuthenticationFilter`

- **路径专属**：`ApiKeyAuthFilter` 的 `shouldNotFilter` 写死 `/external/v1/` 前缀，`JwtAuthenticationFilter` 面向控制台会话；二者与 `/ingest/**` 的设备凭据语义无关。新增一个 `shouldNotFilter = !resolvePath(request).startsWith("/ingest/")` 的专属过滤器，职责单一、互不干扰。
- **复用而非复制校验链**：过滤器只新增「HTTP 专属」的一层（取 `Authorization: Basic` → 解 base64 → 拆用户名密码），**判定逻辑全部调用既有服务方法**：
  - 用户名解析：`DeviceSecretServiceImpl.parseUsername`（恰好一个点，`productKey.deviceKey`）；
  - 准入判定：`DeviceAccessGuard.resolve` → `isPermitted`（产品 `ENABLED` + 设备 `enabled=1`，与 ACL 回调同源）；
  - 密钥比对：`DeviceSecretServiceImpl.matches`（BCrypt 逐次计算）。
- **不改 `EmqxAuthServiceImpl`**：其 `enforceAuth` 开关、`isPlatformUsername`（平台账号）是 **MQTT 回调专属语义**，HTTP 上报不应继承（HTTP 上报必须设备凭据，平台账号天然无点、`parseUsername` 返回 `null` 即被拒）。抽出公共类会把这些 MQTT 语义一并带入，或反向污染 MQTT 侧，故不动。
- **失败响应自写**：`/ingest/**` 在 `SecurityConfig` 中为 `permitAll`（鉴权由本过滤器负责，与 `/internal/**` + `InternalTokenFilter` 同构），因此认证失败**不能**依赖 `AuthenticationEntryPoint`。过滤器仿 `RestSecurityExceptionHandler.write` 直接输出标准 `Result` 信封 + `401` + `WWW-Authenticate: Basic`。**代价**：过滤器内多一处 JSON 序列化（注入 `ObjectMapper`），与既有 `InternalTokenFilter`（自写 `{"result":"deny"}`）范式一致。

### 4.3 为什么 HTTP 上报直投 `IngestPipeline.submit`，而不新增 `IngestDispatcher` fan-out 路

- **`IngestRecord` 是唯一载体**：`IngestPipeline.submit(IngestRecord)` 已封装「分片（`routeIndex` 按 `deviceKey.hashCode()` 取模 → **同设备恒同队列**）+ 有界队列 + worker 批量落库」。HTTP 侧只要构造出与 MQTT 同形的 `IngestRecord`，就**自动获得**与 MQTT 完全一致的分片与有序。
- **`IngestDispatcher` 契约代价高**：其类注释明确「逐条隔离失败，绝不让异常冒泡（否则 worker 会整批重试导致消息重复落库）」。HTTP 上报**不是** fan-out 的一路，而是**上游的另一个生产者**；把它做成第 7 路只会让「生产者」与「消费者」混淆，并要在批循环里再维护一路隔离契约。
- **零改动主链路**：直投 `submit` 后，`IngestPipeline` / `IngestPersistenceService` / `ThingModelInterpretServiceImpl` **一行不改**；下文 §9 的全部 fan-out（影子 / 告警 / 规则 / 场景 / 历史 / 命令回执 / OTA）自动生效。这与 T-17 / T-19 / T-23「旁路不改管线」的既有论证骨架完全同构。
- **代价**：HTTP 上报与 MQTT **共用**同一条摄取队列，因此二者**共享**队列容量与 worker 并发（`app.ingest.queue-capacity` / `worker-count`）。这是**预期**：统一入管线正是 L11 的范围要求，背压由既有有界队列 + 死信统一承担（§8.5）。

### 4.4 为什么合成 `topic` 并让 `messageType` 对齐 MQTT 取值

- **下游依赖 `messageType` 语义**：`IngestPersistenceService.resolveStatus` 以 `data` / `heartbeat` → ONLINE、`lwt` → OFFLINE 推导设备状态；`ThingModelInterpretServiceImpl` 仅当 `MESSAGE_TYPE_DATA = "data"` 才解析物模型。HTTP 侧 `messageType` 取同名常量值，**解析与状态推导零成本复用**。
- **`topic` 字段保持非空且可解释**：`IngestRecord.topic` 会被落进 `message.topic` 列（`IngestPersistenceService.toMessage`）。HTTP 无 topic，若置空会让日志 / 排查失去上下文；按 `device/{deviceKey}/{messageType}` 合成，使 HTTP 上报在 `message` 表中与 MQTT 上报**形态一致**（可直接按 topic 检索）。
- **不新增主题、不改 ACL**：合成 topic **不经过**自有 EMQX —— HTTP 上报是**入站 HTTP**，与 Broker 无关；自有主题、QoS 策略、`emqx-init` 认证 / 授权配置**零改动**。
- **代价**：`message.qos` 列对 HTTP 上报是**推导值**（按 messageType 映射）而非真实协商值。这是可接受的展示差异，已在 §2.1 明确映射规则。

### 4.5 为什么本期不引入网关父子拓扑 / Modbus 主站（评估结论）

路线图 L11 明示「边缘网关协议适配方案（**评估后定**）」。经全库核查，平台当前**不存在**任何子设备 / 网关父子拓扑概念（无 `parent_id` 列、无子设备表；代码中「网关」仅指 HTTP 网关空闲超时，见 `RealtimeProperties`），也**不存在**任何 Modbus 实现。评估结论如下：

- **结论（本任务采纳）**：**协议转换在边缘侧完成**。网关 / 采集器负责把 Modbus、串口等现场协议转成 JSON，经**既有 MQTT 接入**（网关作为一个普通 MQTT 设备，topic 携带真实子设备标识）或**本期新增 HTTP 上报**投递；平台侧**只认物模型**，不感知网关内部拓扑。
- **为什么不做平台侧 Modbus 主站**：需要常驻轮询器 + 点表（寄存器地址映射）模型 + 连接池 + 断线重连，是一套独立的**采集子系统**，与「统一按物模型解析」的 L1 依赖正交，且会引入平台对现场网络的可达性要求（穿透 / 防火墙），运维面陡增。
- **为什么不做网关父子拓扑**：需要新增 `gateway` / `sub_device` 表、`parent_id` 列、**子设备鉴权**（网关代子设备上报的授权链）、父子级联删除、以及前端拓扑可视化 UI —— 是独立能力域。若强行在本期塞入，会让 T-11 已交付的「一设备一凭据」身份体系被迫分支。
- **代价**：平台**无法**在控制台看到「网关 → 子设备」的层级，也**不能**由平台下发 Modbus 写寄存器命令。这是**预期边界**，与路线图「评估后定」的措辞一致；若后续确有强诉求，应作为独立任务（建议编号 T-26+）先行设计子设备数据模型。

### 4.6 为什么不做 HTTP 幂等去重，也不做同步落库

- **与 MQTT 语义对齐**：MQTT QoS 1 是「至少一次」，重复投递由业务侧容忍；HTTP 上报同样只保证「受理」，不承诺「恰好一次」。引入幂等表会给每次上报增加一次写放大与清理负担，收益与 MQTT 不一致。
- **保持 fire-and-forget**：HTTP 上报**异步入队**（`IngestPipeline.submit`），响应 `200` 仅代表「**已受理**」，**不代表已落库 / 已解析**。这与 MQTT 回调线程「只构造 `IngestRecord`」的语义完全一致（`IngestRecord` 类注释：后续所有 DB / HTTP 操作都在 worker 线程完成）。
- **不做同步落库的理由**：同步落库会让 HTTP 请求阻塞在摄取 worker 上，把设备侧的上报超时风险传导进平台；且与「统一入管线」相悖。
- **代价**：设备侧**拿不到**「数据是否真的写库成功」的回执。若设备需要强确认，应改用 MQTT QoS 1 或（后续）拉取式确认，属 §2.2 不做项。

## 5. 载荷格式

### 5.1 上报请求

```
POST /api/ingest/{deviceKey}/{messageType}
Authorization: Basic base64("{productKey}.{deviceKey}:{device_secret}")
Content-Type: application/json
```

- `messageType` ∈ `data` / `heartbeat` / `lwt`（其它值 → `400` + `6247`）。
- Body 为设备上报的**原始载荷**，平台**不预解析语义**（与 MQTT 完全一致：MQTT 侧也不解析，直接入队，由物模型解析环节统一处理）。

`data`（物模型属性 / 事件上报）：

```
POST /api/ingest/dev001/data
Authorization: Basic ZGsxMDAxLmRldjAwMTpzM2NyM3Q...

{"method":"thing.event.property.post","params":{"power":1,"temperature":23.5}}
```

`heartbeat`：

```
POST /api/ingest/dev001/heartbeat

{}
```

`lwt`（设备侧离线前主动上报，或网关代设备公告离线）：

```
POST /api/ingest/dev001/lwt

{}
```

> 空 body 是**合法**的（与 MQTT 空 payload 一致），不返回 `400`。

### 5.2 成功响应

```json
// 200
{
  "code": 200,
  "message": "成功",
  "data": {
    "deviceKey": "dev001",
    "messageType": "data",
    "topic": "device/dev001/data",
    "receivedAt": "2026-10-04T12:00:00",
    "accepted": true
  }
}
```

- `accepted` 恒为 `true`，语义为「**已受理并入队**」（见 §4.6、§8.5）。
- `receivedAt` 为服务端受理时刻，即写入 `IngestRecord.receivedAt()`、最终落 `message.sentAt` 的时间。

### 5.3 失败响应

| 场景 | HTTP | code | message |
| --- | --- | --- | --- |
| 缺少 / 非 `Basic` 凭据 | `401` | `6246` | 设备凭据缺失或非法 |
| 用户名格式非法（非 `productKey.deviceKey`） | `401` | `6246` | 设备凭据缺失或非法 |
| 设备不存在 / 产品未启用 / 设备被禁用 | `401` | `6246` | 设备凭据缺失或非法 |
| `device_secret` 不匹配 | `401` | `6246` | 设备凭据缺失或非法 |
| 路径 `{deviceKey}` 与凭据中的 `deviceKey` 不一致 | `401` | `6246` | 设备凭据缺失或非法 |
| `messageType` 不在白名单 | `400` | `6247` | 不支持的 HTTP 上报消息类型 |
| Body 超过 `max-payload-bytes` | `413` | `6248` | HTTP 上报载荷超出上限 |

> 失败响应体为统一 `Result` 信封：`{"code":6246,"message":"设备凭据缺失或非法","data":null}`。

### 5.4 MQTT ↔ HTTP 字段映射

| `IngestRecord` 字段 | MQTT（`MqttMessageHandler.messageArrived`） | HTTP（`HttpIngestServiceImpl`） |
| --- | --- | --- |
| `deviceKey` | `topic.split("/")[1]` | 路径 `{deviceKey}`（已校验 == 凭据中的 deviceKey） |
| `topic` | 真实订阅到的 topic | 合成 `device/{deviceKey}/{messageType}` |
| `messageType` | `topic.split("/")[2]` | 路径 `{messageType}` |
| `payload` | `new String(mqttMessage.getPayload(), UTF_8)` | 请求体原文字符串（`UTF-8`） |
| `qos` | `mqttMessage.getQos()` | `data`→`1`、`heartbeat`→`0`、`lwt`→`1` |
| `receivedAt` | `LocalDateTime.now()` | `LocalDateTime.now()` |

- 合成 topic `device/{deviceKey}/{messageType}` 与 MQTT 实际 topic 完全同形，故 `message.topic` 列语义一致。
- `message.direction` 由 `IngestPersistenceService` 统一置 `SUBSCRIBE`（不改）。

## 8. 上报处理流程

### 8.1 挂载点

```
HTTP 请求
  → DeviceCredentialAuthFilter（仅 /ingest/**；校验 Basic 凭据 → 通过则请求属性写入已认证 deviceKey）
  → HttpIngestController（POST /ingest/{deviceKey}/{messageType}）
  → HttpIngestService.ingest(deviceKey, messageType, payload)
       ├─ 校验 messageType 白名单（否则 6247）
       ├─ 校验路径 deviceKey == 已认证 deviceKey（否则 6246）
       ├─ 构造 IngestRecord(deviceKey, "device/{deviceKey}/{messageType}", messageType, payload, qos(messageType), now())
       └─ IngestPipeline.submit(record)          ← 与 MQTT 共用的唯一投递入口
  → 返回 200 + Result.success({deviceKey, messageType, topic, receivedAt, accepted=true})
```

- Controller **不**直接依赖 `ingest` 包，经 `HttpIngestService`（接口在 `service` 包，实现只在 `service.impl`）收敛，保持分层单向（满足 ArchUnit 规则）。
- `HttpIngestServiceImpl` 依赖 `IngestPipeline` 与 `HttpIngestProperties`，**不触碰任何 Mapper**。

### 8.2 鉴权链（`DeviceCredentialAuthFilter`）

`shouldNotFilter`：`!resolvePath(request).startsWith("/ingest/")`（`resolvePath` 剥去 `server.servlet.context-path` = `/api`，与 `ApiKeyAuthFilter.resolvePath` 同口径）。

`doFilterInternal` 流程：

1. 解析 `Authorization: Basic`，base64 解码为 `username:password`；缺失 / 格式非法 → 失败。
2. `deviceSecretService.parseUsername(username)` → `productKey` / `deviceKey`；`null` → 失败。
3. `request.getRequestURI` 路径段中的 `{deviceKey}` 与之比较；不一致 → 失败。
4. `deviceAccessGuard.resolve(productKey, deviceKey)` → `null` → 失败；`!isPermitted` → 失败。
5. `deviceSecretService.matches(password, meta.secretHash())` → `false` → 失败。
6. 全部通过 → `request.setAttribute(DeviceCredentialAuthFilter.AUTHENTICATED_DEVICE_KEY, deviceKey)` + `filterChain.doFilter(...)`。

失败 → 自写响应：`401` + `WWW-Authenticate: Basic realm="{app.http-ingest.realm}"` + `Result.error(ResultCode.DEVICE_CREDENTIAL_INVALID)`（UTF-8 JSON，注入 `ObjectMapper`），**不继续**链。

### 8.3 等价构造

```java
// HttpIngestServiceImpl
String topic = "device/" + deviceKey + "/" + messageType;
IngestRecord record = new IngestRecord(deviceKey, topic, messageType, payload, qosOf(messageType), LocalDateTime.now());
ingestPipeline.submit(record);
```

`qosOf`：`heartbeat` → `0`，其余（`data` / `lwt`）→ `1`（与 `MqttMessageHandler.subscribe()` 的订阅 QoS 对齐）。

### 8.4 等价性论证（字段级对照）

由 §5.4 的映射表，HTTP 与 MQTT 构造出的 `IngestRecord` **六个字段全部同构**（`deviceKey` / `topic` 同形 / `messageType` 同值 / `payload` 同源 / `qos` 对齐 / `receivedAt` 同义）。因此进入 `IngestPipeline.submit` 后：

- **分片一致**：`routeIndex(deviceKey)` 只依赖 `deviceKey`，同一设备经两种协议上报**落同一队列**，保证单设备有序；
- **落库一致**：`IngestPersistenceService.persist` 对二者无差别（`direction=SUBSCRIBE`、`resolveStatus` 按 `messageType`、`sentAt=receivedAt`）；`lwt` 的「不改 `last_seen`」保护对二者同样生效；
- **解析一致**：`ThingModelInterpretServiceImpl` 仅看 `messageType=="data"` 与 `payload`，二者走**完全相同**的 `upsertIfNewer`，故 `device_property_latest` 最终值一致；
- **旁路一致**：影子 / 告警 / 规则 / 场景 / 历史 / 命令回执 / OTA 全部由 `IngestDispatcher` 统一驱动，与来源协议无关。

⇒ 直接满足路线图 L11 验收句「HTTP 上报数据与 MQTT 上报在属性最新值上等价」。

### 8.5 背压与失败语义

- **入队满**：`IngestPipeline.submit` 在队列满 / 停机时走 `onOverflow`（`metrics.dropped("queue_full")` + `DeadLetterService.record`），**不抛异常**。因此 HTTP 侧仍返回 `200`（受理）—— 背压可见性由既有**死信记录 + metrics** 承担，与 MQTT 完全一致。
- **`app.ingest.enabled=false`**：与 MQTT 一致降级 —— 但 HTTP 侧**不做** `legacySyncHandle` 同步落库（该分支是 MQTT 回调专属回滚开关）。`app.ingest.enabled=false` 时 `HttpIngestService` 直接丢弃并记 WARN（避免在请求线程同步落库，污染 HTTP 超时）。**注**：`/ingest/**` 的开关是 `app.http-ingest.enabled`，与 `app.ingest.enabled` 正交（前者控入口，后者控管线）。
- **停机排空**：`IngestPipeline.@PreDestroy stop()` 的 `drainToDeadLetter` 同时覆盖 HTTP 与 MQTT 入队的消息。

## 9. 与既有链路的交互边界

- **摄取管线（T-14 / `IngestPipeline` / `IngestDispatcher`）**：**零改动**——HTTP 是**生产者**，只是调用既有 `submit`；不新增 fan-out 路、不改逐条 / 逐批结构。
- **落库（T-14 / `IngestPersistenceService`）**：**零改动**——HTTP 记录与 MQTT 记录走同一 `persist`，`direction=SUBSCRIBE`、`resolveStatus`、`lwt` 保护均复用。
- **物模型解析（T-14 / `ThingModelInterpretServiceImpl`）**：**零改动**——HTTP 上报 `data` 自动解析并 `upsertIfNewer`，与 MQTT 同一路径。
- **MQTT 接入（T-11 / `MqttMessageHandler` / `EmqxAuthServiceImpl`）**：**零改动**——不新增主题、不改 ACL、不改共享订阅、不改认证回调。
- **命令 / 影子 / 告警 / 规则 / 场景 / 历史 / OTA**：**零改动**且**自动生效**——全部由摄取管线统一驱动，与来源协议无关（T-15 / T-16 / T-17 / T-19 / T-23 / T-21 / T-22）。
- **设备身份体系（T-11 / `DeviceSecretService` / `DeviceAccessGuard`）**：**只读复用**其公共方法（`parseUsername` / `matches` / `resolve` / `isPermitted`），不改签名、不改语义；禁用 / 停用的**主动失效**对 HTTP 上报同样即时生效（与 ACL 回调同源）。
- **开放 API（`/external/v1` / `ApiKeyAuthFilter`）**：**零改动**——不新增上报端点，避免设备上报与第三方应用鉴权语义混淆（§4.2）。
- **内部回调（`/internal/**` / `InternalTokenFilter`）**：**零改动**——EMQX 认证 / ACL 回调不受影响。
- **死信（T-14 / `DeadLetterService`）**：**零改动**——HTTP 入队溢出 / 停机排空复用既有死信通道。
- **`SecurityConfig`**：**唯一改动点** —— 新增 `/ingest/**` 为 `permitAll` 并注册 `DeviceCredentialAuthFilter`（锚定 `JwtAuthenticationFilter`，见 §13）。

| 码 | 名称 | 文案 | HTTP |

| `6246` | `DEVICE_CREDENTIAL_INVALID` | 设备凭据缺失或非法 | `401` |

> - **不新增「入队失败」码**：`IngestPipeline.submit` 无返回值且不抛异常（§8.5），HTTP 一律以 `200` 受理，背压走死信 + metrics，**不新增同义码**。
> - **不新增「载荷非法」码**：Body 语义不预校验（§7），非法载荷由 T-14 解析环节兜底（既有 `THING_MODEL_PARSE_FAILED(6101)` / 死信）。

@Data

## 13. 安全与边界

- **凭据复用与同源**：HTTP 上报鉴权与 MQTT 认证 / ACL 回调**同源**（`DeviceAccessGuard`），产品停用 / 设备禁用经主动失效后**对 HTTP 上报即时生效**。
- **不泄露信息**：认证失败一律 `6246` + `401`，不区分「不存在 / 禁用 / 密钥错」，避免设备枚举。
- **路径与凭据强一致**：路径 `{deviceKey}` 必须等于凭据解析出的 `deviceKey`，**杜绝**「用合法设备 A 的凭据上报设备 B」的越权（§7、§8.2）。
- **BCrypt 逐次比对**：密钥比较走 `matches`（BCrypt），**不可缓存**（与 `EmqxAuthServiceImpl` 注释口径一致：缓存只消除 DB 查询，比较必须逐次计算）。
- **传输安全**：HTTP Basic 为明文凭据，**必须**部署在 TLS 反代之后（`https`）；DEPLOYMENT 文档须明示「禁止在无 TLS 的公网直接暴露 `/api/ingest/**`」。
- **载荷上限**：`max-payload-bytes`（默认 64KB）防大包内存放大；超限 `413` + `6248`。
- **不做越权能力**：HTTP 上报**只上行**，不能查询、不能下发命令、不能操作其它资源（§2.2）。
- **主链路隔离**：HTTP 上报经统一 `IngestPipeline` 有界队列，**不阻塞** HTTP 请求线程（`submit` 带 `offerTimeoutMs`，溢出走死信）；**不影响** MQTT 摄取与既有巡检。
- **`SecurityConfig` 登记**：新增 `.requestMatchers("/ingest/**").permitAll()`（鉴权由 `DeviceCredentialAuthFilter` 负责，与 `/internal/**` 同构）并注册该过滤器。
  - **过滤器顺序**：`DeviceCredentialAuthFilter` 以 `JwtAuthenticationFilter` 为锚点注册（`addFilterBefore`），与 `internalTokenFilter` 并列；**必须**保证 `jwtFilter` 的注册仍在锚点之前完成（既有注释：否则锚点无已知顺序会抛 `IllegalStateException`）。实施时补一条**过滤器顺序单测**固定「deviceCredentialFilter 早于 JwtAuthenticationFilter」。
- **不新增自有 MQTT 主题 / 不改 ACL**：HTTP 上报为入站 HTTP，**不经过**自有 EMQX（§4.4）。
- **无迁移**：零 DDL，见 §6。

| A1 | **路线图 L11 验收项（等价）**：同一设备先经 MQTT 上报 `{"method":"thing.event.property.post","params":{"power":1}}`，再经 HTTP 上报同法但 `power=2`；`device_property_latest` 的 `power` 最终为 `2`；两条 `message` 记录 `direction=SUBSCRIBE`，其中 HTTP 条 `topic=device/{deviceKey}/data` |
| A2 | HTTP 上报 `data` → 物模型解析生效：`device_property_latest` 按 `reportedAt` 守卫更新（`upsertIfNewer` 语义与 MQTT 一致；旧时间戳不覆盖） |
| A3 | HTTP 上报 `heartbeat` → 设备置 `ONLINE`；HTTP 上报 `lwt` → 设备置 `OFFLINE` **且 `last_seen` 不被改写**（与 `IngestPersistenceService` 既有保护一致） |
| A4 | 鉴权边界：无 `Authorization` / 非 Basic / 用户名无点 / 设备不存在 / 产品停用 / 设备禁用 / 密码错误 / 路径 `{deviceKey}` 与凭据不一致 → 全部 `401` + `6246`；`WWW-Authenticate` 头存在 |
| A5 | 载荷边界：`messageType=foo` → `400` + `6247`；body 超 `max-payload-bytes` → `413` + `6248`；空 body → `200`（合法） |
| A6 | **旁路全生效**：HTTP 上报 `data` 与 MQTT 上报同数据，**影子 / 告警 / 规则 / 场景 / 历史** 的产出一致（等价验证，与 A1 同源） |
| A7 | **主链路隔离**：并发 MQTT 与 HTTP 上报同一设备，`message` 无重复落库、无乱序（同 `deviceKey` 同队列）、摄取异常不影响 HTTP 响应 |
| A8 | **开关**：`HTTP_INGEST_ENABLED=false` 重启 → `/api/ingest/**` 不可用；MQTT 上报、控制台、既有巡检**不受影响** |
| A9 | 分片一致：同一 `deviceKey` 经 HTTP 与 MQTT 上报，落库顺序与同队列假设一致（`routeIndex` 只依赖 `deviceKey`） |
| A10 | 回归：既有后端测试（T-23 收口时 `mvn -B verify` **693 项**）全绿；前端 `lint` / `test` / `build` 全绿；`routes.spec.js` 断言不变 |
