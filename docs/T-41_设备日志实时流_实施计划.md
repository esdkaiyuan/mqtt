# T-41 设备日志实时流 实施计划

> 版本：v1.1　创建日期：2026-10-21　状态：**已交付**
> 目标：补齐 T-36 遗留的 X-3 设备日志实时流，让设备日志页在写入发生后自动刷新，而不是只能手动点「刷新」。

---

## 1. 为什么之前没做

设备日志不是一张表，而是查询时对四张表做 `UNION ALL`：

- `message`（上行 / 下行报文）
- `device_command_record`（命令生命周期）
- `device_event_record`（物模型事件）
- `device_status_history`（在线状态变更）

没有单一写入点，直接在 SQL 查询层挂钩无法实现实时推送；在四条写路径分别构造一份「完整日志条目」又会造成实时影子与分页查询两份数据不一致。

---

## 2. 本批方案（低风险）

**写路径只发「有更新」信号，前端按信号刷新时间线。**

```
IngestDispatcher（消息 / 事件 / 状态变更后）
        │
DeviceCommandServiceImpl（命令记录落库 / 终态后）
        │  notify(device)
        ▼
DeviceLogNotifier → RealtimeStreamService.publishEvent(ownerId, "device-log",
                     { deviceId, deviceKey, occurredAt })
        │
        ▼
前端 ui.events（保留 eventName）→ DeviceLog.vue
        ├─ 当前第 1 页：800ms 防抖后自动刷新
        └─ 非第 1 页：显示「有 N 条新日志 → 立即刷新」
```

### 关键决策

1. **事件只带设备标识，不带日志条目** —— 日志查询仍是唯一数据源，避免实时增量与分页结果出现两份真相。
2. **前端防抖刷新，不逐条插入** —— 一次上报可能同时产生 message / event / status 多条日志，逐条插入会让顺序与分页错乱；防抖后整页重查最稳。
3. **非首页不自动刷新** —— 用户正在翻旧日志时，自动重置到第 1 页会打断阅读；改为提示有新日志，由用户决定何时刷新。
4. **打开实时开关时从当前事件末尾开始** —— 避免开关打开瞬间把过去 200 条事件全部当成新日志刷新。
5. **通知失败静默** —— 日志已落库，SSE 订阅者掉线不能让写入链路失败；`DeviceLogNotifierImpl` 内部捕获异常只记 DEBUG。
6. **保留 SSE event 名** —— `realtime.js` 解析 `event:` 行并附到事件对象 `eventName`；无 event 行时对象形状不变，既有消费方零影响。

### 覆盖范围与限制

- 覆盖：所有进入摄取管线的数据（消息 / 事件 / lwt 状态 / OTA / 回执）+ 控制台命令下发（含离线入队、同步终态）。
- 未覆盖：**纯手工状态变更**（禁用 / 启用、超时巡检把命令置 TIMEOUT）不会即时通知；这些操作频率低，日志页手动刷新即可。
- 通知是「有更新」提示，不是日志内容本身；多副本下由一个副本收到事件并推给本副本订阅者，SSE 订阅本身按副本连接，行为一致。

## 5. 验收标准

1. 设备上报后，停留在日志第 1 页并开启实时开关时，时间线自动刷新；
2. 在第 2 页及以后时，不打断阅读，显示「有 N 条新日志」，点击后回到第 1 页；
3. 关闭开关后不再自动刷新；
4. 命令下发 / 离线入队后同样触发刷新；
5. 既有 SSE 消费方行为不变，后端 `verify` / 前端 lint+test+build 全绿。

## 7. 明确不做

- 实时日志条目逐条 append（分页顺序与四路 union 会错乱）；
- 手工状态变更 / 超时巡检的即时通知；
- 设备日志导出与实时流的联动（导出仍是一次性快照）；
- 跨副本 SSE 订阅迁移（连接粘在哪个副本就由哪个副本推送）。
