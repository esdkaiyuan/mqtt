## 1. 背景与目标

设备组织维度（分组 / 标签）随 T-18 落地后，规则引擎与告警中心却仍只能用「单设备 / 全部设备」两档圈定作用对象 —— 该语义由 `rule_definition.device_id` 与 `alert_rule.device_id` 两个可空列表达：`device_id IS NULL` 表示「该用户全部设备」，非空表示「仅这一台」。

设备一多，这个模型就不可维护：给某个车间的 50 台设备配同一条温度告警，只能建 50 条规则；想把规则收紧到「某车间」，只能逐台加。分组与标签已经能表达「哪些设备是一伙的」，但规则与告警读不到这个维度。

对标清单把该缺口记为 **G-6-3（规则作用域）**、**G-7-4 / G-8-4（告警作用域）**、**X-5（作用域粒度不足）**，均为 P1。

本链路目标：把 `rule_definition` 与 `alert_rule` 的作用域从两档扩为**四档** —— 「全部设备 / 指定设备 / 按分组 / 按标签」，**分组档含所有后代分组**；同时保持存量「单设备 / 全部设备」行为零变化，既有评估链路与抑制 / 冷却逻辑零回归。

## 2. 范围

### 2.1 在范围内

- 规则 / 告警 CRUD 的作用域校验：档位与字段一致性、分组 / 标签归属、数量上限、缺省推断。

- 前端：告警规则页与规则编辑器的作用范围选择器（四档 + 条件控件），列表「作用范围」展示。

## 3. 术语表

| 术语 | 含义 |
|------|------|
| 作用域 `scope_type` | 规则 / 告警的适用设备范围，四值：`ALL` / `DEVICE` / `GROUP` / `TAG` |
| 全部设备 `ALL` | 该用户全部设备（既有 `device_id IS NULL` 语义） |
| 指定设备 `DEVICE` | 单台设备（既有 `device_id` 非空语义） |
| 分组作用域 `GROUP` | 命中选中分组**及其所有后代分组**内的设备 |
| 标签作用域 `TAG` | 命中选中标签关联的设备（标签无层级） |
| 隶属集合 | 某设备所属分组（含祖先）与标签的 ID 集合 |
| 推评估 | 设备上报属性 / 事件时按设备反查适用规则（`onProperties` / `onEvents`） |
| 巡检 | 离线告警定时扫描（`AlertSweeperServiceImpl`） |

## 4. 作用域模型

### 4.1 判别列而非并集

批量操作（T-18 / T-22）用 `BatchTargetRequest` 表达「手选 ∪ 分组 ∪ 标签 ∪ 产品」的**并集**。规则 / 告警作用域**不采用并集**：

- 配置页语义是「这条规则管哪些设备」，四档互斥比并集直观；
- 并集下「全部设备」与其它维度叠加会产生歧义（「全部设备 ∪ 某分组」等于全部设备）；
- 并集会把匹配判定与 SQL 过滤复杂化，而四档判别足以覆盖真实诉求。

故用 `scope_type` 判别列 + 每档各自的数据列，同一时刻只有一档生效。

### 4.2 存储

| 列 | 类型 | 说明 |
|----|------|------|
| `scope_type` | VARCHAR(16) NOT NULL | 四值判别列 |
| `device_id` | BIGINT NULL | `DEVICE` 档使用（保留既有列与外键，语义不变） |
| `group_ids` | TEXT NULL | `GROUP` 档使用，JSON 数组文本 |
| `tag_ids` | TEXT NULL | `TAG` 档使用，JSON 数组文本 |

JSON 以文本落库，沿用 `rule_definition.action_config` 与 `webhook_config.events` 的既有口径；实体侧以瞬态视图字段（`List<Long>`）暴露给前端，沿用 `RuleDefinition.actionConfigView` 的口径 —— 库中不暴露双重形态，响应中不给前端裸 JSON 串。

为什么不建关联表：作用域集合小（受分组 / 标签数量与上限约束），关联表需新增四张表与一整套 CRUD；且本期匹配在 Java 侧完成（见 §4.3），SQL 不需要 JSON 或关联查询，关联表的唯一收益（SQL 可 JOIN）用不上。

作用域 JSON 的解析与序列化统一走工具 `ScopeJson`（`toIdList` / `write`）：服务层用它装配响应视图，评估层用它做匹配，避免两处各写一份解析逻辑而漂移。

### 4.3 匹配方向：按需匹配而非预展开

分组档含子分组，有两种实现方向：

- **(a) 落库预展开**：保存时把选中分组展开为「自身 + 全部后代」写入 `group_ids`；
- **(b) 匹配时上溯**：落库只存选中分组，匹配时把设备的分组隶属上溯到祖先再求交。

选 **(b)**。分组树在规则存续期内可能被移动 / 重命名 / 增删：

- (a) 会因树变更而失效，必须在分组写路径挂重算钩子，把「规则域」耦合进「分组域」，且重算是一次跨表批量写；
- (b) 的存储与树变更解耦 —— 匹配以设备当前隶属为准，天然反映最新树形，无需任何重算。

匹配判定为纯函数 `ScopeMatcher.matches(scope, deviceId, memberships)`：

| 档位 | 命中条件 |
|------|----------|
| `ALL` | 恒命中 |
| `DEVICE` | `scope.deviceId == deviceId` |
| `GROUP` | `scope.groupIds ∩ memberships.groupIds ≠ ∅` |
| `TAG` | `scope.tagIds ∩ memberships.tagIds ≠ ∅` |

其中 `memberships` 由 `DeviceScopeService.memberships(userId, deviceId)` 解析：

- **分组隶属**：设备直接分组（`device_group_relation`）∪ 各分组沿 `parent_id` 上溯到的全部祖先，在内存中基于该用户平铺分组表上溯（一次 `list` 即可，不逐台查库）；
- **标签隶属**：设备标签（`device_tag_relation`）。

一次评估调用解析一次，供该次调用内全部规则复用，匹配本身是纯内存集合运算。

### 4.4 作用域 → 设备集合（巡检方向）

离线巡检以「规则 → 设备」方向工作（先取规则，再找作用域内离线设备），需要 `DeviceScopeService.deviceIds(userId, scope)`：

| 档位 | 设备集合 |
|------|----------|
| `ALL` | **空集**，表示「不限设备」（交由巡检的全量分支处理，不物化该用户全部设备 ID） |
| `DEVICE` | 单元素集合 |
| `GROUP` | 选中分组 `descendantIds` 展开后取 `deviceIdsByGroupIds` |
| `TAG` | `deviceIdsByTagIds` |

实现复用 `DeviceGroupService.descendantIds` / `deviceIdsByGroupIds` 与 `DeviceTagService.deviceIdsByTagIds`，归属校验复用 `getOwned`，去重后返回。`ALL` 之所以返回空集而非物化全部设备 ID：巡检的离线查询本就支持「不限设备」的 `deviceId = null` 分支，物化全部设备 ID 会在大用户下生成超长 IN 列表，收益为负。

### 4.5 为什么两个方向都要

推评估每次只面对**一台**设备、却要判定**全部规则**，设备 → 隶属方向最省（一次解析、多次复用）；巡检每次面对**一条**规则、却要筛**全部设备**，作用域 → 设备集合方向最省。两个方向各服务一条热路径，共用同一份作用域模型与同一套归属校验，不构成重复实现。

## 5. 数据模型

迁移 `V16__rule_alert_scope.sql`：**只加列与索引、不改既有列**，`V1`~`V15` 零改动。

### 5.1 `alert_rule` 追加列

| 列 | 类型 | 说明 |
|----|------|------|
| `scope_type` | VARCHAR(16) NOT NULL DEFAULT 'ALL' | 作用域档位 |
| `group_ids` | TEXT NULL | `GROUP` 档分组 ID JSON 数组 |
| `tag_ids` | TEXT NULL | `TAG` 档标签 ID JSON 数组 |

回填（覆盖存量行，新行由默认值承担）：

```sql
UPDATE alert_rule
SET scope_type = CASE WHEN device_id IS NULL THEN 'ALL' ELSE 'DEVICE' END;
```

索引 `idx_alert_rule_scope (user_id, scope_type)` 支撑 §7.2 的档位过滤。

### 5.2 `rule_definition` 追加列

同上三列、同上回填；索引 `idx_rule_scope (user_id, scope_type)`。

两表既有 `device_id` 列与外键保持不变 —— `DEVICE` 档语义与改造前的「单设备」逐位一致，`ALL` 档等价于改造前的 `device_id IS NULL`。

## 6. 参数校验

| 对象 | 规则 |
|------|------|
| `scopeType` | 仅接受 `ALL` / `DEVICE` / `GROUP` / `TAG`，其余返 `6268`（告警）/ `6269`（规则） |
| 档位与字段一致性 | `ALL` 要求 `deviceId` / `groupIds` / `tagIds` 皆空；`DEVICE` 要求 `deviceId` 非空且其余为空；`GROUP` 要求 `groupIds` 非空且其余为空；`TAG` 要求 `tagIds` 非空且其余为空；不一致返 `6268` / `6269` |
| `deviceId` | 非空时须为当前用户设备，越权沿用既有 `DEVICE_NOT_OWNED` |
| `groupIds` | 每项须为当前用户分组（`DeviceGroupService.getOwned`），越权 `403`；去重；数量 ≤ `app.scope.max-targets`，超出返 `6268` / `6269` |
| `tagIds` | 每项须为当前用户标签（`DeviceTagService.getOwned`），越权 `403`；去重；数量 ≤ `app.scope.max-targets`，超出返 `6268` / `6269` |
| 缺省推断 | `scopeType` 为空时按 `deviceId` 是否为空推断为 `DEVICE` / `ALL`，兼容仅传 `deviceId` 的既有客户端 |

校验落在既有 `applyRequest` 私有方法内（告警与规则各一处），与现有集中校验口径一致 —— 非法配置统一抛业务异常，不引入 Bean Validation。

## 7. 处理流程

### 7.1 规则推评估（`RuleEvaluationServiceImpl`）

`onProperties` / `onEvents` 流程：

1. 加载该用户启用规则（既有短 TTL 缓存不变，缓存条目仍只存规则定义）；
2. 解析一次设备隶属 `DeviceScopeService.memberships(userId, deviceId)`；
3. 逐规则以 `ScopeMatcher.matches` 取代原 `inScope(rule, deviceId)` 静态判定。

规则缓存不携带作用域解析结果 —— 匹配是纯内存运算，无需为作用域引入额外的缓存失效面。

### 7.2 告警推评估（`AlertEvaluationServiceImpl`）

`selectEnabledForDevice` 的 SQL 由「`device_id IS NULL OR device_id = #{deviceId}`」改写为档位判定：

```sql
AND ( scope_type = 'ALL'
      OR (scope_type = 'DEVICE' AND device_id = #{deviceId})
      OR scope_type IN ('GROUP', 'TAG') )
```

返回后对 `GROUP` / `TAG` 档用 `ScopeMatcher` + 设备隶属过滤；`ALL` / `DEVICE` 档已由 SQL 精确保证，Java 侧不再判定。

为什么 `GROUP` / `TAG` 不下推到 SQL：需要递归祖先（`WITH RECURSIVE`）或 JSON 交集（`JSON_OVERLAPS`，MySQL 8.0.17+），可移植性与可读性都差；而该档规则数受单用户规则上限约束，Java 过滤成本可控。`idx_alert_rule_scope` 让「同用户 + 档位」的取数走索引。

### 7.3 离线告警巡检（`AlertSweeperServiceImpl`）

`sweepRule` 改为按作用域取设备集：

- 先以 `DeviceScopeService.deviceIds(userId, scope)` 解析作用域设备集；
- 改调 `DeviceMapper.findOfflineDevicesForAlert` 的 IN 变体（新增 `deviceIds` 参数）：`ALL` 档传空集表示不限（保持既有 `deviceId = null` 的全量语义），`DEVICE` 档传单元素，`GROUP` / `TAG` 档传解析结果；
- `recoverOnline` 的在线设备筛选同样按作用域设备集过滤，替代原先「`device_id` 非空则单台、否则全量」的分支。

`LIMIT #{limit}` 语义不变：无论哪档，单轮单规则取离线设备仍受 `sweepBatchSize` 截断。

### 7.4 与既有链路的关系

不新增 MQTT 主题、不改 ACL、不改 `emqx-init.sh`；`IngestPipeline` / `IngestDispatcher` / `MqttMessageHandler` 一行不改；分组与标签的写路径（`DeviceGroupServiceImpl` / `DeviceTagServiceImpl`）一行不改。

## 8. 交互边界

| 边界 | 约定 |
|------|------|
| 与 T-18 分组 / 标签 | 只读复用 `descendantIds` / `deviceIdsByGroupIds` / `deviceIdsByTagIds` / `getOwned`，不写分组域；分组删除前置校验已保证「有子分组或有设备的非空分组」不可删，作用域引用**不阻塞**分组删除 —— 删除后匹配自然落空（见自审第 5 条） |
| 与 T-19 规则引擎 | 仅以 `ScopeMatcher` 替换 `inScope`；规则缓存、冷却锚点、执行落库与投递链路不变 |
| 与 T-17 告警评估 | 仅以作用域判定替换设备过滤；评估四步、抑制窗口与恢复逻辑不变 |
| 与 T-27 通知渠道 | 无耦合；作用域只决定「是否触发」，不改变触发后的通知分发 |
| 与 T-22 / T-18 批量目标 | 语义相近但独立：批量是「一次性目标并集」，作用域是「长期适用集合」；本期不合并、不共用请求体 |
| 与前端 | 作用域四档 + 条件控件；仅传 `deviceId` 的既有客户端按 §6 缺省推断继续可用 |

## 9. 接口设计

### 9.1 端点

不新增端点。`AlertRuleController`（`/alert-rules`）与 `RuleController`（`/rules`）的创建 / 更新请求体追加 `scopeType` / `groupIds` / `tagIds`；列表 / 详情响应追加同名回显字段（`groupIds` / `tagIds` 以 ID 数组返回，`scopeType` 以字符串返回）。

## 12. 安全与边界

- 作用域内分组 / 标签一律按 `user_id` 归属校验，越权返 `403`（复用 `getOwned`）。
- 不引入跨租户可见面：推评估按「设备归属用户」加载规则，匹配只在该用户自己的分组 / 标签与设备间进行。
- 匹配异常逐条隔离，只记 WARN，不冒泡到摄取与巡检链路（沿用既有 `try/catch` 口径）。
- 迁移只加列与索引，`V1`~`V15` 零改动；应用回滚后新列不影响旧代码（旧代码不读新列）。
- `group_ids` / `tag_ids` 只落 ID，不落名称快照 —— 名称变更后展示随分组 / 标签实时变化，避免快照与实体不一致。

## 附：设计自审

1. **是否动到底层架构**：否。规则评估的作用域判定、告警评估的设备过滤与离线巡检的作用域取数三处替换为等价或更宽的作用域判定，评估四步、抑制窗口、冷却锚点、执行与通知链路均不变；改动面为「两表三列 + 一个作用域服务 + 三处判定替换」，符合「先补齐功能缺口，再动底层架构」。
2. **是否新增第二套写路径**：否。作用域随规则 / 告警的既有创建 / 更新单入口写入，校验落在既有 `applyRequest` 内；不新增端点、不新增独立作用域写接口。
3. **是否引入跨租户越权面**：否。分组 / 标签归属逐项 `getOwned` 校验；推评估按设备归属用户加载规则，匹配只在该用户自有的分组 / 标签与设备间进行；越权统一 `403`。
4. **回滚是否安全**：物理层只加列与索引，`V1`~`V15` 零改动；应用回滚后旧代码不读新列，存量行回填值（`ALL` / `DEVICE`）恰好等价于旧语义，无需回滚脚本。
5. **遗留待定**：分组删除不阻塞作用域引用 —— 删除后该分组从 `group_ids` 中「失联」，匹配自然落空，规则静默降级为「少管一批设备」。是否需要「删除前提示被 N 条规则引用」的软约束，另立任务评估；本期以「分组删除前置校验已限制非空分组不可删」作为第一道防线，并接受静默落空。
6. **遗留待定**：`scope_type` 未加 CHECK 约束（MySQL 8 对枚举可用 CHECK，但既有表均未使用），取值约束由服务层校验保证；若后续统一引入 CHECK 约束，另立任务一并补齐。
