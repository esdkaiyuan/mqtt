### A+B 的实现策略（关键设计决策）

**A 与 B 共用数据模型，唯一差异是 `device_point_table.executor` 一列**：

- `EDGE` —— 路线 A：点表下发给边缘网关，网关自行采集（平台不碰现场网络）
- `PLATFORM` —— 路线 B：平台侧主站按点表轮询采集

这样两条路线可**按设备逐台灰度切换**，不必二选一；`Product.protocol_type` 是两者共同的挂载点。

## 0. 结论先行

现状调研得出三条**与直觉相反**的判断，直接决定改造路线：

| # | 判断 | 依据 | 影响 |
|---|------|------|------|
| 1 | 「设备只支持 ESP」**不是协议层限制**。`Product` 表无 `protocol_type` 字段，纯 Modbus 设备**今天就能登记**——只要把它建模成一台"网关/采集器"。 | `Product.java` 字段全集无接入协议维度 | 卡点不在"能不能登记"，而在**网关是"代连 MQTT"而非"边缘驱动"** |
| 2 | 平台侧 Modbus 主站是 T-24 **主动划出的边界**，不是遗漏。 | `T-24_设计文档.md:130-133` 明确"协议转换在边缘侧完成"，理由是需常驻轮询器 + 点表模型 + 连接池 | 推翻它=新建一个子系统，须作为独立立项而非"扩展" |
| 3 | 文档**不是缺内容，是缺"权威单一源"**。主题规范只存在于 ESP32 手册散文、错误码 98 个枚举只在前端留了 10 条摘录、Alink payload 散落在 5 份 T-xx 设计文档里。 | 见 §3.3 | 文档工作量的大头是**收敛与生成**，不是写作 |

**总体路线主张：不推翻边缘转换的架构判断，但要补齐三件事**——① 设备接入从"ESP32 一家"扩展为"多协议网关 + 多厂商芯片"；② 把协议/契约从散落文档**收敛为可生成的权威源**；③ 把日志与可观测从"能看"升级为"能定位"。

## 1. 现状诊断：与一线厂商的差距

### 1.1 三条能力线的成熟度

| 能力线 | 现状 | 一线厂商应有 | 定性 |
|--------|------|-------------|------|
| 设备接入 | 一机一密 + X.509/JWT + 网关代连；**无批量注册/一键激活** | 批量注册、设备激活流程、烧录凭据工具 | **P0 阻断** |
| 协议覆盖 | MQTT + HTTP 上报；边缘转换策略已定 | 多协议网关驱动 + 点表模型 | **P1 分歧点** |
| API 文档 | 170 个 `@Operation`，**覆盖率 100%** | 缺 SecurityScheme、缺产物导出 | P0（低成本高收益） |
| 协议文档 | 主题/ACL/payload 无权威文档 | 单一权威协议规范 + 版本化 | P0（低成本高收益） |
| 日志 | 设备日志 4 表 UNION（**设计不错**）；应用日志**纯文本无 traceId** | 结构化 + 全链路追踪 + 集中留存 | P0（最薄弱） |
| 可观测 | Micrometer 指标齐全 + Prometheus 端点 | 指标告警规则、死信闭环、readiness | P1 |

### 1.2 最薄弱的三个点

**① 应用日志：全仓库 0 个 `logback-spring.xml`、0 个 MDC/traceId、0 处结构化输出。** 落盘只靠 Docker `json-file`（20m×5=100MB），容器重建即丢，排障只能 `docker compose logs` 关键字匹配。**这是商用化的第一道红线**——客户报障时你无法定位单次请求。

**② 死信只能看不能动。** `ingest_dead_letter` 表设计了 `REPLAYED`/`DISCARDED` 状态、含 `attempts`/`error_message`，但 `DeadLetterController` **只有分页查询，无任何写路径**。消息丢了只能手工改库。

**③ 文档承诺了不存在的能力。** 前端 `apiEndpoints.js:169` 已对外宣称「429 超出密钥调用频率限制」，而全仓 grep `RateLimit` **零命中**。这是对外合规风险，须优先处理（要么实现，要么撤文案）。

### 阶段三：设备接入扩展（P1，含架构分歧点）

#### 3.1 必做：批量注册与激活流程

当前 `DeviceController` 只有单个 `POST /devices`，设备创建后即 `INACTIVE`；`DeviceBatchController` 的批量能力**全是"已存在设备的运维操作"**（commands / enable / disable / groups / tags）。这与阿里云/腾讯云的「批量注册实例 → 激活 → 烧录凭据」标准流程断层。

- 批量创建设备（CSV 导入 / API 批量）
- 设备激活流程与激活码
- 凭据批量分发（导出格式复用既有 `exportCredentials`）

#### 3.2 关键决策点：边缘驱动 vs 平台侧协议栈

这是**必须拍板的第一件事**。两条路线：

**路线 A · 强化边缘（延续 T-24 判定，推荐起步）**
- 平台只认物模型，协议转换在边缘侧完成
- 补齐"边缘驱动模式"：网关设备类型 + 点表下发给网关 + 网关负责 Modbus/OPC-UA 采集
- **优点**：无需平台侧可达现场网络，运维面不陡增，符合当前架构惯性
- **代价**：平台看不到"网关→子设备"的实时层级；点表管理要放在网关侧或另建配置通道

**路线 B · 平台侧 Modbus 主站（推翻 T-24）**
- 新建采集子系统：轮询器 + 点表模型 + 连接池 + 断线重连
- **优点**：控制台可见完整拓扑、可直接下发写寄存器命令，体验最接近阿里云
- **代价**：平台引入对现场网络的可达性要求（穿透/防火墙），运维面陡增；需新增 `point_table`/`driver_config` 表

> **建议**：先走 A，用真实客户诉求检验。若确有"必须平台下发写寄存器"的强场景，再以独立立项走 B。
>
> 无论走哪条，`Product` 表都需要新增 `protocol_type` / `driver_id` 维度——这是当前**完全缺失**的接入协议抽象。

#### 3.3 样例层重建

`sketch_jul21a/esp32_firmware`（ESP32-S3 + MPU6500，PlatformIO，**走裸 WebSocket**）与 `arduino_firmware`（硬编码 SSID `8202`、IP `192.168.125.19`）**都还是 WebSocket 时代的产物，与现有 MQTT 平台完全脱节**。仓库内 **0 个** Modbus/OPC-UA/LoRa/BLE 样例。

- 新建 `examples/` 目录，与 `sketch_jul21a/`（历史归档）分离
- 覆盖：ESP32 / ESP8266 / 树莓派 Python / 边缘网关（Modbus→MQTT）/ 各云厂商 SDK
