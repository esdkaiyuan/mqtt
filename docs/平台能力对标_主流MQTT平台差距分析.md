# 主流 MQTT / IoT 平台能力对标与差距分析

> 版本：v1.0　创建日期：2026-10-26　状态：持续更新
> 对标对象：阿里云 IoT、ThingsBoard、AWS IoT Core、EMQX Cloud / EMQX Enterprise、华为云 IoTDA、ThingsCloud。
> 目的：回答「本平台还缺什么、哪些值得补、按什么顺序补」。本轮已落地的补强见 [T-53 实施计划](T-53_平台治理与规模化补强_实施计划.md)，逐项可认领的存量清单见 [头部平台对标_尚未补齐功能项清单](头部平台对标_尚未补齐功能项清单.md)。

## 1. 平台定位差异

| 维度 | 本平台 | 一线公有云 IoT | 开源 / 私有化平台（ThingsBoard / EMQX） |
|---|---|---|---|
| 部署 | 自部署 Docker Compose，单租户、多用户 | 托管 SaaS，多租户 | 自部署，可多租户 |
| 数据归属 | 用户级 `user_id` 隔离 | 实例 / 产品级隔离 | 租户 / 客户级隔离 |
| 强项 | 设备建模 + 命令 / 影子 + 规则 / 告警 / 场景 + OTA + 看板 / HMI + Modbus 主站，一条链路完整 | 生态、设备量大、边缘与 AI 集成 | Broker 性能 / 规则 SQL / 数据桥接 |
| 弱项 | 多租户、脚本化数据解析（声明式映射已具备）、数据桥接、SDK 生态 | 私有化成本、定制受限 | 业务侧开箱能力需二次开发 |

> 结论：本平台不应按「公有云规模」补齐所有能力，而应按**自部署商用平台**的场景取舍。多租户、计费等 SaaS 能力优先级低于数据桥接、脚本化解析与开放集成。

## 3. 本轮（T-53）已补齐

| 能力 | 落点 | 对标意义 |
|---|---|---|
| 审计日志 | `audit_log` + 拦截器 + 查询 / 导出 + 前端页 | 对齐 ThingsBoard / 阿里云的操作审计；写操作可追溯到用户、IP、资源与结果 |
| 设备台账 CSV 导入 / 导出 | `CsvReader` / `DeviceImportService` / `DeviceImportController` / 导出端点 | 对齐主流平台的设备批量迁移；逐行独立事务 + 一次性凭据 |
| 开放 API 批次二 | 分组 / 标签 / 点位表 / 规则执行 / 场景执行 / 看板只读端点 | 补齐「控制台有、开放侧没有」的查询能力 |
| HTTP 上报限流与幂等 | `HttpIngestGuard` + `Idempotency-Key` | 生产接入可靠性：防重试风暴、防重复落库 |
| OTA 固件版本跟踪与降级拦截 | `device.firmware_version` + `FirmwareVersionComparator` | 对齐主流平台设备版本治理：成功回写、防乱序回退、建任务阻止降级 |
| Payload Codec 数据映射（T-55） | `product.payload_codec` + 声明式模板 | 非 Alink 报文无需脚本即可进入物模型解析与全部下游链路 |
| 开放 API 写操作与 SDK 示例（T-57） | `/external/v1` 设备 / 规则 / 场景写端点 + D6 | 第三方从「监控」走向「运营」，最小 SDK 降低接入成本 |
| TOTP 多因素认证（T-58） | `sys_user` MFA 三列 + `TotpUtil` / `MfaCrypto` + 二步登录 | 账号安全基线：密码泄露不再直接失守，密钥加密存储 |
| Kafka 数据桥接（T-56） | `FORWARD_KAFKA` + `KafkaMessageForwarder` + `app.bridge.kafka` | 规则 / 场景命中数据直达数据湖 / 流处理 |

### 3.1 T-54 追加补齐

| 能力 | 落点 | 对标意义 |
|---|---|---|
| 设备当前固件版本 | `V32` + 设备详情 / 开放 API / 台账导出 | 运维可直接看到设备版本，支撑版本分布与升级决策 |

## 4. 剩余差距与优先级建议

### 4.1 P1（自部署商用平台应优先补）

| 能力 | 为什么重要 | 建议做法 |
|---|---|---|
| 自定义脚本解析 / 复杂变换 | 现场仍有需要表达式运算、字符串处理、多模板分支的报文 | 在 Payload Codec 之上评估受限脚本引擎（资源 / 安全沙箱），或扩展声明式函数集 |
| 产品 / OTA 开放写操作 | 第三方需要维护产品与固件升级，而非只读查询 | 设备 / 规则 / 场景写已交付；后续评估产品 / 物模型与 OTA 任务写的审计与回滚语义 |
| 数据库 / 时序库数据桥接 | 一线平台规则引擎的核心价值是「把数据送到该去的地方」 | Kafka 已交付（T-56）；`FORWARD_DB` 需数据源与 DDL 管理，另立任务 |
| SSO / 多租户 | 企业客户需要统一身份与租户隔离 | MFA 已交付；SSO 可后置 OIDC，多租户需评估归属模型改造 |
| 跨设备属性对比 | 看板目前只能单设备多属性 | 前端在 `usePropertyHistory` 上支持多设备序列；后端已有 `deviceIds` 数组能力 |

### 4.2 P2（规模化 / 体验增强）

- OTA 固件对象存储 / CDN、SHA-256 + 签名校验；
- HMI 分享 / 外链、自由拖拽组态、桌面端工程代码导出；
- MQTT 5 特性（会话过期、消息过期、Retained 管理）；
- 多租户 / 组织隔离（SaaS 化前置）；
- OPC-UA / Modbus RTU / 串口驱动；
- 时序预物化、按产品分档保留、跨设备对比；
- 审计日志外部归档（S3 / 日志平台）、Prometheus 告警规则文件；
- 场景秒级定时、执行记录归档；
- 分组拖拽排序、看板 / 属性时序开放 API（本轮已补看板 / 执行记录只读，属性时序已有设备级端点）。

### 4.3 明确不做 / 保持设计取舍

- **MQTT 下行固定 QoS 1、不保留**：避免设备离线残留旧命令，已有影子补发兜底；
- **告警窗口单副本内存**：跨副本持久化成本高于收益，重启后重新累计可接受；
- **场景 / 规则类未拆独立子包**：当前规模由 ArchUnit 守边界，物理拆分推迟到代码量或部署需求触发；
- **message 表分区 / Kafka**：按 R5 数据量门槛触发，不在当前优先级。

## 5. 建议演进路线

| 批次 | 主题 | 主要内容 |
|---|---|---|
| T-53（已交付） | 平台治理与规模化 | 审计、设备导入导出、开放 API 批次二、HTTP 限流与幂等 |
| T-54（已交付） | OTA 版本治理 | 设备固件版本跟踪、成功回写与防回退、建任务降级拦截 |
| T-55（已交付） | 数据解析 | 产品级 Payload Codec：非 Alink JSON 声明式映射、校验 / 渲染 / 缓存 |
| T-56（已交付） | 数据桥接（Kafka） | 规则 / 场景 `FORWARD_KAFKA`、`app.bridge.kafka`、Topic/Key/载荷模板 |
| T-57（已交付） | 开放生态 | 开放 API 设备 / 规则 / 场景写操作 + 最小 SDK 示例 |
| T-58（已交付） | 账号安全 MFA | TOTP 动态口令、二步登录、密钥加密存储、全局开关 |
| T-59（建议） | 安全与租户 | OIDC SSO、多租户隔离方案评估、恢复码与强制 MFA |
| T-60（建议） | OTA 与边缘 | 对象存储 / CDN、固件签名、OPC-UA / RTU |
| T-61（建议） | 可视化与体验 | 跨设备对比、HMI 分享 / 拖拽、分组拖拽排序 |

> 排期原则：先补「数据能不能用」（解析已补，桥接 / 脚本化待补），再补「第三方能不能集成」（写 API 与最小 SDK 已补，正式 SDK 待补），最后补「规模化与合规」（租户 / MFA / 对象存储）。每批仍按仓库既有约定：先写实施计划，再落代码 / 迁移 / 测试 / 文档回填。
