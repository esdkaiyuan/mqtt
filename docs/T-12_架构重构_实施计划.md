# T-12 架构重构 实施计划

> **给执行者：** 本计划按阶段与任务顺序执行。每个任务以「先写失败测试 → 验证失败 → 最小实现 → 验证通过 → 提交」的循环推进；步骤使用 `- [ ]` 勾选跟踪。
> **阶段可并行性：** R1 与 R4 可并行（无文件交集）；R2 依赖 R1 的摄取管线；R3 依赖 R2 的多副本形态。**不要跳过 R0**——没有基线就无法验收「吞吐 ≥ 3 倍」。

**Goal:** 在不拆微服务的前提下，把「接入 → 缓冲 → 落库 → 推送」改造为可水平扩展、失败不丢消息、生产配置正确的形态，并把前端工程化补齐到可回归。

**Architecture:** 模块化单体（边界由 ArchUnit 强制，物理拆分按 R5 触发）+ 进程内异步批量摄取 + EMQX 共享订阅去重 + Redis Pub/Sub 跨副本广播。核心原则：**MQTT 回调线程内禁止任何 DB / HTTP 操作**。

**Tech Stack:** Spring Boot 3.3.0（R3 升级）/ Java 17 / MyBatis-Plus 3.5.7 / MySQL 8.0 / Redis 7 / EMQX 5.0 / Flyway / Paho 1.2.5 / JUnit 5 + Mockito / Micrometer / Vue 3 + Vite / SSE

**Spec:** `docs/重构方案_现状评估与目标架构.md`

### 0.1 本轮新增的关键事实（Spec 未记录，已核实）

1. **EMQX 共享订阅可用于 MQTT 3.1.1 客户端**，逻辑全在 Broker 侧，客户端只需订阅 `$share/{group}/{topic filter}`。因此 **R2 不需要升级 Paho 即可实现多副本去重**，Spec 3.3 中「Paho 1.2.5 不支持 MQTT 5 故需换客户端」的约束不成立。参见 EMQX 官方文档：客户端只需修改订阅的 topic 内容，服务端完成全部共享订阅逻辑 [$TRAE_REF](https://docs.emqx.com/en/emqx/latest/faq/feature.html)[$TRAE_REF](https://www.emqx.com/en/blog/introduction-to-mqtt5-protocol-shared-subscription)。
2. **共享订阅不保证单设备消息顺序**：EMQX 的 `shared_subscription_strategy` 仅有 `random` / `round_robin` / `sticky` / `hash`（按 clientId 哈希），**没有按 topic 哈希** [$TRAE_REF](https://docs.emqx.com/zh/emqx/latest/configuration/mqtt.html)。因此 R2-3 必须配合 R1-2 的「状态更新时间戳守卫」，否则乱序的 `lwt` / `data` 会让设备状态错判。严格单设备有序只能走 R5 的 Kafka（按 deviceKey 分区）。
3. **nginx 会先于后端断开 SSE**：`docker/nginx.conf:65-75` 的 `location /api` 设置 `proxy_read_timeout 60s`，而服务端 `stream-timeout-ms=0`（永不超时）。当前 SSE 在无设备数据时 60 秒内无任何字节下行，**nginx 会在 60 秒断开连接**，前端 `api/realtime.js` 又无重连 → 实时数据静默停止。这是已存在的功能缺陷，R2-1 修复。
4. **EMQX 认证结果缓存**：EMQX 为外部数据源提供认证结果缓存，可显著减少对后端的回调次数 [$TRAE_REF](https://emqx.io/docs/en/latest/access-control/authn/authn.html)。但需确认 `emqx/emqx:5.0` 是否具备该能力；不具备时以后端 Redis 缓存兜底（R3-1）。
5. **激活 prod profile 会同时启用从未验证过的 JDBC 参数**：`application-prod.yml:6` 使用 `useSSL=true`，而基础配置用 `useSSL=false`。R1-1 激活 profile 后必须验证 MySQL TLS 连接可用。

## Global Constraints

- Java 版本固定 **17**；Spring Boot 在 R1/R2 保持 **3.3.0**（升级集中在 R3-3）
- 后端包根 `com.mqtt.cloud`；新增摄取包固定为 `com.mqtt.cloud.ingest`
- 所有 Controller 返回 `com.mqtt.cloud.common.Result<T>`；业务异常统一抛 `BusinessException(ResultCode)`
- **`server.servlet.context-path=/api`**：Controller 的 `@RequestMapping` 与 `SecurityConfig` 的 requestMatcher 必须使用**去掉 `/api` 之后**的路径；只有前端/nginx/curl 等外部 URL 才带 `/api`
- **不改动 Topic 结构**：`device/{deviceKey}/data`、`/heartbeat`、`/lwt`、`/cmd/#`
- **不引入新中间件**：R1/R2 仅使用已有的 MySQL / Redis / EMQX
- Flyway 迁移编号接续 V2，本计划占用 **V3**（死信表）、**V4**（`message` 分区）
- 新增业务码从 **6007** 起编号，追加到 `common/ResultCode.java` 枚举末尾（保持 `NAME(code, "message", HttpStatus.X)` 格式）
- 后端 Maven 命令在 `backend/` 目录下执行；compose 命令使用 `docker compose -f docker/docker-compose.yml`
- 每个任务结束必须提交，提交信息用中文，格式 `feat|fix|chore|docs|test|perf|refactor(scope): 描述`
- **Windows PowerShell 5** 环境：命令使用 PowerShell 语法，路径含中文需加引号

### 设计要点（必须遵守）

1. **回调线程零 DB / 零 HTTP**：`messageArrived` 只做「解析 topic + 构造 `IngestRecord` + `submit`」。
2. **单设备有序**：`submit` 按 `Math.floorMod(deviceKey.hashCode(), workerCount)` 路由到固定 worker 队列，同一 deviceKey 永远进同一队列。
3. **有界 + 可观测的溢出**：队列有界（默认 20000）。`offer(record, 50ms)` 失败时**不静默丢弃**，而是计入 `ingest.dropped` 指标 + 写死信表（R1-3）+ 限频 ERROR 日志。
   > 说明：阻塞回调线程可以形成对 Broker 的背压，但 Paho 1.2.5 的 `CommsCallback` 阻塞会连带阻塞 receiver 线程，可能触发 keepalive 超时导致重连风暴。因此选择「有界队列 + 显式溢出告警 + 死信兜底」，而非阻塞。
4. **批量落库**：按 `batch-size`（默认 500）或 `flush-interval-ms`（默认 200）双阈值 flush。
5. **设备解析批量化**：每批用一次 `findByDeviceKeys` 查询替代「每条消息一次设备查询」。
6. **状态更新时间戳守卫**：为 R2-3 共享订阅的乱序到达做准备，状态更新必须带 `last_seen` 条件（详见 R1-6）。
7. **同步回退开关**：`app.ingest.enabled=false` 时走原同步路径，用于 R1 出问题时的即时回滚。

- [ ] **Step 5: 实现 `IngestPipeline`（生命周期 + 路由 + 溢出）**

```java
package com.mqtt.cloud.ingest;

import jakarta.annotation.PreDestroy;
import lombok.extern.slf4j.Slf4j;
import org.springframework.boot.context.event.ApplicationReadyEvent;
import org.springframework.context.event.EventListener;
import org.springframework.stereotype.Component;

import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.BlockingQueue;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicBoolean;

@Slf4j
@Component
public class IngestPipeline {

    private final IngestProperties properties;
    private final IngestMetrics metrics;
    private final List<BlockingQueue<IngestRecord>> queues = new ArrayList<>();
    private final List<IngestWorker> workers = new ArrayList<>();
    private final AtomicBoolean running = new AtomicBoolean(false);

    // 构造器注入 IngestProperties / IngestMetrics / IngestWorkerFactory（worker 由外部按队列构造）

    /** 回调线程调用：只做路由与入队，禁止任何 DB / HTTP 操作。 */
    public void submit(IngestRecord record) {
        metrics.submitted().increment();
        int idx = Math.floorMod(record.deviceKey().hashCode(), queues.size());
        BlockingQueue<IngestRecord> queue = queues.get(idx);
        try {
            if (!queue.offer(record, properties.getOfferTimeoutMs(), TimeUnit.MILLISECONDS)) {
                onOverflow(record);
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            onOverflow(record);
        }
    }

    private void onOverflow(IngestRecord record) {
        metrics.dropped("queue_full").increment();
        // 限频告警：避免队列持续满时刷屏
        log.error("摄取队列已满，消息转入死信: deviceKey={}, topic={}", record.deviceKey(), record.topic());
        // 调用 IngestDeadLetterService.recordAsync(record, "queue_full")（R1-3 接入）
    }

    @EventListener(ApplicationReadyEvent.class)
    public void start() { /* 创建队列与 worker 并启动 */ }

    @PreDestroy
    public void stop() { /* 停止接收 → 排空至 shutdownDrainTimeoutMs → 剩余转死信 */ }
}
```

`stop()` 必须：
1. `running=false`，`submit` 直接走溢出分支（不再入队）
2. 逐个 worker `shutdown()` 并 `awaitTermination(shutdownDrainTimeoutMs)`
3. 仍未落库的批次转死信并记 `ingest.deadletter{reason=persist_failed}`

- [ ] **Step 6: 实现 `IngestWorker`（攒批 + 重试）**

单个 worker 持有自己的队列与线程：

```java
void loop() {
    List<IngestRecord> batch = new ArrayList<>(properties.getBatchSize());
    while (running || !queue.isEmpty()) {
        IngestRecord first = queue.poll(properties.getFlushIntervalMs(), TimeUnit.MILLISECONDS);
        if (first == null) continue;
        batch.add(first);
        queue.drainTo(batch, properties.getBatchSize() - 1);

        int attempt = 0;
        while (true) {
            try {
                List<ResolvedEvent> events = persistence.persist(batch);
                dispatcher.dispatch(events);
                metrics.persisted().increment(batch.size());
                break;
            } catch (Exception e) {
                attempt++;
                if (attempt >= properties.getMaxAttempts()) {
                    metrics.batchFailures().increment();
                    deadLetterService.recordBatch(batch, e.getMessage());
                    break;
                }
                sleep(properties.getRetryBackoffMs() * attempt);   // 线性退避，最多 3 次
            }
        }
        batch.clear();
    }
}
```

**注意：** `dispatcher.dispatch(events)` 必须在 `persist` 事务提交之后调用（`persist` 返回即已提交），否则会出现「推送了但库里没有」。

- [ ] **Step 7: 实现 `IngestPersistenceService`（批量落库）**

```java
@Service
@RequiredArgsConstructor
public class IngestPersistenceService {

    private final DeviceMapper deviceMapper;
    private final MessageMapper messageMapper;
    private final DeviceStatusHistoryMapper statusHistoryMapper;
    private final IngestMetrics metrics;

    @Transactional(rollbackFor = Exception.class)
    public List<ResolvedEvent> persist(List<IngestRecord> batch) {
        // 1. 批量解析设备：一次查询替代 N 次
        Set<String> keys = batch.stream().map(IngestRecord::deviceKey).collect(toCollection(LinkedHashSet::new));
        Map<String, Device> devices = deviceMapper.findByDeviceKeys(keys).stream()
                .collect(toMap(Device::getDeviceKey, identity()));

        // 2. 未注册设备：计数后丢弃（保持既有语义，但改为可观测）
        List<IngestRecord> known = batch.stream()
                .filter(r -> devices.containsKey(r.deviceKey()))
                .toList();
        metrics.dropped("unknown_device").increment(batch.size() - known.size());

        // 3. 批量写 message（direction=SUBSCRIBE）
        List<Message> messages = known.stream().map(r -> toMessage(devices.get(r.deviceKey()), r)).toList();
        messageMapper.insertBatch(messages);

        // 4. 设备状态：按 deviceKey 分组，取 receivedAt 最大者决定目标状态
        //    → 批量 update + 状态变化者批量 insert device_status_history
        //    详见 R1-6 的时间戳守卫实现
        ...

        // 5. 产出下游事件（Webhook / 实时通道）
        return known.stream().map(r -> new ResolvedEvent(devices.get(r.deviceKey()), r)).toList();
    }
}
```

- [ ] **Step 2: 多端订阅 + 异步投递 + 心跳**

`RealtimeStreamServiceImpl` 关键改动：

```java
    /** 订阅者：userId -> 该用户的所有连接（支持多标签/多端同时在线） */
    private final Map<Long, Set<Subscriber>> subscribers = new ConcurrentHashMap<>();

    @Override
    public SseEmitter subscribe(Long userId, boolean admin) {
        SseEmitter emitter = new SseEmitter(properties.getStreamTimeoutMs());
        Subscriber subscriber = new Subscriber(userId, admin, emitter);
        emitter.onCompletion(() -> removeQuietly(subscriber));
        emitter.onTimeout(() -> removeQuietly(subscriber));
        emitter.onError(e -> removeQuietly(subscriber));
        subscribers.computeIfAbsent(userId, k -> ConcurrentHashMap.newKeySet()).add(subscriber);
        startHeartbeatIfNeeded();          // 单一调度线程，避免每连接一个线程
        return emitter;
    }

    /** 本地扇出：快照订阅者后异步投递，绝不阻塞调用方（MQTT 摄取线程或 Redis 订阅线程） */
    public void publishLocal(Long deviceId, Long ownerId, String topic, String payload) {
        List<Subscriber> snapshot = subscribers.values().stream()
                .flatMap(Set::stream)
                .filter(s -> s.admin() || (ownerId != null && ownerId.equals(s.userId())))
                .toList();
        if (snapshot.isEmpty()) return;
        dispatchExecutor.execute(() -> snapshot.forEach(s -> sendQuietly(s, event)));
    }
```

心跳：用 `TaskScheduler`（`ScheduleConfig` 已有 `@EnableScheduling` 时可注入 `ThreadPoolTaskScheduler`；否则在 `RealtimeStreamServiceImpl` 内用单个 `ScheduledExecutorService`，`@PreDestroy` 关闭）每 `heartbeatIntervalMs` 向所有订阅者发送 SSE 注释帧 `:hb`，发送失败即摘除该订阅者。**无订阅者时停止心跳**，避免空转。

保留原 `publish(Device, String, String)` 方法签名（内部委托 `publishLocal`），保证 R1 回退路径与既有测试可用。

```java
    /** EMQX 可能把共享订阅的原始主题透传给授权回调，匹配前先剥离 $share/{group}/ 前缀 */
    private String stripSharedPrefix(String topic) {
        if (topic == null || !topic.startsWith(SHARED_PREFIX)) {

        int groupEnd = topic.indexOf('/', SHARED_PREFIX.length());
```

# 阶段 R5：触发式（不排期）

| 组件 | 触发条件 | 动作 |
|------|---------|------|
| 消息队列（Kafka / RocketMQ，按 deviceKey 分区） | 设备数 > 5000，或上行 QPS > 2000，或需要跨重启不丢消息，或**需要严格单设备有序** | 拆出 `ingest` 独立组件；EMQX 规则引擎/桥接投递，消费者批量落库 |
| 时序库（TDengine / ClickHouse） | `message` 表 > 1 亿行，或历史查询 P99 > 1s | 承载遥测查询，MySQL 只留元数据 |
| 物理 Maven 多模块拆分 | 后端代码 > 2 万行，或某逻辑模块需独立部署/伸缩 | 按 R3-2 的模块映射物理拆分 |
| 独立抓取/告警体系 | 需要 SLA 与值班 | Prometheus + Grafana + Alertmanager，接入 `ingest_dropped_total`、`ingest_deadletter_total` 告警 |

# 全局验收与回滚

## 回滚矩阵

| 阶段 | 回滚手段 | 代价 |
|------|---------|------|
| R1 | `INGEST_ENABLED=false` 回退同步落库；`V3`/`V4` 迁移不回退（表与分区保留无害） | 吞吐回到基线 |
| R1-5 分区 | 分区不可逆回退到非分区表需重建表；**因此设了执行门槛**，未过门槛不执行 | 需停机窗口 |
| R2-1 | `STREAM_TIMEOUT_MS` / `STREAM_HEARTBEAT_INTERVAL_MS` 调整；nginx SSE location 可移除 | 回到 60 秒断连 |
| R2-2 | `REALTIME_BROADCAST_ENABLED=false` 退回单副本本地推送 | 需同时把副本数降为 1 |
| R2-3 | 订阅主题去掉 `$share` 前缀，副本数降为 1 | 回到不可水平扩展 |
| R2-4 | `--scale backend=1` | 失去水平扩展 |
| R3-1 | `ACCESS_CONTROL_CACHE_TTL_SECONDS=0` 关闭缓存 | 认证延迟回到基线 |
| R4 | 前端按页面独立提交，可单页回滚 | 无 |

## 关键风险

| 风险 | 缓解 |
|------|------|
| 激活 prod profile 暴露未验证的 `useSSL=true` | R1-1 Step 6 显式验证，失败降级 `sslMode=PREFERRED` |
| 共享订阅导致单设备消息乱序 | R1-6 时间戳守卫；严格有序走 R5 Kafka |
| 批量落库的内存丢失窗口 | 有界队列 + 停机排空 + 死信兜底 |
| Redis 成为实时链路单点 | AOF + 端口收敛；失败必须告警（实时可丢，历史以 DB 为准） |
| `message` 分区改造锁表 | R1-5 执行门槛 + 副本库演练 + 停机窗口 |
| 异步化后吞吐仍不达标 | R0 基线先行，R1 验收量化对比；不达标则提前进入 R5 队列评估 |
| ArchUnit 规则首次运行大量失败 | 分阶段放宽规则集（先分层、后跨模块），但**不得**用 `@ArchIgnore` 绕过 |
