# T-25 认证方式扩展（Auth Mode Extension）设计文档

> 所属链路：L12 认证方式扩展（`docs/平台功能链路路线图.md` §3）
> 依赖链路：L1 设备接入与身份体系（T-11，设备凭据 `productKey.deviceKey` + `device_secret`、`product.auth_mode` 枚举预留、`product.topic_prefix` 默认值）、L11 多协议接入（T-24，EMQX 认证/授权回调链路与 HTTP 上报）
> 文档状态：已交付（2026-10-05）
> 最后更新：2026-10-06

## 1. 背景与目标

T-11 建立了设备接入的身份底座：用户名固定为 `{productKey}.{deviceKey}`，口令为 32 位 base62 的 `device_secret`，落库前经 BCrypt 哈希；`product` 表已预留 `auth_mode` 与 `topic_prefix` 两列，但 `auth_mode` 在创建产品时被固定写入 `SECRET`，X.509 与 JWT 两个枚举值仅存在于表结构而未参与任何判定。

T-24 打通了设备上报的多协议入口，但认证与授权回调仍只有一条口令通路：`EmqxAuthServiceImpl.authenticate` 只做 BCrypt 比对，`AclEvaluator` 的主题前缀写死为 `device/{deviceKey}`，`MqttMessageHandler.subscribe` 的共享订阅写死为 `device/+/...`。也就是说，设备一旦拿到 `device_secret` 就必须长期持有，缺少可轮换、可吊销、可免密下发的凭据形态。

T-11 §3.2 的 YAGNI 表对此有明确记录：

```
| mTLS 客户端证书、JWT 认证 | 仅在 product.auth_mode 预留枚举值，不实现 |
```

路线图 §3 的 L12 需求如下：

```
#### L12 · 认证方式扩展（拟 T-25）
- **目标**：落地 X.509 / JWT 认证与产品级 Topic 模板。
- **范围**：X.509 证书签发与吊销；JWT 认证；`topic_prefix` 模板变量化。
- **依赖**：无（但需存量设备刷机窗口）。
- **验收**：三种认证方式并存，EMQX 认证回调按产品 `auth_mode` 分派。
```

本次交付的目标：

1. 让 `product.auth_mode` 真正生效，产品可在 `SECRET` / `X509` / `JWT` 三种模式间选择。
2. 提供 X.509 的设备证书签发与吊销能力，证书与设备一一绑定，吊销后立即失去接入资格。
3. 提供 JWT 的设备令牌签发能力，令牌可设有效期，支持不改口令前提下的凭据轮换。
4. 把 `topic_prefix` 从固定值升级为含变量的模板，产品可自定义主题层级，`AclEvaluator` 与共享订阅随模板同步。
5. 认证模式或主题模板变更时，该产品下全部设备的认证缓存立即失效，避免新旧口径并存。
6. 三种模式共用同一条 EMQX 回调，按产品 `auth_mode` 分派，不改动 EMQX 的调用形状。

## 2. 范围

### 2.1 在范围内

| 项 | 说明 |
| --- | --- |
| `auth_mode` 落库 | 产品创建与更新接受 `auth_mode`，缺省回落 `SECRET` |
| X.509 证书签发 | 后台自建 CA 按 `{productKey}.{deviceKey}` 签发设备证书 |
| X.509 证书吊销 | 吊销记录落库，认证回调拒绝已吊销证书 |
| X.509 接入 | EMQX 启用 mTLS 监听器，取对端证书的 CN 作为用户名 |
| JWT 签发 | 后台按设备签发 JWT，载 `sub` 为 `{productKey}.{deviceKey}` |
| JWT 接入 | 设备以 JWT 作为 MQTT 口令，回调内校验签名与有效期 |
| 模板变量化 | `topic_prefix` 支持 `{productKey}` / `{deviceKey}` 两个占位符 |
| 授权同步 | `AclEvaluator` 按解析后的前缀判定，共享订阅按模板生成 |
| 缓存失效 | 产品 `auth_mode` 或 `topic_prefix` 变更时清空该产品设备缓存 |

### 2.2 不在范围内

| 项 | 归属 |
| --- | --- |
| EMQX 多认证器链与监听器级 `enable_authn` | 归运维配置，文档在 §4.1 说明取舍 |
| CRL 文件下发与 EMQX 原生吊销校验 | EMQX 5.0.26 无 `crl_check`，改由后端拒入，见 §4.3 |
| 子设备拓扑、网关代理接入 | 归 L13 规划，与本期无耦合 |
| 证书在线续期与 OCSP | 以短有效期加重签替代 |
| 设备侧证书生成与烧录工具链 | 归 `docs/ESP32_接入手册.md` 与产线流程 |
| 控制台登录 JWT（`app.jwt.secret`） | 归 T-11，与设备 JWT 语义不同，见 §4.4 |

## 3. 术语表

| 术语 | 含义 |
| --- | --- |
| `auth_mode` | `product` 表枚举列，取值 `SECRET` / `X509` / `JWT` |
| mTLS | 双向 TLS，客户端须提交由服务端信任的 CA 签发的证书 |
| CA | 签发设备证书的自建证书颁发机构，含 CA 证书与 CA 私钥 |
| 吊销列表 | `device_certificate` 表中 `revoked_at` 非空的行集合 |
| JWT | JSON Web Token，设备令牌以 HS256 签名，`sub` 为设备用户名 |
| `topic_prefix` 模板 | 含 `{productKey}` / `{deviceKey}` 占位符的主题前缀串 |
| `peer_cert_as_username` | EMQX SSL 监听器选项，将证书字段映射为用户名，取值含 `cn` |
| 回调分派 | 认证回调依据产品 `auth_mode` 选择校验分支 |
| `is_superuser` | EMQX 认证响应字段，本平台恒为 `false` |

## 4. 认证与主题方案

### 4.1 单条 HTTP 认证器加后端分派

EMQX 只保留一条 HTTP 认证器，请求体在原有 `username` / `password` / `clientid` 之外补充 `${cert_subject}` 与 `${cert_common_name}`；三个模式的判定全部在 `EmqxAuthServiceImpl` 内完成。

为什么是单认证器加后端分派，而非 EMQX 多认证器链：EMQX 5.0 的认证链是监听器间共享的全局配置，多认证器的求值顺序与 `ignore` 落空规则不易与「按产品分派」这一业务语义对齐；同一条链路内还必须避免同类型认证器重复。把分派收敛到后端，产品维度的判定与其他业务查询天然同源，也不必为新增模式反复调整 EMQX 配置。

- **代价**：认证回调的请求体与分支判断都集中在后端，回调耗时略高于纯本地机制；需保证回调在 EMQX 的认证超时内返回。

### 4.2 X.509 走 mTLS 监听器

新增 8883 SSL 监听器，配置 `cacertfile` 指向暂停自建 CA 证书，`verify` 取 `verify_peer`，并取 `peer_cert_as_username` 为 `cn`。`fail_if_no_peer_cert` 固定为 `false`：`verify_peer` 已使 EMQX 向客户端索证并填出 `${cert_subject}` / `${cert_common_name}`，但若同时置为 `true`，不带证书的 SECRET / JWT 设备将无法在同一 8883 监听器上完成握手，故保持 `false` 让三类设备共用该端口，X.509 分支所需的证书缺失交由后端在认证回调内拒绝。设备证书的 CN 直接写为 `{productKey}.{deviceKey}`，与既有用户名规则一致。

为什么走 mTLS 而非在口令位比对证书指纹：EMQX 5.0.26 的 HTTP 认证器不提供证书 PEM 或指纹占位符，只有 `cert_subject` 与 `cert_common_name` 两个派生字段，指纹比对本就无法在回调内完成；mTLS 让证书有效性由 TLS 层先判定，回调只做归属与吊销核对，职责更清晰。

- **代价**：需新增监听端口与证书文件卷，存量设备若不支持 TLS 需停留在 1883；证书有效期与轮换成为运维项。

### 4.3 证书吊销以吊销表加后端拒入

新增 `device_certificate` 表记录签发与吊销，认证回调在 X.509 分支内查询该设备的吊销状态，命中即拒。

为什么用吊销表而非 EMQX 原生 CRL：EMQX 5.0.26 的 SSL 监听器选项中没有 `crl_check` 与 `crl_file`，无法在 TLS 层执行 CRL 校验；改由后端拒入，与既有的准入判定同源，且吊销即时生效，无需等待监听器重载。

- **代价**：已握手完成的连接不会因吊销被立即断开，需搭配短有效期与主动踢线；吊销列表的查询进入认证热路径，须走缓存。

### 4.4 JWT 复用 MQTT 口令位

设备以 JWT 作为 MQTT 口令，用户名仍为 `{productKey}.{deviceKey}`，回调在 JWT 分支内校验签名、有效期与 `sub` 归属。

为什么复用口令位而非自定义 MQTT 属性：EMQX 认证器可读取的字段以用户名、口令、客户端 ID 与网络地址为主，自定义属性不进入认证回调；复用口令位无需改动客户端连接形状，现有 MQTT 客户端库即可承载。设备 JWT 另立签名密钥，绝不与控制台登录的 `app.jwt.secret` 共用，二者受众与有效期语义完全不同。

- **代价**：口令位承载的字符串明显长于 32 位密钥，需确认客户端缓冲与抓包日志的口令脱敏。

### 4.5 主题前缀模板变量化

`topic_prefix` 支持 `{productKey}` 与 `{deviceKey}` 两个占位符，解析分两处：授权回调以具体设备键代入，共享订阅以 `+` 代入设备占位符并遍历产品。

为什么做成模板而非固定两段式：既有默认值 `device/{deviceKey}` 已隐含设备段，若把前缀写死为不含设备层的固定串，会与已上线设备的主题结构冲突；模板在保留默认值语义的同时允许产品自定义层级，且订阅侧只需把设备占位符替换为通配即可生成共享订阅。

- **代价**：模板一旦放宽，非法占位符与超长前缀需要在写入时拦截；订阅需按产品逐个生成，产品数量增长时订阅条目线性增加。

### 4.6 认证模式变更即失效缓存

产品 `auth_mode` 或 `topic_prefix` 变更时，调用 `evictProduct` 清空该产品下全部设备的 `AuthMeta` 缓存。

为什么不做 TTL 自然过期：认证缓存默认 TTL 为 60 秒，若等待过期，切换窗口内新旧模式并存，可能出现「已切 X.509 但设备仍以口令接入」的越权窗口；`ProductServiceImpl` 在改产品键与停用产品时已有显式清缓存的先例，模式变更沿用同一处理。

- **代价**：一次产品更新会让该产品所有设备在下次认证时回源数据库，形成一次短时查询尖峰。

## 5. 载荷与响应

### 5.1 认证回调请求扩展

`POST /internal/emqx/auth` 的请求体在既有三字段后追加两个可空字段，EMQX 侧以占位符填充：

```json
{
  "clientid": "device-001",
  "username": "prod-abc.dev-001",
  "password": "eyJhbGciOiJIUzI1NiJ9...",
  "cert_subject": "CN=prod-abc.dev-001,O=MQTT Cloud",
  "cert_common_name": "prod-abc.dev-001"
}
```

`cert_subject` 与 `cert_common_name` 在非 TLS 连接下为空串，字段保持可空，不影响既有 `SECRET` 通路。

### 5.2 证书签发请求

`POST /api/devices/{deviceId}/certificate` 无请求体，改为读取路径参数与当前登录主体；响应返回一次性明文私钥与证书链：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "deviceId": 1024,
    "subject": "CN=prod-abc.dev-001,O=MQTT Cloud",
    "serial": "4A7F1C90E2B3D451",
    "notBefore": "2026-10-05T10:00:00",
    "notAfter": "2027-10-05T10:00:00",
    "certificatePem": "-----BEGIN CERTIFICATE-----\n...",
    "privateKeyPem": "-----BEGIN PRIVATE KEY-----\n..."
  }
}
```

`privateKeyPem` 在库中不留存，仅签发响应返回一次。

### 5.3 JWT 签发请求

`POST /api/devices/{deviceId}/token` 无请求体，响应返回令牌与过期时刻：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "deviceId": 1024,
    "username": "prod-abc.dev-001",
    "token": "eyJhbGciOiJIUzI1NiJ9...",
    "expiresAt": "2026-10-05T11:00:00"
  }
}
```

### 5.4 吊销请求与响应

`POST /api/devices/{deviceId}/certificate/revoke` 接受可选原因，返回吊销结果：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "deviceId": 1024,
    "serial": "4A7F1C90E2B3D451",
    "revokedAt": "2026-10-05T12:30:00",
    "reason": "device_decommissioned"
  }
}
```

### 5.5 回调响应

认证与授权回调的响应形状保持不变，认证成功返回 `result=allow` 与 `is_superuser=false`，失败返回 `result=deny`；三种模式共用同一响应，不因模式不同而分叉。

## 6. 数据模型

新增一张表记录证书生命周期，其余改动均为既有列的语义启用，不新增列。

```sql
CREATE TABLE device_certificate (
    id              BIGINT AUTO_INCREMENT PRIMARY KEY,
    device_id       BIGINT       NOT NULL,
    product_key     VARCHAR(64)  NOT NULL,
    device_key      VARCHAR(64)  NOT NULL,
    serial          VARCHAR(64)  NOT NULL,
    subject         VARCHAR(256) NOT NULL,
    issued_at       DATETIME     NOT NULL,
    not_after       DATETIME     NOT NULL,
    revoked_at      DATETIME     NULL,
    revoke_reason   VARCHAR(64)  NULL,
    created_at      DATETIME     NOT NULL,
    CONSTRAINT uk_device_cert_serial UNIQUE (serial)
);
```

迁移文件命名沿用现有序列，为 `V13__device_certificate.sql`。`serial` 唯一约束保证同一证书不会被重复记录；`device_id` 建普通索引以支撑「按设备查吊销状态」。已吊销行保留而非删除，便于审计追溯。

`product.auth_mode` 与 `product.topic_prefix` 均由 T-11 建列，本期只改变其读写行为：`auth_mode` 由固定写入改为读取请求值，`topic_prefix` 由固定值改为模板解析。存量 `product` 行的 `auth_mode` 均为 `SECRET`，默认主题模板 `device/{deviceKey}` 与既有硬编码前缀等价，迁移安全。

## 7. 参数校验

| 字段 | 位置 | 规则 |
| --- | --- | --- |
| `authMode` | `ProductRequest` | 可空；非空时须为 `SECRET` / `X509` / `JWT` 之一，否则抛 `AUTH_MODE_UNSUPPORTED` |
| `topicPrefix` | `ProductRequest` | 可空；非空时须匹配占位符白名单，未知占位符或非法字符抛 `TOPIC_PREFIX_TEMPLATE_INVALID` |
| `deviceId` | 路径参数 | 必填；设备不存在时抛既有 `DEVICE_NOT_FOUND` |
| `reason` | 吊销请求体 | 可空；非空时长度不超过 64 |
| 回调证书字段 | `AuthRequest` | 可空；X.509 分支下为空即拒 |

`authMode` 的取值集合以枚举常量维护，避免在校验注解内硬编码字符串；`topicPrefix` 的占位符白名单为 `{productKey}` 与 `{deviceKey}`，解析时若出现未闭合花括号或未知名字即拒。

> 认证失败在回调侧统一返回 `deny`，不向 EMQX 暴露具体失败原因；产品级参数错误才经由 `ResultCode` 返回给控制台。

## 8. 处理流程

### 8.1 认证分派

`EmqxAuthService.authenticate` 的签名扩展为承载证书字段，实现内先按用户名解析出 `productKey` 与 `deviceKey`，再取产品 `auth_mode` 分派：

```java
boolean authenticate(String username, String password, String clientId,
                     String certSubject, String certCommonName);
```

分派逻辑：

- `SECRET`：走既有分支，`deviceSecretService.matches(password, meta.secretHash())`。
- `X509`：要求 `certCommonName` 非空且等于用户名，且该设备在吊销表中无有效吊销记录。
- `JWT`：以设备 JWT 密钥验签 `password`，校验未过期且 `sub` 等于用户名。

三个分支共用前置的准入判定，即 `DeviceAccessGuard.resolve` 与 `isPermitted`，保证「认证拒绝、授权放行」不会出现语义分叉。

### 8.2 证书签发

签发流程为：校验设备存在且其产品 `auth_mode` 为 `X509`；以 CA 证书与 CA 私钥签发 CN 为 `{productKey}.{deviceKey}` 的证书；生成随机序列号；私钥仅随响应返回；将 `serial` / `subject` / `not_after` 落库。同一设备重复签发表明重新签发，旧证书不自动吊销，由运维按需显式吊销。

### 8.3 证书吊销

吊销流程为：按 `deviceId` 定位当前有效证书行，写入 `revoked_at` 与 `revoke_reason`；随后清空该设备认证缓存，使下一次回调立即读吊销态。若设备无有效证书行，抛 `DEVICE_CERTIFICATE_REVOKE_FAILED`。

### 8.4 主题前缀解析

授权回调内，`AclEvaluator` 以 `productKey` 与 `deviceKey` 解析 `topic_prefix` 模板得到具体前缀，再以该前缀替代既有的 `TOPIC_ROOT + deviceKey + "/"` 判定归属；publish 与 subscribe 的 `cmd/` 例外规则保持原语义。

共享订阅侧，`MqttMessageHandler.subscribe` 遍历启用产品，将各产品模板中的 `{productKey}` 代入产品键、`{deviceKey}` 代入 `+`，对每个产品生成 `data` / `heartbeat` / `lwt` / `reply` / `ota` 五条共享订阅。默认模板下生成结果与既有 `device/+/...` 完全一致。

### 8.5 缓存与失效

`AuthMeta` 扩展 `authMode` 与 `topicPrefix` 两个字段，`DeviceAccessGuard.loadFromDb` 在构造时一并填充。产品更新命中 `auth_mode` 或 `topic_prefix` 变化时调用 `evictProduct`；产品停用与产品键变更沿用既有清缓存路径。缓存命中时不再回源，模式与模板均以缓存快照为准。

### 10.2 错误码

| 6249 | `AUTH_MODE_UNSUPPORTED` | 认证模式取值非法 | 400 |

## 11. 前端与文档站

控制台产品表单新增认证模式选择，三选项与后端枚举一一对应，选择 `X509` 或 `JWT` 时给出存量设备需刷机的提示。设备详情页新增证书与令牌操作区，签发后私钥以一次性弹层展示并提示不再回显，吊销操作二次确认。

文档站在接入章节区分三种模式的连接参数：`SECRET` 展示用户名与密钥，`X509` 展示证书与 CA 获取方式及 mTLS 端口，`JWT` 展示令牌请求与续期流程。ESP32 接入手册补充证书烧录与令牌刷新的段落。

## 12. 配置项

紧随 `app.http-ingest` 之后、`logging` 之前新增认证扩展配置段：

```yaml
  auth-extension:
    x509:
      enabled: ${AUTH_X509_ENABLED:false}
      ca-cert-path: ${AUTH_X509_CA_CERT:}
      ca-key-path: ${AUTH_X509_CA_KEY:}
      validity-days: ${AUTH_X509_VALIDITY_DAYS:365}
    jwt:
      enabled: ${AUTH_JWT_ENABLED:false}
      secret: ${AUTH_JWT_SECRET:}
      ttl-seconds: ${AUTH_JWT_TTL_SECONDS:3600}
```

对应属性类 `AuthExtensionProperties`，前缀 `app.auth-extension`，含两个静态内部类承载 `x509` 与 `jwt` 分组。

三处需注意：`secret` 与既有 `app.jwt.secret` 是不同用途的密钥，命名上以分组区分；`ca-key-path` 指向的私钥文件权限须限制为服务进程可读；`enabled` 为假时，对应模式的签发端点返回禁用错误，认证回调对处于该模式的产品一律拒。

## 13. 安全与边界

CA 私钥是整条信任链的根，仅在签发时读取，不入库、不落日志、不经接口下发。签发的设备私钥同样只随响应返回一次，服务端不留副本，丢失即重签。

认证回调对三种模式统一返回 `deny` 而不泄露细节，防止借错误差异探测某个用户名是否存在。JWT 与证书均校验主体归属，`sub` 与 CN 必须等于 `{productKey}.{deviceKey}`，避免持有一张合法证书即接入任意设备。

主题模板写入时做白名单校验，解析时对未闭合占位符直接拒，防止模板注入导致前缀越界。吊销与模式切换均即时清缓存，把越权窗口收敛到「清缓存到设备重连」这一最短区间。

## 14. 测试与验收

### 14.1 单元测试

| 用例 | 断言 |
| --- | --- |
| `SECRET` 分支 | 正确口令放行，错误口令拒绝，行为与改造前一致 |
| `X509` 分支 | CN 归属正确且未吊销放行，CN 不符或已吊销拒绝 |
| `JWT` 分支 | 有效令牌放行，过期、篡改签名、`sub` 不符拒绝 |
| 模式分派 | 产品分别置为三种模式时，仅对应分支生效 |
| 模板解析 | 默认模板与既有前缀等价，含未知占位符抛对应错误码 |
| 订阅生成 | 默认模板生成的共享订阅与既有 `device/+/...` 逐条一致 |
| 缓存失效 | 产品 `auth_mode` 变更后，该产品设备缓存被清空 |
