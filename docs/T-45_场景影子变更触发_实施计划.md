# T-45 场景影子变更触发 实施计划

> 版本：v1.0　创建日期：2026-10-21　状态：已交付
> 目标：补齐 G-12-4 的剩余部分，让场景可由设备影子的 **reported / desired** 属性变化触发，并避免自动化内部写入导致自触发循环。

---

## 1. 背景与范围

T-43 已让场景支持设备上下线触发，但影子的 `reported` / `desired` 变化仍不能直接驱动场景。典型需求：

- 设备上报属性变化（reported）→ 触发场景；
- 控制台 / 开放 API / 上位机写入期望值（desired）→ 触发场景（例如写入 desired 后通知运维）。

本任务交付：

- 新触发源 `SHADOW`，支持变更侧 `REPORTED` / `DESIRED` / `ANY` 与可选属性标识符；
- 影子 CAS 成功后发布 `DeviceShadowChangedEvent`（只含实际变化的属性）；
- `desired` 变更按命令来源过滤：仅 `CONSOLE` / `OPEN_API` / 直接调用触发，`SCENE` / `RULE` / `OTA` / `POINT_TABLE` 等内部自动化跳过；
- 前端表单 / 画布 / 试运行与列表文案；
- `V24` 新增 `scene_definition.trigger_shadow_side`。

不在本任务范围：影子版本冲突错误码、事件重放、按变更前后值的完整审计、影子变更开放 API。

---

## 2. 触发语义

| 字段 | 说明 |
|---|---|
| `triggerType=SHADOW` | 影子变更触发 |
| `triggerShadowSide` | `REPORTED` / `DESIRED` / `ANY`，缺省 `REPORTED` |
| `triggerIdentifier` | 可选属性标识符；为空表示任意属性 |
| `triggerDeviceId` | 可选作用域；为空表示账号下任意设备 |

- 只有影子版本 CAS **成功**且目标侧属性值**确有变化**时才发布事件；
- `reported` 由摄取链路在属性 `upsertIfNewer` 后回读权威值合并，天然继承乱序守卫；
- `desired` 由命令 / 影子写入链路合并；内部自动化来源不触发场景；
- 同一批多个属性变化合并为一个事件，`changes` 只含变化键；
- 触发上下文：`triggerIdentifier` 为配置标识符或首个变化键，`triggerValue` 为 `k=v, ...` 摘要，`triggerEventType` 为 `reported` / `desired`；
- 冷却窗口、条件组、步骤流、执行记录复用既有场景引擎。

## 3. 后端实现

### 3.1 模型与校验

- `ShadowChangeSide`：`REPORTED` / `DESIRED` / `ANY` 常量与集合；
- `SceneConstants.TRIGGER_SHADOW` 加入触发源集合；
- `SceneRequest` / `SceneDefinition` 新增 `triggerShadowSide`；
- `SceneValidator`：
  - `SHADOW` 只允许可选 `triggerDeviceId` / `triggerIdentifier` 与 `triggerShadowSide`；
  - 拒绝比较符 / 阈值 / 事件类型 / cron；
  - `triggerShadowSide` 缺省 `REPORTED`，非法值 `6241`；
  - 非 `SHADOW` 源携带 `triggerShadowSide` 一律拒绝；
  - 条件组与步骤校验沿用既有口径。
- `SceneMatcher.matchesShadowTrigger`：作用域 → 变更侧（空 / `ANY` 不限）→ 属性标识符（空不限）。

### 3.2 影子事件

- `DeviceShadowChangedEvent(deviceId, side, changes, version, source, occurredAt)`；
- `DeviceShadowServiceImpl.merge` 在每次 CAS 尝试前快照目标侧，成功后 `diff` 出变化键；CAS 重试耗尽不发布；
- `applyReported` 来源固定 `INGEST`；
- `applyDesired(deviceId, desired, source)` 保存来源；旧 2 参方法委托为 `source=null`；
- `DeviceCommandServiceImpl` 把 `command.source()` 传入 `applyDesired`；
- 事件发布失败只记 WARN，不影响影子写入。

### 3.3 场景评估

- `SceneEvaluationService.onShadow(...)` 加载设备与启用场景，逐场景匹配后复用 `fire()`；
- `@Transactional(REQUIRES_NEW)`：`AFTER_COMMIT` 回调中开独立事务；
- desired 内部来源在监听器入口直接跳过，避免为无效事件打开事务；
- 评估方法内部再次兜底过滤，异常只记 WARN。

### 3.4 试运行

`SceneTestServiceImpl`：

- SHADOW 需 `deviceId`；`value` 作为变更侧（缺省按场景侧，`ANY` 试运行取 `REPORTED`）；
- `identifier` 可空；为空时使用场景配置标识符或任意键占位；
- 非法变更侧 `6241`。

## 8. 关键决策与已知限制

1. **只发布「实际变化」**：值未变、CAS 失败不发布，避免重复触发；代价是 CAS 重试耗尽的事件会丢失（影子本身也放弃本次合并）。
2. **desired 内部来源过滤**：防止「场景写 desired → 影子触发同一场景」的自触发循环；也意味着自动化内部写入不会触发影子场景。
3. **变化摘要而非完整快照**：`triggerValue` 只保留 `k=v, ...` 文本，便于排障，不承载完整前后值。
4. **复用场景执行模型**：SHADOW 只新增触发评估入口，步骤流 / 冷却 / 重试 / 循环不做特殊处理。
5. **事件在写入线程同步发布**：reported 在摄取线程、desired 在命令事务提交后；评估异常全量隔离，不影响影子写入。
