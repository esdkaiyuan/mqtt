> 上位文档：`docs/平台功能链路路线图.md`（L13）　前置链路：L12 / T-25 认证方式扩展

## 1. 背景与目标

路线图能力域 14 在 T-25 之后仍余一项差距 ——「缺子设备（网关代连）认证」。现状是设备表 `device` 没有父子关系列，一台设备只能表示一个直连身份；真实项目里常见的形态是「一台带通信能力的网关下面挂若干不具备联网能力的子设备（传感器、执行器、表计）」，子设备自己既不连 Broker、也不该在平台上被当成孤立的一等设备。

T-24 曾就 Modbus / 边缘网关给出「平台侧不建拓扑、由边缘侧转换后统一上报」的评估结论，该结论的适用面是**协议转换**（把 Modbus 等工业协议翻译成 MQTT / HTTP）—— 这类转换发生在边缘，平台无需知道寄存器地址。本鏈路要解决的是另一件事：**接入身份与授权**。当网关代表子设备收发报文时，平台必须回答「这个网关是否有权收发这台子设备的数据」，这个判断只能由平台持有拓扑才能做出。

本鏈路目标：在既有设备体系上补齐父子拓扑与网关代连授权，使一台网关可以在**自己的连接**上代表其子设备完成上下行，且不破坏现有摄取、命令、影子、告警、场景、OTA 全部链路。

## 2. 范围

### 2.1 在范围内

- `device` 表新增拓扑列（自引用父键 + 拓扑角色），迁移 `V14__device_topology.sql`。
- 网关与子设备的挂载 / 解绑 / 查询端点，含同产品、层级、数量三项校验。
- `AclEvaluator` 增加委托分支：网关账号可收发其子设备主题前缀内的报文。
- 认证元数据 `AuthMeta` 携带拓扑角色，供授权判定读取。
- 设备列表与详情的前端拓扑呈现（节点类型筛选、子设备区块、父网关选择）。
- 错误码 `6254`~`6260`、`app.device-topology` 配置组、单元测试与验收项。

### 2.2 不在范围内

| 事项 | 归属 |
|------|------|
| 平台侧 Modbus / 工业协议驱动 | 维持 T-24 结论：边缘侧转换，平台不建协议拓扑 |
| 子设备物模型继承与云端属性映射 | 若确有必要，另立任务；本期子设备各自按所属产品物模型解析 |
| 多级拓扑（网关挂网关） | 本期限定两层，深度上限由配置控制，超出即拒 |
| 子设备本地扫码入网 / 动态注册 | 依赖设备端协议扩展，本期仅提供平台侧显式挂载 |
| 嵌套主题（`device/{gw}/sub/{sub}/...`）下的寻址改造 | 本期不采用，理由见 §4.1 |

## 3. 术语表

| 术语 | 含义 |
|------|------|
| 节点类型 `node_type` | 设备的拓扑角色，取值 `DIRECT`（普通直连）、`GATEWAY`（网关）、`SUB`（子设备） |
| 父网关 `parent_id` | 子设备指向所属网关的 `device.id`，仅 `node_type=SUB` 时非空 |
| 代连 | 网关以自身凭据建立唯一连接，代表其子设备发布 / 订阅子设备主题 |
| 委托授权 | 授权回调在判定网关账号时，额外放行其子设备前缀的规则 |
| 归属前缀 | 由产品 `topic_prefix` 模板代入具体设备键解析得到的设备命名空间 |
| 拓扑深度 | 从根设备到叶设备的层数，本期上限 2（网关 → 子设备） |

## 4. 拓扑与代理方案

### 4.1 嵌套主题方案的取舍

子设备接入有两种主流主题形态。一种是嵌套式，如 `device/{gwKey}/sub/{subKey}/data`，网关是唯一被认证的实体，子设备身份编码在主题里；另一种是扁平式，子设备与直连设备共用 `device/{deviceKey}/{messageType}`，凭父键区分归属。

嵌套式的代价集中在既有代码的**主题解析契约**上。`MqttMessageHandler.messageArrived` 内 `String[] parts = topic.split("/")` 后固定取 `parts[1]` 为设备键、`parts[2]` 为消息类型，`parts.length < 3` 即丢弃；`MqttMessageHandler.subscribe` 用产品模板把设备位代成 `+` 生成共享订阅；`IngestPipeline.routeIndex` 按记录里的设备键哈希分片；`AclEvaluator.prefixMatches` 按段比较前缀。改为嵌套式，这四处都要改：解析要按层级取键、订阅过滤器要变成 `device/+/sub/+/data`（层级固定则模板变量语义被破坏）、分片键要改为子设备键（否则同一网关下全部子设备挤在同一 worker）、前缀比较要允许额外的一层。

扁平式的收益是上述四处**一行不改**。子设备在主题层面与直连设备完全同形，共享订阅 `device/+/data` 天然覆盖，分片天然按子设备键分散，命令下行 `device/{subKey}/cmd/down` 天然可寻址。代价是授权层要多一条判断：网关账号访问别人的前缀时，凭什么放行。这条判断需要平台持有拓扑 —— 正是本鏈路要补的数据模型。

据此选定扁平式，主题形状不变，新增面收敛为「拓扑数据 + 委托授权」两块。

### 4.2 代连下的主题形状

子设备沿用与直连设备相同的五类上行主题与一条下行主题，设备位填子设备键：

| 方向 | 主题 | 说明 |
|------|------|------|
| 上行 | `device/{subKey}/data` | 属性与数据上报 |
| 上行 | `device/{subKey}/heartbeat` | 心跳 |
| 上行 | `device/{subKey}/lwt` | 遗嘱离线 |
| 上行 | `device/{subKey}/reply` | 命令回执 |
| 上行 | `device/{subKey}/ota` | 升级进度 |
| 下行 | `device/{subKey}/cmd/down` | 命令下发 |

产品自定义 `topic_prefix` 模板同样生效：网关与其子设备同属一个产品（§7 强制），故子设备主题与网关主题共用同一模板形状，平台共享订阅与平台发布命名空间自动覆盖，无需额外订阅。

### 4.3 委托授权

授权回调 `POST /api/internal/emqx/acl` 收到的用户名是网关的 `{productKey}.{gatewayKey}`，但主题里的设备位是子设备键。判定分两步：

1. 按用户名解析出网关身份，走既有 `DeviceAccessGuard.resolve` + `isPermitted`，产品停用或网关禁用一律拒；
2. 主题设备位与网关键不一致时，查该设备是否为**当前网关的子设备**且同产品、未删除、未禁用；成立则按网关自己的 `cmd/` 例外语义放行（发布禁 `cmd/`、订阅仅 `cmd/`）。

解绑或删除子设备后委托立即失效（判定每次回源拓扑缓存，见 §5.4）。子设备自身的直连身份若同时存在，仍走原有自身前缀分支，两条分支互不影响。

### 4.4 父子拓扑数据模型

复用 T-18 `device_group` 已验证的自引用写法，在 `device` 表增加两列：`parent_id BIGINT NULL` 与 `node_type VARCHAR(16) NOT NULL DEFAULT 'DIRECT'`。约束在应用层强制（同产品、父为网关、深度不超限、子设备不得再有子设备），库层只保证引用完整性：外键 `ON DELETE SET NULL`，父设备被删除时子设备自动回退为「无父」的孤儿子设备，由运维重新挂载，不产生级联删除。

不新增独立拓扑表。理由是拓扑关系是一对多的树、单列即可表达，独立表会引入与 `device` 的一致性维护成本（同产品校验、删除联动、缓存失效），收益不足。

### 4.5 深度与数量边界

深度上限默认 2（网关 → 子设备一层）。设为可配置而非硬编码，是因为判断「要不要放开多级」需要真实的现场形态支撑，而不是设计期假设；本期默认下，子设备不得已有下级、且 `maxDepth` 需 ≥ 2，违反即返 `6257`。

单网关子设备数上限默认 200，用于防止一次拓扑查询拉回过大集合、也防止单网关成为整批下发的长尾。超限返 `6260`。两个上限都放在 `app.device-topology` 配置组，与 T-18 分组深度的处理方式保持一致。

### 4.6 状态与故障域

子设备的在线状态由其自身 `heartbeat` / `lwt` 驱动，与直连设备同源，不做「网关在线即子设备在线」的推导 —— 推导会在网关侧子设备掉线但网关仍心跳时给出错误状态。网关禁用或删除时，其子设备因委托失效而无法收发，但 `device` 行与历史数据保留；网关重新启用后委托自动恢复，无需重新挂载。

## 5. 认证与授权

### 5.1 网关认证

网关按所属产品的 `auth_mode` 走既有三种方式之一（`SECRET` / `X.509` / `JWT`），`EmqxAuthController` → `EmqxAuthServiceImpl.authenticate` 一行不改。网关的凭据签发、重置、证书签发与吊销全部复用 T-11 / T-25 既有端点。

### 5.2 子设备直连兼容

子设备仍可像普通设备一样签发凭据并直连（认证回调按子设备自身 `deviceKey` 解析，链路不改）。代连与直连并非互斥模式：是否用网关代连由设备端行为决定，平台侧只负责两种路径都能授权。这样设计避免了在认证回调里增加「子设备禁止直连」这类拒绝分支，减少一格语义分叉。

### 5.3 授权判定改造

`AclEvaluator.allowDevice` 现签名 `(productKey, deviceKey, topicPrefix, action, topic)`。改造为在主题不在自身前缀内时进入委托判定：

```
allowDevice(productKey, deviceKey, topicPrefix, action, topic):
    ownPrefix = resolver.resolve(topicPrefix, productKey, deviceKey)
    if topic.startsWith(ownPrefix):                 # 自身命名空间，语义不变
        return publish ? !topic.startsWith(ownPrefix + "cmd/")
                       : subscribe && topic.startsWith(ownPrefix + "cmd/")
    return allowDelegated(productKey, deviceKey, topicPrefix, action, topic)
```

`allowDelegated` 从主题解析出目标设备键，查拓扑（缓存优先）得到其父网关键；父网关键等于当前 `deviceKey` 时，按委托语义放行。目标设备键的解析取主题首段之后、消息类型之前的部分，与 `MqttMessageHandler` 的取法保持同源 —— 若产品模板为多段（如 `device/{productKey}/{deviceKey}`），目标键位由模板反解得到，避免写死下标。

平台分支 `allowPlatform` 与前端只读分支不改：平台共享订阅按产品模板生成，子设备主题落在同一模板命名空间内，本就被覆盖。

### 5.4 缓存与失效

授权判定要求每次都能读到最新拓扑。`DeviceAuthCacheService` 现有缓存键为 `(productKey, deviceKey)`，本鏈路将 `AuthMeta` 扩展两个字段：`nodeType` 与 `parentId`（内存载体，非库列）。拓扑变更（挂载 / 解绑 / 删除 / 角色变更）时主动失效**双方**的缓存项 —— 子设备的、网关的（网关若同时被解绑最后一个子设备，其 `nodeType` 可回落 `DIRECT`，由角色收敛规则决定，见 §8.2）。

目标设备键 → 父网关键的查询同样走缓存，键为子设备的 `(productKey, deviceKey)`，复用同一份 `AuthMeta`，不新增缓存组件。

## 6. 数据模型

迁移 `V14__device_topology.sql`，只加列与索引、不改既有列，应用版本可安全回滚（回滚后新列留存，旧代码忽略）。

```sql
-- ============================================================
-- V14：设备拓扑（T-26 子设备与网关代理接入）
-- 用途：
--   1) device.node_type  拓扑角色：DIRECT / GATEWAY / SUB
--   2) device.parent_id  子设备指向所属网关（自引用）
-- 说明：只加列与索引，不改既有列，应用版本可安全回滚。
--       存量设备 node_type 一律为 DIRECT、parent_id 一律为 NULL，
--       与既有「全部为直连设备」语义等价，迁移安全。
--       深度上限（默认 2）与单网关子设备数上限（默认 200）在应用层校验，
--       库层只保证引用完整性：父设备删除时子设备 parent_id 置 NULL，
--       子设备回退为无父状态，不做级联删除。
-- ============================================================

ALTER TABLE device ADD COLUMN node_type VARCHAR(16) NOT NULL DEFAULT 'DIRECT' COMMENT '拓扑角色：DIRECT=普通设备，GATEWAY=网关，SUB=子设备';
ALTER TABLE device ADD COLUMN parent_id BIGINT NULL COMMENT '父网关设备（device.id），仅 node_type=SUB 时非空';
CREATE INDEX idx_device_parent ON device (parent_id, deleted);
ALTER TABLE device ADD CONSTRAINT fk_device_parent FOREIGN KEY (parent_id) REFERENCES device(id) ON DELETE SET NULL;
```

| 列 | 类型 | 语义 |
|----|------|------|
| `node_type` | `VARCHAR(16) NOT NULL DEFAULT 'DIRECT'` | 拓扑角色，取值 `DIRECT` / `GATEWAY` / `SUB` |
| `parent_id` | `BIGINT NULL` | 父网关 `device.id`，`SUB` 非空，其余为 `NULL` |

索引 `idx_device_parent (parent_id, deleted)` 支撑「按网关列子设备」与「按子设备查归属」两条热路径。唯一键 `uk_product_device (product_id, device_key)` 不变 —— 子设备键在同一产品内天然唯一，无需为子设备另建约束。

## 7. 参数校验

挂载与建子设备时逐项校验，任一不成立即拒并返回对应错误码。

| 校验 | 规则 | 错误码 |
|------|------|--------|
| 父设备存在且未删除 | 按 `parentId` 查 `device` | `6255` |
| 父非子设备 | `node_type ≠ 'SUB'`；`DIRECT` 允许，首次挂载自动提升为 `GATEWAY`（§8.2） | `6256` |
| 同产品 | `parent.product_id = child.product_id` | `6258` |
| 深度不超限 | 子设备不得已有子设备，且 `maxDepth ≥ 2` | `6257` |
| 数量不超限 | 该网关已有子设备数 `< maxSubDevicesPerGateway` | `6260` |
| 自身不可为父 | `childId ≠ parentId` | `6254` |
| 非自环 | 挂载后不构成环（本期两层下退化为上一条） | `6254` |

解绑、删除、角色变更共用同一批前置校验：网关下仍有子设备时，删除网关或把网关改为非网关返 `6259`。

## 8. 处理流程

### 8.1 创建子设备

两条入口。一是「先建设备再挂载」，走既有 `POST /devices` 再调挂载端点，兼容存量批量导入流程；二是 `POST /devices/{gatewayId}/sub-devices` 一步建成并挂载，服务端在同一事务内建设备行（`node_type=SUB`、`parent_id=网关 id`、`product_id=网关产品`）并写凭据。两条入口服务端校验一致，最终都收敛到同一挂载方法，避免两条写路径。

### 8.2 挂载与解绑

挂载：校验通过后更新子设备 `node_type='SUB'`、`parent_id=网关 id`，随后失效子设备与网关两侧缓存。网关若当前 `node_type='DIRECT'`，挂载时一并提升为 `GATEWAY`（首次挂载自动收敛角色，避免要求调用方先手工改角色）。

解绑：`parent_id` 置 `NULL`、`node_type` 回落 `DIRECT`，失效两侧缓存。网关失去最后一个子设备后，其角色**保持** `GATEWAY` 不变 —— 角色代表「具备网关能力」，不应因当下无子设备而回退，否则同一台设备会随业务波动反复变角色，前端筛选与授权缓存都不稳定。

### 8.3 上行代连

网关在自己的连接上向 `device/{subKey}/data` 等主题发布。EMQX 授权回调收到 `username={pk}.{gwKey}`、`topic=device/{subKey}/data`、`action=publish`，`AclEvaluator` 判定网关自身前缀不含该主题，转委托判定命中子设备归属，放行。消息进入 `IngestPipeline` 后，记录里的设备键即子设备键，`routeIndex` 按子设备键分片，`IngestPersistenceService` 解析到子设备行，后续物模型解析、影子、告警、规则、场景、属性历史全部按子设备落地，无一条旁路需要为「子设备」特判。

### 8.4 下行命令

平台按子设备键发布 `device/{subKey}/cmd/down`，走 `allowPlatform` 放行。网关订阅 `device/{subKey}/cmd/down`（`action=subscribe`），`allowDelegated` 按「订阅仅 `cmd/` 前缀」放行。子设备回执经网关发布到 `device/{subKey}/reply`，命中委托发布的非 `cmd/` 分支。整条命令链路的记录、状态机、超时巡检、影子补发均按子设备身份工作，形如对直连设备操作。

### 8.5 网关删除与禁用

删除网关：若其下仍有子设备，返 `6259` 要求先解绑或迁移；无子设备时按既有删除流程执行，子设备不受影响（它们已无父）。若外部直接删除导致外键触发，`parent_id` 置 `NULL`，子设备回退为无父状态。

禁用网关：走既有 `disableDevice`，同时失效网关缓存。禁用后委托判定在 `isPermitted` 处即被拒，子设备收发随之中止；子设备行与历史数据不受影响，网关重新启用后恢复。

## 9. 交互边界

| 交互对象 | 边界 |
|----------|------|
| `MqttMessageHandler` | 不改。主题形状与设备键取法原样保留 |

## 10. 接口设计

### 10.1 端点

| 方法 | 路径 | 说明 |
|------|------|------|
| `POST` | `/api/devices/{gatewayId}/sub-devices` | 建子设备并挂载，返回含一次性明文凭据的创建结果 |
| `POST` | `/api/devices/{gatewayId}/sub-devices/{subDeviceId}` | 把既有设备挂到网关下 |
| `DELETE` | `/api/devices/{gatewayId}/sub-devices/{subDeviceId}` | 解绑，子设备回落为普通设备 |
| `GET` | `/api/devices/{gatewayId}/sub-devices` | 列该网关的子设备（分页） |
| `GET` | `/api/devices/{subDeviceId}/parent` | 查子设备的父网关 |
| `PUT` | `/api/devices/{deviceId}/node-type` | 变更拓扑角色（`DIRECT` ↔ `GATEWAY`，有子设备时不得降级） |

设备列表查询 `DeviceQueryDTO` 增加 `nodeType`、`parentId` 两个可选过滤项，`Device` 响应体增加 `nodeType` / `parentId` 两个字段。归属校验沿用既有规则：仅本人设备可操作，`ADMIN` 旁路。

### 10.2 错误码

|----|------|------|------|
| `6254` | `DEVICE_TOPOLOGY_INVALID` | 设备拓扑配置非法 | `400` |
| `6255` | `DEVICE_PARENT_NOT_FOUND` | 父网关设备不存在 | `404` |
| `6256` | `DEVICE_PARENT_KIND_INVALID` | 父设备不是网关，无法挂载子设备 | `400` |
| `6257` | `DEVICE_TOPOLOGY_DEPTH_EXCEEDED` | 设备拓扑层级超出上限 | `400` |

## 13. 安全与边界

委托授权扩大的是**网关账号**的收发范围，且范围严格限定在「该网关的、同产品的、未删除的」子设备前缀内，不构成跨租户越权：子设备归属校验与网关归属校验都落在同一 `owner_id` 语义下，跨用户的设备不可能建立父子关系（挂载端点按当前用户二次过滤）。子设备前缀的解析复用产品模板，模板非法时按既有兜底跳过该产品，不让单条脏数据使整条授权链路不可用。

网关被禁用时委托即时失效，避免「禁用网关但其子设备仍可收发」的旁路。拓扑缓存与既有认证缓存共用失效入口，不引入独立的失效时机。

不新增 MQTT 主题、不改 `emqx-init.sh`、不改摄取管线，故 T-25 已验收的三方式认证与模板 ACL 行为不受影响；`app.device-topology.enabled=false` 时全部改动退化为空操作，可作为现场回滚开关。

## 附：设计自审

1. **是否动到底层架构**：否。主题形状不变，摄取管线零改动，改动面为「两列 + 一条授权分支 + 一组拓扑端点」，符合「先补齐功能缺口，再动底层架构」。
2. **是否新增第二套写路径**：否。子设备仍是 `device` 行，凭据仍走 `DeviceCredentialService`，命令仍走 `DeviceCommandService`，订阅仍走产品模板。
3. **是否引入跨租户越权面**：否。父子关系建立受当前用户归属校验，委托范围限定在同产品、同用户的子设备前缀。
4. **回滚是否安全**：物理层只加列与索引，`enabled=false` 可停用全部新行为。
5. **遗留待定**：`node_type` 与既有 `device_type`（sensor / gateway / actuator）语义有重叠，本期把 `node_type` 定为拓扑判定的唯一依据，`device_type` 保持自由文本分类，未做二者同步；若后续现场反馈需要收敛，另立小任务。
