# MQTT 云平台 — 现状评估与重构方案

> 版本：v0.5（R1-8 完成：连接韧性与授权兜底收敛，附录 C 缺陷 4/5/6 已关闭）
> 日期：2026-09-29
> 范围：`MQTT自建站点` 主项目（Spring Boot 3.3 + Vue 3 + EMQX 5 + MySQL 8 + Redis 7）
> 目的：为「换底层架构、提升性能」提供事实依据与分阶段方案；决策确认后再拆解为 T-12 实施计划
> 方法：基于当前代码库静态调研，全部结论标注 `文件:行号` 证据；性能结论先做结构性推断，**R0 阶段已实测回填**（见附录 B），测量环境与实测暴露的环境缺陷见附录 C

## 0. 结论摘要

**结论一：性能天花板不在框架，在上行链路的执行模型。**
每条设备上行消息在 Paho 的**单个回调线程**内同步完成 5~6 次数据库往返，无批量、无异步、无背压；且 `messageArrived` 捕获异常后正常返回，Paho 随即 ACK —— 数据库写失败即**静默丢消息**。换框架（换 ORM、换 Web 容器）解决不了这个问题，改执行模型才能解决。

**结论二：当前系统无法水平扩展，根因是进程内状态。**
后端以单一 MQTT 客户端全量订阅 `device/+/data|heartbeat|lwt`（无 `$share` 共享订阅，`cleanSession=true`），SSE 订阅者存于进程内 `Map` 且无跨副本通道。多开一个副本的后果是：**重复落库 + 重复 Webhook + 一半用户收不到实时数据**。

**结论三：现在不建议拆微服务。**
后端主代码仅 **4508 行 / 101 个文件 / 10 个包**，领域边界清晰但体量小。微服务会先引入分布式事务、链路追踪、配置中心、服务发现四类新问题，收益远小于成本。建议走 **模块化单体 + 独立数据面**：先把「接入 → 缓冲 → 落库 → 推送」改成可水平扩展的形态，再按明确阈值拆出需要独立伸缩的组件。

**额外发现（此前文档未记录）**：`application-prod.yml` 是**死配置**——仓库内没有任何地方设置 `SPRING_PROFILES_ACTIVE`，Docker 部署实际运行在默认 profile 下，因此 `logging.level.com.mqtt.cloud=DEBUG`、`com.baomidou.mybatisplus=DEBUG` 与 `log-impl: StdOutImpl`（打印全部 SQL）在生产环境**全部生效**。

## 2. 问题清单

分级依据：**P0 = 直接限制性能或导致数据丢失/无法扩展；P1 = 显著增加成本或风险；P2 = 影响效率与可维护性。**

### P0-1 上行链路：单线程同步落库 + 失败静默丢消息

**现象**：`messageArrived` 在 Paho 单回调线程内顺序执行：设备查询 → 状态更新（含状态历史 INSERT）→ `message` INSERT → `history_record` INSERT → Webhook 查询 → 同步遍历 SSE 订阅者推送。整条链路同步、串行、无缓冲。

**证据**：
- `MqttMessageHandler.java:62-99`（全链路）、`:84`（写 message）、`:86`（写 history）、`:95`（同步推 SSE）
- `MessageServiceImpl.java:72-81`、`HistoryServiceImpl.java:29`
- `DeviceServiceImpl.java:151-175`（读-改-写 + 状态历史 INSERT）
- `application.yml:46`（`max-inflight: 100`）

**影响**：
1. 吞吐上限 = `1 / 单条消息的 DB 串行延迟`，与设备数无关，只与 DB 延迟有关；DB 抖动即打满 `maxInflight` 触发 Broker 背压。
2. `MqttMessageHandler.java:89-91` 捕获全部异常后**正常返回** → Paho 判定投递成功并 ACK → 该消息**永久丢失**，无重试、无死信、无补偿。这是可靠性问题，不只是性能问题。
3. `RealtimeStreamServiceImpl.publish` 为 `synchronized` 且在回调线程内执行（`RealtimeStreamServiceImpl.java:66`）→ **慢 SSE 客户端会阻塞 MQTT 消息接收**，实时通道反向拖累主链路。

### P0-2 无法水平扩展：进程内状态 + 全量订阅

**现象**：后端 MQTT 客户端订阅 `device/+/data`(QoS1)、`device/+/heartbeat`(QoS0)、`device/+/lwt`(QoS1)，未使用共享订阅；`cleanSession=true` 且无持久会话；SSE 订阅者存于进程内 `Map<Long, Subscriber>`；SSE 超时配置为 `0`（永不超时）。

**证据**：`MqttMessageHandler.java:54-58`、`MqttClientManager.java:139-140`、`RealtimeStreamServiceImpl.java:30`、`application.yml:45`、`application.yml:109`

**影响**：
1. 后端加副本 → 每个副本都收到**全量**消息 → 重复落库、重复 Webhook、重复推送。
2. 副本 A 的 `publish` 触达不到副本 B 上的 SSE 订阅者 → 用户随机收不到实时数据（且无告警）。
3. `cleanSession=true` + 无持久会话 → 后端重启窗口内的消息**不可恢复**（即使 QoS1 也无法补投）。
4. `stream-timeout-ms=0` 且无服务端心跳 → 客户端异常断开（无 TCP FIN）时 `onCompletion/onError` 不回调，emitter 永驻 Map → **内存泄漏**。
5. 同一 userId 新订阅会关闭旧 emitter（`RealtimeStreamServiceImpl.java:52-55`）→ 不支持多标签/多端同时在线。

### P0-3 设备认证热路径无缓存，BCrypt 每次连接计算

**现象**：每次设备连接触发 `/internal/emqx/auth`，执行 2 次数据库查询（product + device）与一次 BCrypt（strength=10）校验；全代码无 `@Cacheable`，Redis 仅用于 JWT 黑名单与 API Key 节流。

**证据**：`EmqxAuthServiceImpl`（authenticate 流程）、`ProductServiceImpl.java:98-101`、`DeviceServiceImpl.java:133`、`DeviceSecretServiceImpl.java:18`/`:39`；grep 确认无 `@Cacheable`

**影响**：认证延迟直接叠加到每次连接建立；设备批量重连（网络抖动、Broker 重启、固件重试）时 DB 与 CPU 同时承压。ACL 回调本身是纯字符串前缀匹配、0 次 DB（`AclEvaluator.java:22-64`），但**每条收发消息都会打一次 HTTP 回调**，是固定开销。

### P1-1 生产环境开启全量 SQL 日志，prod profile 是死配置

**现象**：`application.yml:69` 配置 `mybatis-plus.configuration.log-impl: StdOutImpl`（每条 SQL 打印到 stdout），`:114`/`:117` 将 `com.mqtt.cloud` 与 `com.baomidou.mybatisplus` 设为 `DEBUG`。`application-prod.yml` 虽将级别覆盖为 INFO/WARN，但**仓库内无任何地方设置 `SPRING_PROFILES_ACTIVE`**（compose、Dockerfile、deploy.sh 均无），故 prod profile 从未激活。

**证据**：`application.yml:69`、`:111-120`；`application-prod.yml:18-21`；`docker/docker-compose.yml`、`docker/Dockerfile.backend`、`scripts/deploy.sh`（grep 无 `SPRING_PROFILES_ACTIVE`）

**影响**：生产环境每条 SQL 输出到容器 stdout → 日志量放大、I/O 开销、Docker 日志无轮转时快速占满磁盘；且 SQL 日志会打印 `payload` 参数，存在**数据泄漏**风险。同时 `application-prod.yml` 中 Hikari 连接池 50（base 为 20）等配置全部未生效。

### P1-2 数据模型冗余：同一份数据写三处

**现象**：`data` 上行消息同时写 `message`（`direction='SUBSCRIBE'`）与 `history_record`；两表字段高度重叠（`device_id`/`topic`/`payload`/时间），仅 `payload` 类型不同（`TEXT` vs `JSON`）；同一事件有三个时间戳（`message.sent_at` 应用侧赋值、`message.received_at` DB 默认值、`history_record.timestamp`）。

**证据**：`V1__baseline.sql:63-78`（message）、`:81-91`（history_record）、`:51-60`（device_status_history）；`MqttMessageHandler.java:84`/`:86`

**影响**：
1. 写入放大一倍，直接加剧 P0-1。
2. 查询口径分裂：历史页查 `history_record`、消息页查 `message`，同一事件两处答案可能不一致（例如其中一次写入失败）。
3. 无分区、无保留策略，`message` 表无限增长；`message` 上有 5 个单列索引 + 1 个复合索引（`V1__baseline.sql:72-76`），写多读少的表索引过多会拖慢写入。

### P1-3 事务边界错误（"假装的事务"）

**现象**：
1. `publishMessage` 在 `@Transactional` 内**先做 MQTT 远程发布**再写库 —— 事务与数据库连接跨越一次网络往返。
2. `messageArrived` 串行调用 3 个各自 `@Transactional` 的方法，**无统一事务** → 部分成功无法回滚。
3. `exportCredentials` 的 `@Transactional` 覆盖全表循环 + 逐设备重置密钥。

**证据**：`MessageServiceImpl.java:36-62`（`:46` publish、`:59` save）、`MqttMessageHandler.java:83-88`、`DeviceCredentialServiceImpl.java:49-61`

**影响**：长事务占用连接池；跨系统（MQTT/HTTP）与数据库混在一个事务里，语义上**无法回滚**（MQTT 消息发出去就收不回），属于伪事务；上行链路的部分失败导致数据不一致。

### P1-4 前端：全量引入 Element Plus、巨型组件、零测试

**现象**：`main.js` 全局 `app.use(ElementPlus)` 并引入全量 CSS；构建产物 `element-plus` chunk **949KB**（gzip 292KB）、`echarts` chunk 568KB；11 个页面全部超过 230 行，最大 919 行；`package.json` 无任何测试框架。

**证据**：`frontend/src/main.js:3-4`/`:16-18`、`frontend/vite.config.js:20-26`、构建输出、`frontend/package.json:6-10`/`:21-24`

**影响**：首屏加载与构建体积偏大；页面级改动风险高且无回归网。
**附带修正**：`docs/ARCHITECTURE.md` 中「Element Plus 按需引入 + 图标 tree-shaking」与实现不符（`Icon.vue` 与 SVG 图标确实按需，但 Element Plus 是全量引入），需一并修正。

### P1-5 依赖老化

**证据**：`backend/pom.xml:10`（`spring-boot-starter-parent` 3.3.0）、`:73`（`org.eclipse.paho.client.mqttv3` 1.2.5）、`:49`（`mybatis-plus-spring-boot3-starter` 3.5.7）、`:100`（`springdoc-openapi-starter-webmvc-ui` 2.3.0）、`:55-66`（jjwt 0.12.3）

**影响**：Spring Boot 3.3.x 分支已停止 OSS 维护，缺后续安全补丁；**Paho 1.2.5 发布于 2020 年、不支持 MQTT 5** —— 这直接封死了「用 MQTT 5 共享订阅解决水平扩展」的选项，是本方案的关键约束（见 3.3）。

### P2-1 数据访问层：N+1 与缺分页

**证据**：`DeviceCredentialServiceImpl.java:50-61`（循环内 2N 次查询）、`DeviceMonitorService.java:37-39`（逐设备更新）、`AnalyticsServiceImpl.java:28-53`（把全量设备拉进内存做计数聚合，而非 SQL `GROUP BY`）、`DeviceMapper.xml:37-43`（`findTimeoutDevices` 依赖 `status` + `last_seen` 低选择性单列索引，数据量大易退化）；`findByOwnerId` / `getUserApiKeys` / `getUserWebhooks` / `getHistoryByDeviceId` / `exportCredentials` 均无分页。

**影响**：设备量上千后统计、导出、在线巡检明显变慢。

### P2-2 运维与安全细节

| 项 | 证据 | 风险 |
|----|------|------|
| `/actuator/health` 公开且 `show-details: always` | `application.yml:128-135` | 对外暴露依赖组件明细（信息泄漏） |

## 3. 目标架构与关键选型

### 3.1 架构形态：模块化单体（推荐）

| 选项 | 说明 | 评价 |
|------|------|------|
| **A. 模块化单体（推荐）** | Maven 多模块或 Spring Modulith，按领域切 4 个模块：`ingest`（接入摄取）、`device`（设备与身份）、`telemetry`（遥测查询）、`platform`（认证/APIKey/Webhook 等平台能力）。单进程部署，模块间仅经接口调用 | 获得约 90% 的边界收益、0 的分布式代价；为将来按需拆出 `ingest`/`telemetry` 保留清晰接缝 |
| B. 微服务拆分 | `ingest` / `device` / `telemetry` / `auth` 四服务 + 网关 | 4508 行代码承担 4 类分布式新问题，成本远超收益；不建议现在做 |

**推荐 A**。代价：模块边界靠约定 + 测试保障（可用 Spring Modulith 的 ArchUnit 规则做强制校验），无法靠进程隔离强制。

### 3.2 上行链路：接入与落库解耦（核心改造）

| 选项 | 说明 | 评价 |
|------|------|------|
| **A. 引入消息队列**（Kafka / RocketMQ） | EMQX 规则引擎或桥接投递到队列，后端消费者批量落库，失败重试 + 死信 | 解决「重启丢消息」与「多副本重复消费」；代价是多一个中间件及其运维 |
| **B. 进程内异步批量（推荐先做）** | Paho 回调只做「解析 + 入队」，独立线程池按大小/时间双阈值批量写库 | 成本最低、当天可落地，立刻拿到吞吐与可靠性提升；但不解决重启丢消息与多副本重复消费 |
| C. 只做索引与连接池优化 | 不改执行模型 | 收益有限，不解决根因 |

**推荐路径：先 B 后 A。** R1 用 B 把同步落库改为异步批量（拿到 80% 收益），R2 视设备规模决定是否升级到 A。这样不为尚未到来的规模提前买单。

**无论 A/B 都必须落实的设计点**：
1. 回调线程只做「解析 + 入队」，**禁止任何 DB / HTTP 操作**。
2. 批量落库：按 `batch-size`（如 500）与 `flush-interval`（如 200ms）双阈值 flush。
3. 失败重试（指数退避）+ 死信表；**删除静默 catch**，异常必须可观测、可补偿。
4. 背压：队列水位触发告警与限流，而非无声打满 `maxInflight`。
5. 顺序性：按 `deviceKey` 哈希到固定队列/线程，保证**单设备内有序**（全局有序无必要且代价高）。
6. 优雅停机：`server.shutdown: graceful` 已有，需补「停机前 flush 未落库批次」。

### 3.3 实时通道：跨副本广播

| 选项 | 说明 | 评价 |
|------|------|------|
| **A. Redis Pub/Sub（推荐）** | 每个后端副本订阅 Redis 频道；ingest 侧统一发布，本副本只推自己的 SSE 订阅者 | Redis 已在架构内（JWT 黑名单在用），改动最小；代价是 Redis 成为实时链路单点（需开 AOF + 哨兵/集群） |
| B. MQTT 5 共享订阅（`$share`） | 需 EMQX 侧支持 + 客户端支持 MQTT 5 | 当前 Paho 1.2.5 **不支持 MQTT 5**，需更换客户端库（HiveMQ MQTT Client 或 Paho 5.x），与 3.7 依赖升级合并考虑 |
| C. 粘性会话 + 单副本推送 | SSE 是长连接，粘性只能缓解不能解决跨副本 | 不可行 |

**推荐 A**，并把选项 B 作为 R3 依赖升级后的可选增强。

**附带必须修复项**：SSE 增加服务端心跳（如 15s 注释帧）与连接超时（如 30min），消除 emitter 泄漏；同一 userId 的订阅者改为 `Set` 以支持多端/多标签；`publish` 从 `synchronized` 改为「快照订阅者 + 异步投递」，不再阻塞回调线程。

### 3.4 数据模型与存储

- **收敛写入**：`data` 上行**只写一张表**。建议保留 `message` 作为通用消息流水（含 `PUBLISH`/`SUBSCRIBE`），把 `history_record` 降级为只读（停写、保留一个版本周期后再删），历史查询改查 `message` 并按 `topic` 过滤。**需业务确认历史页的查询语义**（是否需要 JSON 结构查询能力——`history_record.payload` 是 `JSON` 类型，`message.payload` 是 `TEXT`，若要按 JSON 字段过滤，需给 `message.payload` 加生成列 + 索引，或改用 JSON 类型）。
- **分区**：`message` 按 `sent_at` 做月度 `RANGE` 分区 + 定时预建分区任务，替代无界增长。
- **保留策略**：明确 TTL（如原始消息 90 天、聚合指标长期），定时任务 `DROP PARTITION`。
- **索引治理**：复核 `message` 上 5 个单列索引的实际使用率，删除冗余索引（写多读少的表，索引越多写越慢）。
- **时序库（可选，R5）**：仅当 `message` 表规模成为查询瓶颈时，再引入 TDengine / ClickHouse 承载遥测查询。触发阈值见 R5。

### 3.5 接入安全：认证结果缓存

1. **Redis 缓存认证元数据**：key `auth:{productKey}:{deviceKey}` → `{凭据哈希, 状态, 产品状态, 版本号}`，TTL 60~300s。把每次认证的 2 次 DB 查询降为 0~1 次。
2. **主动失效**：密钥重置、设备禁用、产品停用时递增版本号，缓存键带版本，旧条目自然失效。
3. **BCrypt 不可削弱**：明文校验必须每次计算（strength=10 保持），但认证回调本身无状态、可水平扩展。
4. **优先用 Broker 侧缓存**：EMQX 5 支持认证结果缓存（auth cache），应优先配置它来减少回调总量，其次才在后端加 Redis 缓存。
5. **ACL 回调**：当前为纯内存匹配（`AclEvaluator.java:22-64`），保持；若主题规则复杂化，改为「规则编译 + 本地缓存」。

## 5. 风险与回滚

| 风险 | 影响 | 缓解 |
|------|------|------|
| 异步化后同设备消息乱序 | 设备状态与历史顺序错乱 | 按 `deviceKey` 哈希到固定队列/线程，保证单设备内有序 |
| 批量落库的内存丢失窗口 | 进程崩溃时未 flush 的批次丢失 | 队列水位上限 + 优雅停机 flush + 死信兜底 |
| Redis 成为实时链路单点 | 实时数据中断 | 开 AOF + 哨兵；实时通道允许丢（历史以 DB 为准），失败需告警而非静默 |
| `message` 分区改造涉及大表 DDL | 停机与迁移风险 | Flyway 新增迁移，先在副本库演练；双写迁移或安排停机窗口 |
| 删除 `history_record` 影响历史页 | 功能回归 | 先停写并保留表（只读）观察一个版本周期，再删除 |
| Vue Query 引入带来大面重构 | 前端回归 | 按页面灰度：先 Dashboard / HistoryQuery，后 DeviceList |
| 依赖大版本升级引入不兼容 | 构建失败或行为变化 | 单独成阶段（R3），升级前补齐集成测试 |

**阶段性回滚**：R1 保留「同步/异步」开关，异常时可切回；R2 保留单副本部署模式，关闭 Redis Pub/Sub 即退回当前形态；R4 前端改动按页面独立提交，可单页回滚。

### C.2 实测暴露的环境缺陷及处置（R0 收尾 + R1-8 已修复并验证）

1. **宿主机 1883 被原生 Mosquitto 占用，EMQX 曾临时映射到 11883。**
   宿主机 `1883` 监听进程为原生 `mosquitto`（Windows 服务，启动类型 Auto），而 EMQX 容器一度映射 `11883→1883`，与 `.env` 的 `MQTT_PORT=1883` 及全部文档口径漂移。压测脚本若用 1883 会连到 Mosquitto 而非 EMQX —— 消息"发布成功"却无人接收，极易被误判为"后端丢消息"。
   **处置**：停止 Mosquitto 服务并置为手动启动，重建 EMQX 容器绑定 `1883→1883`，全项目口径回归标准端口。
   **验收**：`docker ps` 显示 `0.0.0.0:1883->1883`；经宿主 1883 端口连接 EMQX 返回 `CONNACK(0)`；后端日志显示 `MQTT 连接就绪: serverURI=tcp://emqx:1883` 并重新订阅 `device/+/data|heartbeat|lwt`。

2. **EMQX 认证/授权源未下发，`emqx-init` 从未成功执行。**
   EMQX 5 的 REST API **不接受 Basic 认证**（一律返回 401），而 `emqx-init.sh` 原用 `curl -u` 调用，因此脚本从未成功下发配置：`authentication` 列表为空（EMQX 无认证器即放行一切），授权源只剩默认 `file` 规则（末尾 `{allow, all}`）。
   当前因 `.env` 中 `ACCESS_CONTROL_ENFORCE_AUTH=false`（迁移期放行）掩盖了影响；但**一旦按 T-11 计划把它置为 `true`，EMQX 仍不会回调，认证与主题级 ACL 不会真正生效** —— 这是"以为已加固、实际未加固"的隐患。
   **处置**：`emqx-init.sh` 改为先 `POST /api/v5/login` 换取 Bearer token 再调用；补全 `authorization/settings` 请求体（`no_match` / `deny_action` / `cache` 缺一即 400）；compose 的 `emqx` 服务补上 `EMQX_DASHBOARD__DEFAULT_PASSWORD`，避免容器初始密码与 `emqx-init` 登录凭据不一致。
   **验收**：EMQX debug 日志显示连接时 `emqx_authn_http` 回调 `POST /api/internal/emqx/auth` 并返回 `{"result":"allow"}`，订阅时 `emqx_authz_http` 回调 `POST /api/internal/emqx/acl` 且记录 `authorization_permission_allowed ... source: http`；认证器 `password_based:http` 与授权源 `http` 均已启用。
   **遗留**：`authorization/settings` 的 `no_match` **实际仍为默认 `allow`**（`deny_action=ignore`、`cache{enable,max_size:32,ttl:1m}` 也全是默认值，说明脚本那次 PUT 未真正生效），且 `file` 授权源末尾仍保留 `{allow, all}` 兜底规则 —— 即"HTTP 授权未给出结论时一律放行"。这与 T-11 设计意图（未匹配即拒绝）不符，见缺陷 6。

3. **`UploadLoadTest` 的注释声称覆盖认证路径，此前不成立。**
   脚本走真实设备一机一密凭据，本意是同时压测认证回调；受缺陷 2 影响回调未被调用。缺陷 2 修复后该声明成立，压测会同时覆盖认证与授权回调。

4. **后端 MQTT 初始连接一旦失败便永不重连，静默丢弃全部上行消息（P0，R1 必须修）。**
   `MqttClientManager` 用 Paho 的 `setAutomaticReconnect(true)`，但 Paho 的自动重连**只覆盖"曾成功连接后断开"**；初始 `connect()` 抛异常时不会触发重连。后端是纯订阅者，没有主动 publish，因此 `ensureConnected()` 不会被再次调用 —— 结果是**永久失联**。
   实测复现：后端容器于 `2026-09-29 03:14` 重启后，`03:15:16` 初始连接被拒（`MQTT 初始连接失败，后续操作将自动重试: Not authorized to connect`），此后**再无任何重连日志**。期间压测发布 800 条，EMQX `messages.dropped.no_subscriber=800`、`messages.delivered=0`、`delivery.dropped.queue_full=0` —— 消息在 Broker 侧因"无订阅者"被丢弃，DB 增量 0，而发布侧 2829 msg/s 全部"成功"，极易被误判为后端丢消息。
   **处置（临时）**：重启后端容器使其重新建连。
   **根治（已完成，R1-8 / commit `7f4d9ce`）**：把"连接建立"从一次性 `register()` 改为 `mqtt-connector` 守护线程的带退避重连循环（1s→2s→…→上限 30s），`connectionLost` 立即唤醒重试；暴露 `mqtt_connected`（Gauge）与 `mqtt_connect_attempt_total` / `mqtt_connect_failure_total`（Counter），断连可由 `mqtt_connected` 归零捕获；新增 `MqttClientManagerRetryTest` 覆盖重连退避、丢失唤醒、重连开关与优雅停机。
   **验收**：`docker restart mqtt-backend` 后第 1~6 次失败按退避重试、第 7 次（约 65s）自动连上并恢复 3 个订阅，无人工干预；指标 `attempt_total=7`、`failure_total=6`、`connected=1` 与日志一致。

5. **EMQX HTTP 认证连接器处于 alarm（不健康）状态时会"不请求、直接拒绝"，与后端重启形成竞态。**
   EMQX 对 `emqx_authn_http` / `emqx_authz_http` 连接器做健康检查：后端不可用期间连接器进入 alarm，此期间 EMQX **不发出回调请求**，认证结果直接判为拒绝。实测：`03:41:14` 后端重启后连接仍被拒，EMQX 日志中**没有任何** `/api/internal/emqx/auth` 请求记录；`03:42:05` 连接器 alarm 解除（`alarm_is_deactivated ... emqx_authn_http:3` / `emqx_authz_http:4`），`03:42:32` 再次重启后端即连接成功（CONNACK ReasonCode=0，三个订阅全部 `authorization_permission_allowed`）。
   **含义**：**后端每次重启都可能因该竞态而永久失联**（叠加缺陷 4 后不会自愈）。R1 的连接重试必须包含"认证侧恢复后重试"，部署顺序上也应保证后端先于 EMQX 的认证源生效。
   **处置（已完成，R1-8 / commit `7f4d9ce`）**：监督线程不区分失败原因、只按退避持续重试，认证连接器 alarm 解除后即自动连上；启动顺序由 compose 的 `emqx → backend → emqx-init`（`service_healthy`）保证，避免在后端就绪前下发认证源。
   **残留（非缺陷，EMQX 侧行为）**：alarm 期间 EMQX 不发起回调，这约 60s 窗口内**所有**设备连接同样被拒，时长由 EMQX 连接器健康检查周期决定，后端无法缩短；已写入 `DEPLOYMENT.md` Q11 供运维识别。

6. **`emqx-init` 的 `authorization/settings` 未生效，授权兜底仍是"放行"。**
   实测 `GET /api/v5/authorization/settings` 返回 `{"no_match":"allow","deny_action":"ignore","cache":{"enable":true,"max_size":32,"ttl":"1m"}}` —— 三项**全为 EMQX 默认值**，与 `emqx-init.sh` 期望写入的 `no_match=deny` 不符（脚本用 `curl -fsS`，失败即静默或非零退出，需加显式校验）。叠加 `file` 授权源末尾的 `{allow, all}`，当前实际效果是：**主题级 ACL 的拒绝决策可能被兜底规则放行**。
   **处置（已完成，R1-8 / commit `9423bd0`）**：`emqx-init` 写入后 `GET` 回读校验四项断言（HTTP 认证器 `enable=true`、HTTP 授权源 `enable=true`、`file` 源 `enable=false`、`no_match=deny`），任一失败即 `exit 1`；同时显式禁用 `file` 授权源（`enable=false`，rules 置 `{deny, all}` 兜底），使授权决策完全由后端 HTTP 回调裁决。
   **验收**：脚本 exit=0 且输出「EMQX 认证与授权配置完成，且回读校验通过」，`no_match=deny` 与 `file` 源禁用状态均已回读确认 —— T-11 的"未匹配即拒绝"在 `ACCESS_CONTROL_ENFORCE_AUTH=true` 后成立。
