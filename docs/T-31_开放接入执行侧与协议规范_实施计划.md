# T-31 开放接入执行侧与协议规范 实施计划

> 版本：v1.0　创建日期：2026-10-10　最后更新：2026-10-10
> 上游依据：[T-30 商用化重构 开放接入与平台工程化 方案](./T-30_商用化重构_开放接入与平台工程化_方案.md)（v1.1）§0.1「第二批：执行侧 + 协议文档体系」
> 交付原则：端到端可用——点表要真能下发、Modbus 要真能采到值并入库，不以「表建好了」为完成。
> 主题策略：按阶段拆分提交（`feat(point): …` / `feat(modbus): …` / `docs(protocol): …`），不合并提交。

## 计划概览

- **Goal**：把 T-30 第一批立好的数据底座（`device_point_table` / `device_point_run` / `product.protocol_type`）真正跑起来——路线 A 把点表下发到边缘网关并收回执，路线 B 由平台侧 Modbus 主站轮询采集并把值送进既有物模型链路；同时产出 D1 / D2 两份权威协议规范。
- **Architecture**：两条路线**共用一套 SPI**（`PointCollector` 接口 + `CollectRequest` / `CollectResult`），差异只在实现类与触发源。路线 A 的点表下行**复用既有 `device/{key}/cmd/down` 通道**（不新开 topic，避免第二套下行协议）；路线 B 采集结果**复用既有 `IngestPipeline.submit()` 入库入口**（不另写属性落库逻辑）。两者最终都汇聚到 `device_property_latest` + `device_property_history`。
- **Tech Stack**：Spring Boot 4.1.1 + MyBatis Plus + Flyway（V19）+ modbus4j 3.0.6 + Vue 3 + Element Plus；后端为主。
- **Spec**：`docs/T-30_..._方案.md` v1.1 §0.1 / §3.2。
- **Global Constraints**：
  - **零回归红线**：不改 `IngestPipeline` / `IngestDispatcher` / `DeviceCommandServiceImpl` / `ThingModelInterpretServiceImpl` 的既有行为与签名；路线 B 只作为**新的生产者**接入 `IngestPipeline`，不修改其队列与 fan-out 语义。既有 1128 项后端测试必须保持全绿。
  - **执行方隔离**：`device_point_table.executor` 是 A/B 唯一的分支依据。任何取点位的方法**必须**先按 `executor` 过滤，禁止「同一台设备两种执行方混采」（会导致同一点位双写）。单台设备的 executor 一致性由服务层校验保证。
  - **Modbus 只做只读采集**：本批不支持写寄存器 / 写线圈，不下发控制类指令。控制类需求走既有 `cmd/down` 通道（路线 A 能力），避免在协议栈未成熟时开放写操作的风险面。
  - **modbus4j 引入约束**：显式写 `version`（项目已有 paho / archunit 等非 Boot 依赖的显式版本先例）；仅引入 `modbus4j`，不引入 `modbus4j-java-serial` 之外的可选传输扩展，保持依赖面最小。
  - **协议栈实例按需创建**：Modbus 主站连接**不常驻**，按轮询周期建立/复用/关闭；不在应用启动时预建连接（避免 readiness 探针被网络抖动拖垮，见 T-30 三态探针设计）。
  - **执行器线程池不复用调度池**：`ScheduleConfig` 的 poolSize=3 是全局共享的巡检池，Modbus 轮询是阻塞 IO，**不得**挂到该池上，须自建专用池并在配置里显式可配。
  - **点表下发幂等**：同一设备重复下发必须产生同一份 payload（含 `version` 单调递增），供边缘侧丢弃旧版本；不允许无版本号裸下发。
  - **失败落 `device_point_run` 而非抛异常中断整轮**：单点位采集失败只记该点位 FAILED，不影响同设备其他点位。
  - **D1 / D2 必须与代码一致**：主题规则、ACL 规则、payload schema 全部从 `AclEvaluator` / `TopicPrefixResolver` / `ThingModelInterpretServiceImpl` **实际代码**表格化提取，不凭印象编写；发现文档与代码冲突时以代码为准并在文档标注差异。

## 现状基线（实施前已核实）

| 事实 | 结论 |
|---|---|
| V18 两张表 | **只有建表 SQL，无任何 Java 实体 / Mapper / Service** |
| `ProtocolTypeValue` | 已存在（MQTT/HTTP/MODBUS/OPC_UA/GATEWAY_MQTT + normalize + isSupported）；`Product` 实体已有 `protocolType`/`driverId`/`driverConfig` 三列 |
| 下行通道 | 仅 `device/{deviceKey}/cmd/down` 一条 topic，走 `MqttClientManager`（Paho，QoS 1）；**无点表专用 topic** |
| 属性入库 | `IngestPipeline.submit()` → worker → `IngestDispatcher` 第三路 → `ThingModelInterpretServiceImpl.interpret` → `device_property_latest` + `device_property_history` |
| 巡检惯例 | `SchedulingConfigurer` + 共享 `ThreadPoolTaskScheduler`（poolSize=3）；Sweeper 整体 try/catch 只记 WARN |
| pom 协议栈 | **零 Modbus / OPC-UA 依赖**；Boot BOM 托管依赖不写 version，非 Boot 的显式写 |
| ArchUnit | Controller→Service→Mapper→Entity 分层；`ingest` 禁依赖 controller；`service`（接口包）禁依赖 mapper（持久化只在 `service.impl`） |

- [ ] 复用 `DeviceCommandServiceImpl` 的既有失败降级语义：发布异常 → `markQueued` 入离线补发队列（平台对边缘设备离线时点表下发同样需要排队）。
- [ ] 回执处理**幂等**：同一 `dispatchId + pointKey` 重复回执只取第一条（条件更新 `WHERE status='PENDING'`，复用 T-30 死信处置的条件更新范式）。
- [ ] 权限：只允许下发 `executor=EDGE` 的点表；`PLATFORM` 点表由平台自采，下发无意义，接口侧直接拒绝并给出明确错误码（避免运维误操作）。
- [ ] 单测：payload 字段与点表列的映射一致性、`version` 单调性、拒绝下发 PLATFORM 点表、回执幂等。

**Steps**
- [ ] `ModbusCollectProperties`：`enabled`（默认 `false`，与 T-30 限流同策略——避免未配置 Modbus 时误启动）、`host`/`port`/`unitId` 默认值、`connectTimeoutMs`、`readTimeoutMs`、`retry`、`maxConnections`、`minIntervalMs`（**采集周期下限，防止点表误配 100ms 打爆现场总线**）、`enabledDeviceLimit`。
- [ ] `ModbusCollectExecutorConfig` **自建** `ThreadPoolExecutor`（阻塞 IO，与 `ScheduleConfig` 的 poolSize=3 巡检池隔离），核心线程数 / 队列容量可配，拒绝策略为「CallerRuns」并记 WARN（过载时降速而非丢采集）。
- [ ] `ModbusCollectSweeper` 遵循既有 Sweeper 惯例：`implements SchedulingConfigurer`、间隔 `≤0` 时不注册并 log.info、`sweep()` 整体 try/catch 只记 WARN。职责：查「到期的 PLATFORM 点位」→ 按设备分组 → 提交专用线程池 → 线程内执行 `PointCollector`。
- [ ] `ModbusPointCollector` 实现采集：连接（`ModbusMaster`）→ 批量读 → 逐点换算 → 关闭。**连接生命周期必须在 `finally` 关闭**，异常不外泄到调度线程。
- [ ] `ModbusPointDispatch` 把同设备同 `read_interval` 的连续寄存器点位合并成一次读（`readHoldingRegisters` 覆盖区间），显著减少现场总线往返；合并失败自动降级为逐点读。
- [ ] `ModbusValueConverter`：`工程值 = 原始值 * scale + offset`（V18 已有 scale/offset 列），按 `dataType` 处理 int/float/double/bool/string；bool 取 `!=0`。**换算口径必须写进 D2 文档**，避免边缘侧与平台侧算出两个值。
- [ ] `PointRunRecorder`：每次采集无论成败都落 `device_point_run`（OK / FAILED / SKIPPED）。`SKIPPED` 用于「距上次采集未到间隔」。批量写以控制 IO 压力。
- [ ] 采集结果组装为 `IngestRecord`（`messageType="property"` 语义与 MQTT 上报对齐）后 `submit()`，**不直接调 mapper 写属性表**——这是 Global Constraints 里「零回归」的关键：走既有管线才能同时获得告警/规则/场景/历史五条旁路。
- [ ] 认证与现场安全：**默认不做持久连接、不做写操作、不做内网地址透传校验**；`driver_config` 由 ADMIN 维护（沿用 `ProductRequest` 的权限口径）。
- [ ] 单测（重点，modbus4j 难在真机验证，故单测必须扎实）：
  - `ModbusValueConverter` 全 `dataType` × 有/无 scale-offset 的换算矩阵；
  - `ModbusPointDispatch` 的区间合并正确性（跨功能码不合并、跨 unitId 不合并、边界地址不越界）；
  - `PointRunRecorder` 的三态落库；
  - `ModbusCollectProperties` 的 `minIntervalMs` 钳制生效（配置 100ms 被抬到下限）；
  - 连接异常时连接被关闭（可用 mock 验证，不需真机）。

## 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| Modbus 现场总线负载：`read_interval_ms` 误配过小 | 打爆现场总线，影响安全生产 | `minIntervalMs` 硬钳制；批量读合并；ADMIN 独占配置权 |
| modbus4j 无真机可测 | 缺陷逃逸到现场 | 采集逻辑（换算/合并/调度）全部与传输层解耦，单测覆盖换算矩阵与合并边界；连接层用 mock |
| `version` 单调性在多副本下无法保证 | 边缘侧收到乱序版本 | 明确降级为单副本保证并**在 D2 文档标注**；后续如需强保证再引入集中式版本源 |
| 采集值绕过 `IngestPipeline` 直接写属性表 | 丢失告警/规则/场景/历史五条旁路 | Global Constraints 硬约束，代码评审与集成测试双重把关 |
| ArchUnit 分层校验拦截新包 | 构建失败 | P1 实现时即确认 `collect` 包依赖方向；必要时显式放行并注释理由，不靠临时 `@Disabled` |
| Modbus TCP 无内网隔离时可能被恶意地址探测 | 安全风险面 | 本批不做地址白名单校验，但**在 D2 与 DEPLOYMENT 中明确标注为部署侧职责**，作为下一批安全加固项 |

## 验收标准

1. 点表可通过 API 与前端页增删改查，同设备 executor 混用在服务端被拒
2. `executor=EDGE` 的点表能经 `cmd/down` 下发到网关，payload 含单调 `version`，网关回执能落 `device_point_run` 且幂等
3. `executor=PLATFORM` 的点表被 Modbus 主站按周期采集，换算口径与 `scale`/`offset` 一致，结果经 `IngestPipeline` 进既有属性链路
4. 单点位失败不影响同设备其他点位；失败原因落 `device_point_run.error_message`
5. D1 / D2 两份文档每条规则可溯源到源码或迁移 SQL，无凭印象编写的内容
6. 后端 `verify` 与前端 lint / test / build 全绿，既有 1128 项测试零回归
