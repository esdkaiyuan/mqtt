## 1. 背景与目标

T-14 ~ T-19 已交付「物模型 → 命令 → 影子 → 告警 → 分组 → 规则」闭环，但**「一台设备到底发生了什么」缺少一个统一的视图入口**：

- 与设备相关的记录散落在**四张互不相通的表**里，各自有独立的页面，无法串成一条时间线：
  - `message`：原始上下行报文（实时消息页 `MessageMonitor.vue` / 历史数据页）；
  - `device_command_record`：命令下发记录（设备详情页「命令记录」区块 `DeviceCommandHistory.vue`）；
  - `device_event_record`：设备事件上报（设备详情页「事件」区块 `DeviceEventPanel.vue`）；
  - `device_status_history`：设备上下线（连接事件，目前**仅落库、无任何查询入口**）。
- 排障时需要在四个页面之间来回切换、靠时间手工对齐；**离线 / 上线这类连接事件在控制台根本看不到**。
- 路线图 §2 能力域 7「设备日志与诊断」现状为「分散在消息 / 命令 / 事件页，无统一时间线」。

本任务引入**统一日志时间线**：把四类记录在**查询时归并**为一条按时间倒序的时间线，可按类型与时间过滤；并让「一次命令下发」能够串起**「下发 → 回执」**两条记录（路线图 A2 验收项）。

目标：

1. **统一入口**：单台设备的所有历史记录在一个页面、一条时间线上按时间倒序呈现，可按日志类型（消息 / 命令 / 事件 / 连接）与时间范围过滤、分页。
2. **覆盖连接事件**：把此前无入口的 `device_status_history`（上下线）纳入时间线。
3. **可串联命令链路**：命令记录与其对应的**回执报文**（`device/{deviceKey}/reply` 落入 `message`）在时间线上可配对标注为「下发 → 回执」。
4. **零写入改造、可安全回滚**：查询时聚合存量表，**不新建表、不改写入路径、不动 MQTT 主题 / ACL**，回滚只需摘除新增端点与页面。
5. **不破坏既有能力**：四类记录的既有页面与端点保持不变，本任务只**新增**只读查询能力。

## 3. 术语

| 术语 | 含义 |
| --- | --- |
| 设备日志（Device Log） | 某台设备在平台上留下的**只读**历史记录的统一视图 |
| 统一日志条目（DeviceLogItem） | 时间线上的一个节点，由四类来源之一投影而来 |
| 日志类型（DeviceLogType） | 条目来源分类：`MESSAGE`（报文）/ `COMMAND`（命令）/ `EVENT`（事件）/ `STATUS`（连接事件） |
| 连接事件 | `device_status_history` 中的上下线记录（`ONLINE` / `OFFLINE`） |
| 归并键（occurred_at） | 排序时间：报文取 `sent_at`、命令取 `created_at`、事件取 `reported_at`、连接取 `timestamp` |
| 关联键（correlationId） | 用于配对「下发 → 回执」：命令条目为 `command_id`；回执消息条目为解析 `payload.id` 得到 |
| 回执报文 | 设备对命令的应答，发布到 `device/{deviceKey}/reply`，由平台订阅后落 `message`（`direction=SUBSCRIBE`） |

## 4. 主题方案

### 4.1 查询时聚合、不新增表、不改写入路径

统一日志**不是一份新的数据**，而是四张存量表的**只读投影**；因此本任务：

- **不新建表、不新增 Flyway 迁移**：`V1`~`V9` 保持不变；
- **不改任何写入路径**：`MqttMessageHandler` / `IngestDispatcher` / `ThingModelInterpretService` / `CommandReplyService` / `DeviceStatusHistoryService` 均**零改动**；
- **不新增 MQTT 主题、不改 ACL**：本任务只读库，`emqx-init` 零改动；
- **回滚成本极低**：摘除 `DeviceLogController` 端点与前端路由即可，数据层无任何残留。

理由见 §4.3。

### 4.2 权限与隔离

- 接口取当前用户 `SecurityUtils.requireUserId()`；设备级校验：
  - 设备不存在（含已删除）→ `DEVICE_NOT_FOUND(2002)`；
  - 设备存在但 `owner_id != 当前用户` → `DEVICE_NOT_OWNED(2003)`（`HttpStatus.FORBIDDEN`，沿用既有语义，**不新增同义码**）。
- 由于接口是**设备级**且鉴权在入口一次性完成，四张表的查询天然被限定在「本用户的这一台设备」，**无需再对每张表做 `owner_id` 关联过滤**，SQL 显著更轻。
- 需复核：`device_command_record` / `device_event_record` / `device_status_history` 对 `device_id` 均为 `ON DELETE CASCADE`，设备删除后其记录一并消失；`message.device_id` 为 `ON DELETE SET NULL`——即**设备删除后报文不随删除**（既有行为，本任务不改），但由于本接口要求设备存在（`2002` 兜底），`SET NULL` 的孤儿报文不会出现在时间线中，属可接受行为。

### 4.3 为什么是「查询时聚合」，而不是「新建统一日志表」

| 维度 | 查询时聚合（**选定**） | 新建 `device_log` 表（未选） |
| --- | --- | --- |
| 写入路径 | 零改动 | 需在四处写入点双写，且要保证与主链路事务 / 顺序一致 |
| 迁移风险 | 无（无 DDL） | 新增迁移 + 历史数据回填，回滚需删表 |
| 数据一致性 | 天然一致（读的就是唯一事实源） | 双写存在**漂移**风险（MQTT 重投、命令状态机多段更新） |
| 排障价值 | 高（记录即现状） | 中（若双写漏写，日志本身不可信） |
| 性能 | 设备级 + 时间窗 + 已有索引，可控（见 §5.4） | 写入放大；仍需同样查询 |
| 扩展性 | 后续如需「全局日志 / 更快查询」再演进为物化表或 ES | 一开始就背上写放大 |

结论：本任务取**查询时聚合**。四张表在 `(device_id, 时间列)` 上**均已有索引**（`message.idx_device_sent`、`device_command_record.idx_device_created`、`device_event_record.idx_device_reported`、`device_status_history.idx_device_timestamp`），设备级 + 时间窗过滤可走索引，无需新增索引。

### 4.4 「下发 → 回执」如何串联（验收项 A2）

命令记录与回执报文**分别在两张表**，需要一条可配对的关联键：

- **命令侧**：`device_command_record.command_id`（VARCHAR(36)，`uk_command_id` 唯一）——即 关联键。
- **回执侧**：设备回执报文发布到 `device/{deviceKey}/reply`，载荷形如 `{"id":"<command_id>","code":200,"data":{...}}`，由 `CommandReplyServiceImpl` 消费（据 `id` 更新命令状态为 `ACKED` / `FAILED`），同时该报文由 `MqttMessageHandler` 落 `message`（`direction=SUBSCRIBE`，`topic` 以 `/reply` 结尾）。
- **串联方式**：服务层在**组装分页结果时**（Java 侧，而非 SQL 侧）对 `MESSAGE` 条目判定「`topic` 以 `/reply` 结尾」→ 用 `ObjectMapper` 安全解析 `payload.id` → 写入 `correlationId`，并标记 `correlationRole=REPLY`；`COMMAND` 条目 `correlationId = command_id`、`correlationRole=REQUEST`。前端据 `correlationId` 将同组的「命令下发」与「回执」两条记录配对展示。

> 不在 SQL 内做关联的原因：`message.payload` 为 `TEXT` 且内容不保证是合法 JSON（上行既有合法 JSON，也可能是非 JSON 文本），在 SQL 里调用 `JSON_EXTRACT` 会因非法 JSON 报错；Java 侧解析可 `try/catch` 安全降级（解析失败则 `correlationId=null`，不影响该条目展示）。

## 5. 数据模型与统一日志条目

### 5.1 四类来源 → 条目字段映射

| DeviceLogItem 字段 | MESSAGE（`message`） | COMMAND（`device_command_record`） | EVENT（`device_event_record`） | STATUS（`device_status_history`） |
| --- | --- | --- | --- | --- |
| `occurredAt`（排序键） | `sent_at` | `created_at` | `reported_at` | `timestamp` |
| `title` | 报文方向 + topic 末段 | `命令：{identifier or command_type}` | `事件：{identifier}` | `设备上线 / 设备离线` |
| `subType` | `topic` | `command_type` | `event_type`（info/alert/fault） | `status` |
| `identifier` | `null` | `identifier` | `identifier` | `null` |
| `status` | `null` | `status`（PENDING/SENT/QUEUED/ACKED/FAILED/TIMEOUT） | `null` | `ONLINE/OFFLINE` |
| `payload` | `payload` | `params` | `output_data` | `null` |
| `direction` | `PUBLISH`（下行）/ `SUBSCRIBE`（上行） | `DOWN` | `UP` | `null` |

### 5.2 各来源专属可空列

| 字段 | 仅 MESSAGE | 仅 COMMAND | 仅 EVENT | 仅 STATUS |
| --- | --- | --- | --- | --- |
| `topic` | ✅ | | | |
| `qos` | ✅ | | | |
| `receivedAt` | ✅ | | | |
| `commandId` | | ✅ | | |
| `callType` / `source` / `operatorId` | | ✅ | | |
| `result` / `errorMessage` / `attemptCount` / `finishedAt` | | ✅ | | |
| `eventType` | | | ✅ | |
| `correlationId` / `correlationRole` | ✅（仅 `/reply`） | ✅ | | |

### 5.3 关联键与角色

- `correlationId`：`COMMAND` 取 `command_id`；`MESSAGE` 且 `topic` 以 `/reply` 结尾时取解析出的 `payload.id`；其余为 `null`。
- `correlationRole`：`REQUEST`（命令下发）/ `REPLY`（回执报文）/ `null`。
- `logId`：`{logType}-{来源主键}`（如 `COMMAND-1024`），作为前端列表 key，保证跨来源唯一。

### 5.4 排序与分页

- 外层 `ORDER BY occurred_at DESC, seq DESC`（`seq` 为来源主键，保证同一时刻稳定排序）。
- `pageSize` 默认 `20`、上限取 `app.device-log.max-page-size`（默认 `100`）；`pageNum` 从 `1` 起。
- 时间窗为**半开区间** `[startTime, endTime)`；`startTime` / `endTime` 均可空。
- 查询跨度上限 `app.device-log.max-range-days`（默认 `31` 天）：同时给出 `startTime` 与 `endTime` 且超出上限时报 `6223`（防止一次拉过大范围拖垮库）。

## 6. 接口设计

### 6.1 统一日志查询

```
GET /api/devices/{deviceId}/logs
```

| 参数 | 位置 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- | --- |
| `deviceId` | path | Long | 是 | 设备 ID（须为本用户设备） |

### 7.1 分层与类清单（遵守 `LayeringRulesTest`）

### 7.2 聚合 SQL 设计（`DeviceLogMapper.xml`）

可复用片段（四段 `SELECT` 投影到**同一列集**，缺失列置 `NULL`）：

```xml
<sql id="logUnion">
  SELECT CONCAT('MSG-', m.id) AS log_id, 'MESSAGE' AS log_type, m.direction AS direction,
         m.sent_at AS occurred_at, m.topic AS topic, NULL AS identifier, NULL AS sub_type,
         NULL AS status, m.payload AS payload, NULL AS command_id, NULL AS call_type,
         NULL AS source, NULL AS operator_id, NULL AS error_message, NULL AS attempt_count,
         m.received_at AS secondary_time, m.qos AS qos, m.id AS seq
  FROM message m
  WHERE m.device_id = #{deviceId}
    <if test="startTime != null">AND m.sent_at &gt;= #{startTime}</if>
    <if test="endTime != null">AND m.sent_at &lt; #{endTime}</if>
  UNION ALL
  SELECT CONCAT('CMD-', c.id), 'COMMAND', 'DOWN', c.created_at, NULL, c.identifier, c.command_type,
         c.status, c.params, c.command_id, c.call_type, c.source, c.operator_id, c.error_message,
         c.attempt_count, c.finished_at, NULL, c.id
  FROM device_command_record c
  WHERE c.device_id = #{deviceId}
    <if test="startTime != null">AND c.created_at &gt;= #{startTime}</if>
    <if test="endTime != null">AND c.created_at &lt; #{endTime}</if>
  UNION ALL
  SELECT CONCAT('EVT-', e.id), 'EVENT', 'UP', e.reported_at, NULL, e.identifier, e.event_type,
         NULL, e.output_data, NULL, NULL, NULL, NULL, NULL, NULL, e.created_at, NULL, e.id
  FROM device_event_record e
  WHERE e.device_id = #{deviceId}
    <if test="startTime != null">AND e.reported_at &gt;= #{startTime}</if>
    <if test="endTime != null">AND e.reported_at &lt; #{endTime}</if>
  UNION ALL
  SELECT CONCAT('STA-', s.id), 'STATUS', NULL, s.timestamp, NULL, NULL, s.status,
         s.status, NULL, NULL, NULL, NULL, NULL, NULL, NULL, NULL, NULL, s.id
  FROM device_status_history s
  WHERE s.device_id = #{deviceId}
    <if test="startTime != null">AND s.timestamp &gt;= #{startTime}</if>
    <if test="endTime != null">AND s.timestamp &lt; #{endTime}</if>
</sql>
```

分页查询与计数查询分别包一层（**计数用显式 `countQuery`**，不依赖 MyBatis-Plus 的自动 count —— UNION 场景下自动 count 的 SQL 重写不可靠）：

```xml
<select id="pageQuery" resultType="com.mqtt.cloud.dto.response.DeviceLogItem">
  SELECT * FROM ( <include refid="logUnion"/> ) t
  <where>
    <if test="types != null and types.size() > 0">AND t.log_type IN <foreach .../></if>
    <if test="keyword != null and keyword != ''">AND (t.topic LIKE #{keyword} OR ...)</if>
  </where>
  ORDER BY t.occurred_at DESC, t.seq DESC
  LIMIT #{offset}, #{size}
</select>

<select id="countQuery" resultType="long">
  SELECT COUNT(*) FROM ( <include refid="logUnion"/> ) t
  <where> ... 与 pageQuery 相同的过滤 ... </where>
</select>
```

服务层组装 `Page<DeviceLogItem>`（`setTotal` + `setRecords`）后返回，保持 `Result<IPage<...>>` 的对外形状一致。

### 7.3 服务层流程（`DeviceLogServiceImpl`）

1. `requireUserId()` 已在 Controller 完成传参；
2. **设备鉴权**：`deviceMapper.selectById(deviceId)` → 空 = `2002`；`owner_id != userId` → `2003`；
3. **参数归一化**：`types` 白名单校验（非法 → `6224`）；`pageNum` / `pageSize` 夹取（`pageSize` 上限取配置）；`startTime` / `endTime` 解析（非法格式 → `6223`）；跨度校验（> `max-range-days` → `6223`）；
4. `countQuery` → `total`；`total == 0` 直接返回空页（**不再执行 `pageQuery`**）；
5. `pageQuery` → `records`；
6. **关联键回填**：仅对 `logType=MESSAGE` 且 `topic` 以 `/reply` 结尾的条目，用 `ObjectMapper` 安全解析 `payload.id` 写入 `correlationId` / `correlationRole=REPLY`（解析失败 → 保持 `null`，只记 DEBUG）；命令条目填 `REQUEST`；同时按 §5.1 生成 `title` / `direction` 展示字段；
7. 返回 `Page`。

> `ObjectMapper` 注入沿用仓库既有 `tools.jackson.databind.ObjectMapper`（T-15 `CommandReplyServiceImpl` 同款），保证与主链路解析口径一致。

### 7.4 为什么不复用既有各表的 Mapper

`MessageMapper.pageQuery` / `DeviceCommandRecordMapper` / `DeviceEventRecordMapper` / `DeviceStatusHistoryMapper` 各自只查单表、且 `message` 侧做了 `LEFT JOIN device` 的用户过滤；统一时间线需要**跨表归并 + 全局排序 + 全局分页**，在应用层拼四份 `IPage` 再归并**无法正确处理分页**（`total` 与跨源排序都会错）。因此新增独立的 `DeviceLogMapper`，用一个 SQL 完成归并，四张表的既有 Mapper **零改动**。

## 12. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| `UNION ALL` 在无时间窗时的扫描量 | 慢查询 | 设备级限定 + 默认时间窗（前端默认「近 24 小时」）+ 跨度上限 `31` 天；必要时提示用户缩小范围 |
| `message.payload` 非合法 JSON | 关联键解析失败 | Java 侧 `try/catch` 降级为 `null`，不影响条目展示 |
| UNION 场景下 MyBatis-Plus 自动 count 不可靠 | 分页 `total` 错误 | 使用**显式 `countQuery`**，服务层手工组装 `Page` |
| 同一命令产生多条回执 / 重投 | 配对出现多对一 | 配对仅作**展示标注**，不改变任何状态；同 `correlationId` 的多条回执并列展示 |
| 设备删除后 `message.device_id` 置空产生孤儿报文 | 日志缺失 | 既有行为；接口要求设备存在，孤儿报文不进入时间线（可接受，见 §4.2） |
| `types` / 时间参数被构造为注入载荷 | SQL 注入 | 全部走 MyBatis `#{}` 占位符；`types` 白名单校验；`keyword` 由服务层包裹 `%` 后以 `#{}` 传入 |
