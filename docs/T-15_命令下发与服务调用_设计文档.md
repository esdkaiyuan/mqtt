# T-15 命令下发与服务调用 — 设计文档

> 版本：v1.0　创建日期：2026-10-02　状态：待评审
> 上游依据：[`平台功能链路路线图.md`](./平台功能链路路线图.md) 第 3 节 L2、第 5 节（存量缺陷）
> 关联任务：T-14 物模型与数据解析（前置，已交付）、T-16 设备影子（本任务产物是其前置输入）

---

## 1. 背景与目标

### 1.1 背景

平台目前只有**上行**能力，**下行是半成品且有缺陷**：

- `ExternalApiController.sendCommand` 把设备上行 Topic 的末段替换为 `/command`（即 `device/{deviceKey}/command`）后直接发布，**不经任何校验、不留任何记录**；
- `AclEvaluator.allowPlatform` 要求平台发布的 Topic `contains("/cmd/")`，而 `device/{deviceKey}/command` 不含 `/cmd/`，因此该下发**必然被 EMQX 拒绝**（`deny` 默认策略）。这是一条从上线起就不可用的链路；
- 设备侧无回执通道：`allowDevice` 明确禁止设备发布自身 `cmd/` 前缀（防伪造下行），因此回执不能复用下行主题。

对照主流平台，下行是核心能力：阿里云 IoT 以 TSL 的**服务**定义可调用能力，通过 `thing/service/property/set` 与 `thing/service/{identifier}` 下发、设备以 `_reply` 主题回执，并保留**服务调用记录**可查 [$TRAE_REF](https://help.aliyun.com/zh/iot/developer-reference/list-of-operations-by-function)；ThingsCloud 的消息规则支持「下发命令」动作 [$TRAE_REF](https://www.thingscloud.xyz/docs/guide/rules/overview.html)。

### 1.2 目标

1. **修复存量缺陷**：命令主题与 ACL 规则对齐，非 `cmd/` 主题不再产生 ACL 拒绝；
2. **命令全链路可追踪**：每次下发落一条记录，状态从 `PENDING → SENT → ACKED/FAILED/TIMEOUT` 正确流转；
3. **参数按物模型校验**：属性设置校验「可写 + 类型/范围」，服务调用校验「入参定义」，非法参数在云端即被拒绝，不打扰设备；
4. **同步与异步两种调用方式**：异步立即返回，同步等待回执（超时失败）；
5. **端到端可用**：后端接口 + 前端「设备控制」面板与命令记录列表 + 测试 + 文档。

## 2. 范围

### 2.1 在范围内

| 项 | 内容 |
|----|------|
| 主题方案 | 下行 `device/{deviceKey}/cmd/down`；上行回执 `device/{deviceKey}/reply` |
| ACL 修正 | 令命令主题落在 `allowPlatform` 的 `/cmd/` 规则内；不改 ACL 规则本身 |
| 命令记录 | `device_command_record` 表，含状态、类型、参数、结果、耗时 |
| 参数校验 | 属性设置 / 服务调用的入参按物模型校验（复用 T-14 数据类型校验逻辑） |
| 物模型扩展 | `ThingModelDefinition` 增加服务定义与属性 `accessMode`，供校验使用 |
| 回执接入 | 订阅 `device/+/reply`，作为摄取落库后的**第四路旁路**更新命令状态 |
| 调用方式 | 同步（等待回执，超时置 `TIMEOUT`）与异步 |
| 控制台接口 | 下发命令、命令记录分页、可下发能力查询（供前端动态表单） |
| 开放 API | `/external/v1/devices/{deviceKey}/command` 与命令记录，与控制台同语义 |
| 前端 | 设备详情「设备控制」面板 + 「命令记录」列表 |
| 超时兜底 | 定时巡检把长期停留 `PENDING/SENT` 的记录置 `TIMEOUT` |

### 2.2 不在范围内（明确排除）

- **设备影子 / 离线命令缓存**：归 T-16。本任务对离线设备下发即返回 `SENT` 后超时，**不做补发**；
- **命令自动重试与指数退避**：归 T-16（补发语义与影子强相关）；
- **批量下发 / 分组下发**：归 T-18；
- **命令作为规则动作**：归 T-19；
- **命令调试台 / 可视化编排**：仅做表单式面板，不做拖拽；
- **自定义脚本编解码**：只支持 Alink JSON 子集，与 T-14 保持一致；
- **下行 QoS 2 与保留消息**：统一 QoS 1、不保留，避免设备离线时残留旧命令。

## 3. 术语

| 术语 | 含义 |
|------|------|
| 命令 command | 云端主动发给设备的一次请求，含属性设置与服务调用两类 |
| 属性设置 property_set | 要求设备把某个可写属性置为目标值（Alink `thing/service/property/set`） |
| 服务调用 service | 调用物模型中定义的服务并携带入参（Alink `thing/service/{identifier}`） |
| 回执 reply | 设备对命令的应答，携带 `code` 与 `data` |
| 同步调用 | 云端下发后等待回执，拿到终态再返回 |
| 异步调用 | 云端下发后立即返回，终态由命令记录异步更新 |
| 命令记录 | `device_command_record` 中的一行，是命令全生命周期的唯一载体 |

## 4. 主题方案

### 4.1 主题定义

| Topic | 方向 | QoS | 说明 |
|-------|------|-----|------|
| `device/{deviceKey}/cmd/down` | 平台 → 设备 | 1 | 下行命令（属性设置 / 服务调用共用一条） |
| `device/{deviceKey}/reply` | 设备 → 平台 | 1 | 命令回执 |

**为什么下行用一条主题而非按服务分主题**：设备只需订阅一条即可支持全部能力，避免 Topic 数量随服务数膨胀；命令类型由载荷的 `method` 区分，与 Alink 一致。按服务分主题（`device/{key}/cmd/service/{identifier}`）留待有「按服务细粒度授权」需求时再演进。

### 4.2 为什么不是 `device/{deviceKey}/command`

`AclEvaluator.allowPlatform` 对平台发布的要求是：

```java
return ACTION_PUBLISH.equals(action) && topic.contains("/cmd/");
```

`device/{deviceKey}/command` 不含 `/cmd/`，必然被拒。**改主题即修复缺陷**，无需放宽 ACL 规则（放宽会削弱「平台只能发布命令主题」这一约束）。

### 4.3 ACL 影响分析（规则零改动）

| 场景 | ACL 规则 | 新主题是否通过 |
|------|----------|----------------|
| 平台发布下行 | `allowPlatform`：前缀 `device/` 且含 `/cmd/` | `device/{k}/cmd/down` ✅ |
| 设备订阅下行 | `allowDevice`：前缀 `device/{k}/cmd/` | `device/{k}/cmd/down` ✅ |
| 设备发布回执 | `allowDevice`：前缀 `device/{k}/` 且**非** `device/{k}/cmd/` | `device/{k}/reply` ✅ |
| 平台订阅回执 | `allowPlatform`：前缀 `device/` | `device/{k}/reply` ✅ |
| 设备伪造下行 | `allowDevice` 禁止发布 `cmd/` | `device/{k}/cmd/down` ❌（预期拒绝） |
| 设备伪造他人回执 | `allowDevice` 要求前缀为自身 `device/{k}/` | `device/{other}/reply` ❌（预期拒绝） |

结论：**ACL 规则与授权回调一行不改**，仅修正主题即可，且双向不可伪造性由既有规则天然保证。

## 5. 载荷格式（Alink JSON 子集）

### 5.1 下行：属性设置

```json
{
  "id": "8f1c0b6e-...-a1",
  "version": "1.0",
  "method": "thing.service.property.set",
  "params": { "targetTemp": 26, "mode": "cool" }
}
```

### 5.2 下行：服务调用

```json
{
  "id": "8f1c0b6e-...-a1",
  "version": "1.0",
  "method": "thing.service.reboot",
  "params": { "delay": 3 }
}
```

### 5.3 上行：回执

```json
{
  "id": "8f1c0b6e-...-a1",
  "version": "1.0",
  "method": "thing.service.property.set.reply",
  "code": 200,
  "data": { "targetTemp": 26 }
}
```

- `id` **即命令记录的 `command_id`**，是请求 / 应答的关联键（Alink 原生语义，不额外引入 `commandId` 字段）；
- `code` 为 `200` 视为成功（`ACKED`），非 `200` 视为失败（`FAILED`，`error_message` 取 `code` 与 `data` 的文本）；
- `data` 原样以 JSON 文本落 `result`；
- `method` 用于日志与校验可读性，**关联只依赖 `id`**，容忍设备回执 `method` 不精确。

### 5.4 兼容与容错

- 回执 `id` 缺失或匹配不到记录：计指标并忽略，**不报错、不影响其余消息**；
- 回执 `code` 非数字：按 `FAILED` 处理，`error_message` 记为原始文本；
- 设备可能重复回执：只有处于 `PENDING/SENT` 的记录会被更新，**终态不可被覆盖**（幂等守卫）。

## 6. 命令记录数据模型

新增表 `device_command_record`（迁移 `V5__device_command.sql`）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT PK | 自增主键 |
| `command_id` | VARCHAR(36) UNIQUE | 命令唯一标识（UUID），回执关联键 |
| `device_id` | BIGINT FK | 设备 ID（`ON DELETE CASCADE`） |
| `product_id` | BIGINT | 下发时的产品 ID（冗余，便于按产品统计） |
| `command_type` | VARCHAR(16) | `property_set` / `service` |
| `identifier` | VARCHAR(64) NULL | 服务标识符；`property_set` 为 NULL |
| `params` | JSON NULL | 请求参数原文 |
| `status` | VARCHAR(16) | `PENDING` / `SENT` / `ACKED` / `FAILED` / `TIMEOUT` |
| `call_type` | VARCHAR(8) | `sync` / `async` |
| `source` | VARCHAR(16) | `CONSOLE` / `OPEN_API` |
| `operator_id` | BIGINT NULL | 控制台操作者用户 ID；开放 API 为 NULL |
| `result` | JSON NULL | 回执 `data` |
| `error_message` | VARCHAR(255) NULL | 失败原因（发布失败 / 回执非 200 / 超时） |
| `created_at` | DATETIME(3) | 创建时间（含毫秒，用于耗时计算） |
| `sent_at` | DATETIME(3) NULL | 发布到 Broker 的时间 |
| `finished_at` | DATETIME(3) NULL | 终态时间（`ACKED` / `FAILED` / `TIMEOUT`） |

索引：`uk_command_id(command_id)`、`idx_device_created(device_id, created_at)`、`idx_status_created(status, created_at)`（超时巡检用）。

> 耗时 = `finished_at - created_at`；`acked_at` 与终态写入是同一瞬间，故不单列，避免冗余列。

### 6.1 状态机

```
            发布成功               回执 code=200
PENDING ───────────────► SENT ──────────────────► ACKED
   │                      │
   │ 发布失败              │ 回执 code≠200
   ▼                      ▼
 FAILED ◄─────────────────┘

   PENDING / SENT ──(同步等待超时 或 巡检兜底)──► TIMEOUT
```

- `PENDING`：记录已落库、尚未发布；
- `SENT`：已成功投递到 Broker（**不代表设备已收到**，QoS 1 只保证到 Broker）；
- 终态 `ACKED` / `FAILED` / `TIMEOUT` 一经写入不再变更（回执与巡检都以条件更新保证）。

## 7. 参数校验（按物模型）

### 7.1 前置：必须有物模型

命令**必须**有模型才能校验，因此产品未定义物模型时直接拒绝（错误码 `6201`）。这与 T-14「非 Alink 载荷原样落库」的宽松策略不同：上行是「尽量不丢」，下行是「宁可不发也不错发」。

### 7.2 属性设置校验

1. `params` 必须为非空 JSON 对象；
2. 每个键必须是物模型中**已定义**的属性（否则 `6203`）；
3. 属性 `accessMode` 必须为 `rw`（否则 `6202`）；
4. 值必须通过 `dataType` 校验（类型、范围、枚举、文本长度；否则 `6204`）。

### 7.3 服务调用校验

1. `identifier` 必须命中物模型 `services`（否则 `6203`）；
2. `params` 中每个键必须命中该服务的 `inputData`（否则 `6204`）；
3. `inputData` 中 `required=true` 的入参必须存在（否则 `6204`）；
4. 值必须通过对应 `dataType` 校验（否则 `6204`）。

### 7.4 校验逻辑复用

T-14 的 `ThingModelInterpretServiceImpl.normalize` 已实现「按 `dataType` 校验并文本化」的完整逻辑（int/float/bool/text/enum/date/struct/array + 范围）。本任务把它**提取为 `ThingModelParamValidator`**（无状态组件），上行解析与下行校验共用同一实现，避免两套规则漂移：

- 上行：`normalize(spec, value)` → 文本或 `null`（不合法则跳过）；
- 下行：`validate(spec, value)` → 校验结果（含错误原因，用于 `6204` 的提示）。

`ThingModelDefinition` 需同步扩展：

- `PropertySpec` 增加 `accessMode`；
- 新增 `ServiceSpec(identifier, callType, Map<String, ParamSpec> input, Map<String, ParamSpec> output)`；
- 新增 `ParamSpec(identifier, type, min, max, integer, enumKeys, textLength, required)`；
- `ThingModelValidator.parseDefinition` 增加服务与 `accessMode` 的投影（`validate` 的 V1~V16 规则已在 T-14 覆盖服务与入参，无需改校验规则）。

## 8. 同步与异步

| 方式 | 行为 | 返回 |
|------|------|------|
| 异步 `async` | 发布后立即返回 | `commandId` + 当前状态（`SENT`） |
| 同步 `sync` | 发布后等待终态 | 终态记录（`ACKED` / `FAILED` / `TIMEOUT`） |

**同步等待的实现：轮询本表，不用进程内 `Future`。**

原因：多副本部署时回执经共享订阅（`$share/{group}/device/+/reply`）只会落到**其中一个**副本；若同步请求落在副本 A 而回执落在副本 B，进程内 `Future` 永远等不到，只能假超时。命令记录在共享数据库中，轮询天然跨副本正确。

代价：每 `poll-interval-ms`（默认 200ms）一次按唯一索引的主键查询，仅同步调用路径产生，且默认超时 5s 上限内，量级可忽略。

**超时兜底**：定时任务按 `timeout-sweep-interval-ms`（默认 30s）把 `created_at` 早于 `now - sync-timeout-ms`（异步记录用 `async-timeout-ms`，默认 60s）的 `PENDING/SENT` 记录置 `TIMEOUT`，保证**异步命令也不会永远停在 `SENT`**。

## 9. 回执接入摄取管线

沿用 T-14 建立的「落库后旁路分发」模式：

- `MqttMessageHandler.subscribe()` 增加共享订阅 `$share/{group}/device/+/reply`；
- `IngestRecord.messageType()` 为 `reply`，原始消息照常落 `message` 表（为 L7 设备日志留痕），**不触发**设备在线状态刷新（`refreshDeviceStatus` 的 `default` 分支已天然跳过）；
- `IngestDispatcher.dispatch()` 增加**第四路** fan-out `commandReplyService.handle(events)`，逐条隔离异常、绝不冒泡（否则 worker 整批重试会导致消息重复落库）；
- 回执更新走**条件更新**（`WHERE command_id = ? AND status IN ('PENDING','SENT')`），返回受影响行数为 0 说明已是终态或记录不存在，按「重复回执 / 未知回执」计数忽略。

## 10. 接口设计

### 10.1 控制台（JWT，`/devices`）

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/devices/{deviceKey}/command-capability` | 返回可下发能力：`properties`（`rw` 属性及其 `dataType`）与 `services`（含 `inputData`），供前端生成动态表单；无物模型时两者为空并带 `modeled=false` |
| POST | `/devices/{deviceKey}/commands` | 下发命令，请求体见下；返回命令记录（同步为终态，异步为 `SENT`） |
| GET | `/devices/{deviceKey}/commands` | 命令记录分页，按 `created_at` 倒序 |

下发请求体：

```json
{
  "type": "property_set",
  "identifier": null,
  "params": { "targetTemp": 26 },
  "callType": "async"
}
```

- `type`：`property_set` / `service`（必填）；
- `identifier`：`service` 必填，`property_set` 必须为空；
- `params`：必填对象；
- `callType`：可选，默认 `async`；`sync` 即等待回执到终态再返回。

**下行统一 QoS 1、不保留**：QoS 0 不可靠、QoS 2 会带来重复投递，保留消息会在设备离线时残留旧命令 —— 三者都不适合命令语义，故不做成可选项（不引入无意义的旋钮）。

### 10.2 开放 API（API Key，`/external/v1`）

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/external/v1/devices/{deviceKey}/command` | 与控制台同语义，`source=OPEN_API` |
| GET | `/external/v1/devices/{deviceKey}/commands` | 命令记录分页 |

**破坏性变更说明**：原 `POST /external/v1/devices/{deviceKey}/command` 的请求体为 `{payload, qos, retain}`（原始字符串直发）。新契约为结构化命令（`type/identifier/params/callType`）。原契约因 ACL 冲突**本就不可用**，故直接替换而非并存，`SendCommandRequest` 随之删除；`scripts/api-test.ps1` 第 36 项用例同步改写。

### 10.3 错误码

| 码 | 含义 | HTTP |
|----|------|------|
| 6201 | 产品未定义物模型，无法下发命令 | 400 |
| 6202 | 属性不可写（`accessMode != rw`） | 400 |
| 6203 | 标识符未在物模型中定义 | 400 |
| 6204 | 参数不符合物模型定义 | 400 |
| 6205 | 命令记录不存在 | 404 |
| 4001 | 消息发送失败（MQTT 发布异常，复用） | 503 |
| 6004 / 6005 | 产品停用 / 设备禁用（复用） | 409 / 403 |

## 11. 前端设计

设备详情页（`views/workbench/device/DeviceDetail.vue`）新增两个区块，与既有「属性 / 事件」并列：

### 11.1 设备控制面板 `DeviceControlPanel.vue`

- **属性设置**：按 `command-capability` 的 `rw` 属性动态生成表单项（复用物模型编辑器的类型 → 控件映射：数值 → `el-input-number`、bool → `el-switch`、enum → `el-select`、text → `el-input`、date → `el-date-picker`、struct/array → JSON 文本域）；
- **服务调用**：下拉选择服务 → 按 `inputData` 动态生成入参表单（`required` 显示必填标记）；
- **调用方式**：同步 / 异步开关（默认异步）；同步时按钮显示等待态，返回终态后用 `el-message` 提示结果；
- **无物模型**：显示引导提示（去产品页定义物模型），禁用表单。

### 11.2 命令记录 `DeviceCommandHistory.vue`

- 分页表格：时间 / 类型 / 标识符 / 状态 / 耗时 / 结果；
- 状态用 `el-tag` 着色：`ACKED` 绿、`FAILED` 红、`TIMEOUT` 橙、`SENT` 蓝、`PENDING` 灰；
- 结果与参数支持 JSON 美化弹窗（复用设备事件面板的展示方式）；
- 下发成功后自动刷新列表（同步调用直接插入返回记录，避免额外请求）。

## 13. 安全与边界

1. **归属校验**：控制台按 `SecurityUtils` 的 `ownerId` 校验（ADMIN 可操作全部），开放 API 按 API Key 归属校验；越权返回 `2003`；
2. **准入校验**：设备 `enabled=0` 或产品非 `ENABLED` 时拒绝下发（复用 `DeviceAccessGuard`），避免对已封禁设备发命令；
3. **不可伪造**：设备无法发布 `cmd/` 前缀，故无法伪造下行；无法发布他人 `device/{otherKey}/reply`，故无法伪造他人回执（均由既有 ACL 保证）；
4. **参数大小**：`params` 序列化后超过 `max-params-bytes` 直接拒绝，防止超大载荷压垮 Broker；
5. **审计**：`source` + `operator_id` 记录下发来源，命令记录本身即审计日志（L7 设备日志将复用）；
6. **回滚**：`app.command` 无总开关（命令是显式用户动作，无需灰度）；如需停用可直接下线接口或依赖 ACL（`enforce-auth=true` 时未授权主题必被拒）。
