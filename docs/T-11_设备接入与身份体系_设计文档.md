# T-11 设备接入与身份体系（平台级）设计文档

> 版本：v1.0 ｜ 日期：2026-09-28 ｜ 状态：待评审
> 所属：第一阶段「设备接入与安全闭环」子项目 1（共 3 个：接入认证与 ACL / 命令 ACK 闭环 / 传输加密与 OTA）

---

## 1. 背景与目标

### 1.1 背景

当前平台的设备接入层存在三个层面的问题：

1. **无设备身份**：所有设备共用全局账号 `admin/public` 连接 Broker，平台无法区分设备、无法吊销单个设备。
2. **无访问边界**：Broker 未启用认证与 ACL，任何客户端可匿名连接并订阅任意主题（包括其他设备的数据）。
3. **无类型抽象**：设备类型仅以 `device.device_type` 字符串区分，接入方式、Topic 结构、认证方式全部硬编码在代码里。新增一种设备类型需要改代码。

### 1.2 目标

把「设备接入」从"给某类设备打补丁"升级为**平台能力**：

- 引入「产品（Product）」作为设备类型模板，新设备类型只需新增一条产品记录，无需改代码。
- 实现**一机一密**：每台设备独立凭据，可单独吊销。
- 实现**主题级 ACL**：设备只能访问自己命名空间下的主题。
- 前端实时数据不再直连 Broker，改由后端按用户权限过滤后推送。

### 1.3 成功标准

| 编号 | 标准 |
|------|------|
| S1 | 未注册设备、密码错误、已禁用设备连接被 Broker 拒绝 |
| S2 | 设备 A 无法 publish 或 subscribe 设备 B 的主题 |
| S3 | 前端监控页只能看到当前用户有权限的设备数据，且前端产物中不含任何 Broker 凭据 |
| S4 | 存量设备在迁移后可用新凭据正常接入，迁移期老固件不中断 |
| S5 | 新增一种设备类型仅需在平台创建产品，不需要改动后端代码 |

### 2.1 现有 Topic 约定（需兼容）

```
device/{deviceKey}/data       上行数据（QoS 1）
device/{deviceKey}/heartbeat  心跳（QoS 0）
device/{deviceKey}/lwt        遗言（QoS 1）
```

## 4. 总体设计

### 4.1 数据模型

#### 4.1.1 新表 `product`

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT PK | 主键 |
| `product_key` | VARCHAR(64) UNIQUE | 产品唯一标识，如 `esp32-fall-detect`，用于拼 Topic 与用户名 |
| `product_name` | VARCHAR(128) | 展示名 |
| `description` | VARCHAR(512) | 描述 |
| `auth_mode` | VARCHAR(32) | 认证方式，本期固定 `SECRET`；预留 `X509`、`JWT` |
| `topic_prefix` | VARCHAR(128) | Topic 命名模板，默认 `device/{deviceKey}` |
| `payload_format` | VARCHAR(16) | `JSON` / `RAW`，默认 `JSON` |
| `metadata_schema` | TEXT | 可选 JSON Schema，供前端动态表单；本期允许为空 |
| `status` | VARCHAR(16) | `ENABLED` / `DISABLED` |
| `created_at` / `updated_at` / `deleted` | | 审计与逻辑删除 |

#### 4.1.2 `device` 表改造

| 变更 | 说明 |
|------|------|
| `+ product_id` BIGINT NOT NULL | 归属产品 |
| `+ device_secret_hash` VARCHAR(100) | BCrypt 哈希，不可逆 |
| `+ secret_updated_at` DATETIME | 密钥重置时间 |
| `+ enabled` TINYINT NOT NULL DEFAULT 1 | **连接许可**，与运行态 `status`(ONLINE/OFFLINE) 语义分离 |
| 唯一键收敛 | 由 `device_key` 全局唯一改为 `(product_id, device_key)` 唯一 |

**语义澄清（避免歧义）**：

- `enabled` = 平台是否允许该设备连接（管理动作）
- `status` = 设备当前是否在线（运行时状态，由心跳/遗言驱动）
- 二者独立：`enabled=0` 的设备即使曾经在线，也应被拒绝连接并置为 `OFFLINE`

#### 4.1.3 凭据规则

- `device_secret`：32 位随机串（base62），明文**仅在「创建设备」与「重置密钥」响应中返回一次**
- 数据库只存 BCrypt 哈希，任何查询接口不回显
- 用户名格式：`{productKey}.{deviceKey}`（如 `esp32-fall-detect.sensor-01`）
- 密码格式：`device_secret` 明文（由设备侧持有，传输层由 TLS 保护——见子项目 3）

### 4.2 认证与授权（EMQX HTTP 回调）

#### 4.2.1 后端内部接口

| 接口 | 用途 |
|------|------|
| `POST /internal/emqx/auth` | EMQX 认证回调，校验 username/password |
| `POST /internal/emqx/acl` | EMQX 授权回调，判断 publish/subscribe 是否放行 |

**安全约束**：

- 必须携带请求头 `X-Internal-Token`，值取自配置 `app.access-control.internal-token`
- `SecurityConfig` 中 `/internal/**` 不参与 JWT 鉴权，但由独立过滤器校验 `X-Internal-Token`
- nginx 显式拒绝 `/internal/` 的外部访问，仅容器网络内可达

**响应约定**（EMQX 5 HTTP 回调格式）：

```json
// /auth 成功
{"result": "allow", "is_superuser": false}
// /auth 失败
{"result": "deny"}
// /acl
{"result": "allow"}  或  {"result": "deny"}
```

#### 4.2.2 兼容开关

| 配置项 | 默认 | 作用 |
|--------|------|------|
| `app.access-control.enforce-auth` | `true` | `false` 时 `/auth` 与 `/acl` 一律返回 `allow`，用于迁移期双轨运行 |
| `app.access-control.internal-token` | 必填 | 内部接口共享令牌 |

> 灰度流程：先在测试环境以 `enforce-auth=false` 打通链路 → 切 `true` 验证 → 生产刷机 → 生产切 `true`。

### 4.3 Topic 与 ACL 规则

#### 4.3.1 主题规划

沿用现有结构，避免破坏存量约定：

```
{product.topic_prefix}/data       上行数据
{product.topic_prefix}/heartbeat  心跳
{product.topic_prefix}/lwt        遗言
{product.topic_prefix}/cmd/#      下行命令（子项目 2 使用，本期仅建 ACL）
```

默认 `topic_prefix = device/{deviceKey}`，与现有 `device/{deviceKey}/data` 完全一致。

#### 4.3.2 ACL 规则表

| 身份 | publish | subscribe |
|------|---------|-----------|
| 设备（`{productKey}.{deviceKey}`） | `device/{deviceKey}/#` | `device/{deviceKey}/cmd/#` |
| 平台后端账号 | `device/+/cmd/#` | `device/+/#` |
| 前端受限账号（仅迁移期） | 无 | `device/+/data` |

ACL 判断在 `/internal/emqx/acl` 中实现：从 username 解析出 productKey/deviceKey，按上表匹配 `topic` 与 `action`。

### 4.4 后端实时通道（SSE）

#### 4.4.1 选型

采用 **SSE**（`text/event-stream`）而非 WebSocket：

- Spring MVC 原生支持 `SseEmitter`，无需新增依赖
- 单向推送，与"设备数据展示"场景完全匹配
- 前端使用 `fetch` + `ReadableStream` 解析，**携带 `Authorization` 头**，避免 token 进入 URL 与访问日志（不使用 `EventSource`，因其不支持自定义请求头）

#### 4.4.2 接口

```
GET /api/realtime/stream
```

- 鉴权：复用现有 JWT
- 过滤：ADMIN 可见全部设备；其他角色仅可见 `owner_id = 当前用户` 的设备
- 事件格式：

```json
{"deviceId": 1, "deviceKey": "sensor-01", "topic": "device/sensor-01/data", "payload": "...", "ts": "2026-09-28 10:00:00"}
```

#### 4.4.3 数据流

```
设备 → EMQX → 后端 MQTT 订阅(MqttMessageHandler)
                     ├→ 落库（现有逻辑不变）
                     └→ 按用户权限过滤 → SSE 推送到已订阅的浏览器
```

#### 4.4.4 迁移期开关

| 配置项 | 默认 | 作用 |
|--------|------|------|
| `app.realtime.direct-frontend-enabled` | `false` | `true` 时保留 EMQX 直连受限账号，供未升级的前端过渡 |

### 4.5 后端自身连接凭据

后端 Paho 客户端不再使用 `admin/public`，改为**平台级账号**，且同样走 HTTP 回调统一鉴权（避免出现两处配置源）：

- 用户名：固定为 `PLATFORM`（保留名；产品标识与设备标识的命名规则禁用该名称）
- 密码：取自配置 `app.access-control.platform-secret`
- `/internal/emqx/auth` 识别 `username=PLATFORM` 时比对 `platform-secret`，命中即视为平台身份
- `/internal/emqx/acl` 对平台身份放行：`subscribe device/+/#`、`publish device/+/cmd/#`
- 后端连接配置项沿用 `spring.mqtt.username/password`，取值改为上述两项

### 4.6 EMQX 配置变更

- 开启 HTTP 认证（`authentication`）指向 `http://backend:8080/internal/emqx/auth`
- 开启 HTTP 授权（`authorization`，source = HTTP）指向 `http://backend:8080/internal/emqx/acl`
- 建议同时把镜像从 `emqx/emqx:5.0` 升级到仍在维护的 5.x 版本（5.0 已停止维护）；具体版本在实施时按官方当前稳定版确认，本项为可选优化，不阻塞主线

## 5. 存量设备迁移方案

前提：现场已有运行中的设备，且固件可控（可重新烧录）。

| 步骤 | 动作 | 回滚方式 |
|------|------|---------|
| 1 | 建 `product` 表与「默认产品」（`product_key = legacy`），存量设备全部归入 | 删除产品记录 |
| 2 | 为存量设备批量生成 `device_secret`（哈希入库），导出一次性明文清单（CSV，下载后不落库） | 重新生成 |
| 3 | EMQX 开启认证/授权，`enforce-auth=false` → 全链路验证，老固件仍可连 | 关闭认证 |
| 4 | 后端切平台凭据；前端切 SSE 实时通道 | 开 `direct-frontend-enabled=true` |
| 5 | 测试环境置 `enforce-auth=true` 验证拒绝逻辑 | 置回 `false` |
| 6 | 生产刷机写入新凭据 → 置 `enforce-auth=true` → 关闭直连开关 | 临时置回 `false` |

**新增管理能力**：

- `POST /api/devices/{id}/reset-secret` — 重置单设备密钥（返回一次明文）
- `POST /api/devices/export-credentials` — 批量导出凭据清单（一次性，ADMIN）

## 8. 风险与取舍

| 风险 | 影响 | 应对 |
|------|------|------|
| EMQX 回调成为连接关键路径 | 后端不可用时设备无法连接 | 后端本地缓存认证结果 + EMQX 侧认证缓存；回调接口保持轻量（单表查询） |
| 存量设备刷机窗口 | 切换强制认证后老设备掉线 | 双轨开关 + 分环境灰度，先测试后生产 |
| 前端 SSE 连接数 | 每用户一条长连接 | 单实例可接受；后续水平扩展时随子项目「架构重构」一并处理 |
| `device_key` 唯一性收敛 | 存量数据可能存在跨产品重名 | 迁移脚本中先校验重名，冲突则中止并报告 |
| Flyway 基线对齐 | 现有库与脚本可能不一致 | 先以实际库导出结构作为 `V1__baseline.sql`，再叠加 `V2` |
