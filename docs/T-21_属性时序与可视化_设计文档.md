## 1. 背景与目标

T-14 已把上行属性按物模型归一化落进 `device_property_latest`，但该表**每个 `(device_id, identifier)` 只保留最新一条**（建表语句里已注明「时序数据归 T-21」）。因此当前平台**只能回答「现在是多少」，无法回答「过去怎么变的」**：

- 设备详情页的属性面板只显示**当前值**，看不到历史曲线；
- 无法回答「过去 7 天温度怎么走的」「某属性何时越界」这类问题；
- 路线图 §2 能力域 10「属性趋势、聚合（min/max/avg）、看板」现状为「仅消息量趋势（`/analytics/messages/trend`）」，缺口明确写着「**缺属性级时序**」；
- 既有的 `/analytics/messages/trend` 只是**按天统计报文条数**，既不是属性级、也不支持任意时间桶。

本任务引入**属性级时序存储 + 聚合查询 + 可视化**：上行属性在解析链路旁路**追加**写入历史表，按时间桶聚合出 `count / min / max / avg` 序列，前端在设备详情呈现单属性趋势图，并提供可保存的多属性 / 多设备看板。

目标：

1. **属性历史落库**：新增 `device_property_history`（**只加表**，追加写），保留每次上报的原始值与时序，作为属性回看与聚合的唯一事实源。
2. **聚合查询**：提供按时间桶的聚合接口，返回 `count / min / max / avg`；数值型（`int` / `float` / `double`）返回完整聚合，非数值型（`bool` / `enum` / `text` 等）**仅返回 `count`**（`min/max/avg` 置 `null`）。
3. **前端趋势图**：设备详情页新增「属性趋势」区块，选属性 + 选时间范围 + 选粒度即可看曲线。
4. **可保存看板**：新增独立看板页，可把「多设备 × 多属性 × 各自时间范围 / 粒度」的自由组合保存为看板，随时复现。
5. **零破坏、可安全回滚**：摄取写入以 **try/catch 隔离旁路**接入（与影子 / 告警 / 规则并列的第 4 条旁路），不改 MQTT 主题 / ACL、不改既有写入路径语义；回滚只需摘除新增端点与页面、可选删除两张新表。
6. **与 R5 门槛联动**：保留清理策略可配置（开关 / 间隔 / 保留天数 / 批量），并按路线图 §6 要求把「属性历史数据量」纳入 `scripts/r5-trigger-check.*` 的复核项。

## 3. 术语

| 术语 | 含义 |
| --- | --- |
| 属性历史（Property History） | `device_property_history` 中的一行，即某设备某属性在 `reported_at` 时刻的一次上报值 |
| 时间桶（Bucket） | 聚合的时间粒度，如 `5m` / `1h` / `1d`；一个桶聚合成一个数据点 |
| 聚合函数（Aggregation） | `count`（样本数）/ `min` / `max` / `avg`；仅数值型支持后三者 |
| 可数值聚合类型 | 物模型数据类型中仅 `int` / `float` / `double` 可参与 `min/max/avg`；`bool` / `enum` / `text` / `date` / `struct` / `array` 仅 `count` |
| 序列（Series） | 一个 `(deviceId, identifier)` 在给定时间窗与桶粒度下的数据点集合 |
| 看板（Dashboard / Board） | 一组面板的**可保存**配置，归属于创建者 |
| 面板（Panel） | 看板中的一格：`deviceIds` + `identifier` + `bucket` + `rangeDays` + `chartType` + `aggregation` |
| 保留策略（Retention） | 属性历史的保留天数与后台清理批量口径，与 R5 门槛联动评审 |
| 旁路（Side-branch） | 解析链路中一处 `try/catch` 隔离的附加动作，异常只记 WARN、绝不上抛、不影响本批其余消息 |

## 4. 主题方案

### 4.1 新建属性历史表、摄取旁路追加写

- **只加表**：`V10` 新建 `device_property_history` 与 `dashboard` 两张表，**不改任何既有列、不改既有索引**，应用版本可安全回滚。
- **零语义变更**：既有 `device_property_latest`（最新值）、`device_event_record`、`message` 等写入路径**语义不变**；历史写入是**纯追加的旁路**。
- **不动 MQTT**：不新增主题、不改 ACL，`emqx-init` 零改动。

### 4.2 权限与隔离

- 聚合接口取当前用户 `SecurityUtils.requireUserId()`；对请求中的**每一个** `deviceId` 做设备级校验：
  - 设备不存在（含已删除）→ `DEVICE_NOT_FOUND(2002)`；
  - 设备存在但 `owner_id != 当前用户` → `DEVICE_NOT_OWNED(2003)`（`HttpStatus.FORBIDDEN`，沿用既有语义，**不新增同义码**）。
- SQL 天然被限定在「本用户请求的这几台设备」内，因此**不需要**再对每行做 `owner_id` 关联过滤。
- **看板隔离**：`dashboard.user_id` 必须等于当前用户；`GET/PUT/DELETE /dashboards/{id}` 命中非本人看板一律按 `DASHBOARD_NOT_FOUND(6228)` 返回（**不泄露他人看板是否存在**）；`GET /dashboards` 的 `user_id` 由服务端注入，**不接受客户端传入**。
- **标识符白名单**：`identifiers` 必须存在于请求设备的物模型中（经 `ThingModelService.getForProduct` 取定义校验），否则 `PROPERTY_HISTORY_IDENTIFIER_UNSUPPORTED(6226)`。
- 需复核：`device_property_history.device_id` 为 `ON DELETE CASCADE`，设备删除后其历史一并消失（与 `device_event_record` / `device_status_history` 一致）。

### 4.3 为什么是「新建 `device_property_history`」，而不是「复用 `message` + 物模型解析」

| 维度 | 新建 `device_property_history`（**选定**） | 复用 `message` + 解析（未选） |
| --- | --- | --- |
| 数据模型 | 一行一个属性样本，`(device_id, identifier, reported_at)` 直出，聚合 SQL 简单 | 一行一条报文，需在 SQL 侧 `JSON_EXTRACT` 拆 `params`，无法索引到属性级 |
| 聚合性能 | `(device_id, identifier, reported_at)` 复合索引直接走范围扫描 | 全表扫报文 + 运行时 JSON 解析，属性级过滤无法走索引 |
| 与既有能力的关系 | `device_property_latest` 的注释本就预留「时序数据归 T-21」 | 报文保留策略（`message` 的 TTL / 分区）与属性保留策略**互相绑架** |
| 保留策略 | 可**独立**设保留天数与清理批量（L8 验收要求与 R5 联动） | 清理属性历史就等于删报文，影响实时消息页与历史数据页 |
| 类型信息 | 落库即带 `data_type`，聚合时按类型判定是否数值聚合 | 类型需运行时回查物模型，且物模型可能已变更 |
| 迁移/回滚 | 只加表，回滚删表即可 | 无迁移，但「解析逻辑」改动会波及既有查询端点的语义 |
| 写入代价 | 每属性样本一次批量 `INSERT`（可合并进既有事件批量写之后） | 零额外写入，但查询侧持续付代价 |

结论：本任务取**新建属性历史表**。写入侧代价可控（与既有事件批量写同批），查询侧可走索引，且保留策略独立、可与 R5 门槛单独联动评审——与路线图「属性历史表（**或**复用 `message` + 物模型解析）」的二选一中，前者在**性能 / 保留策略独立性 / 回滚安全**三项上全面占优。

### 4.4 写入路径：第 4 条旁路（与影子 / 告警 / 规则并列）

`ThingModelInterpretServiceImpl` 的类头注释已写明：**本类不开启事务**，逐条隔离，单条异常只记 WARN 与 `error` 指标、不上抛、不中断本批、不进死信。属性历史的写入**必须遵循同一纪律**，作为 `interpretProperties` 内的**第 4 条旁路**（前三条第 1 条是 T-16 的 `applyReported`，第 2 条是 T-17 的 `evaluateProperties`，第 3 条是 T-19 的 `evaluateRules`）：

```java
private void interpretProperties(Device device, ThingModelDefinition definition,
                                 JsonNode root, IngestRecord record) {
    ...
    List<PropertyHistoryService.Sample> historySamples = new ArrayList<>();
    for (Map.Entry<String, JsonNode> entry : params.properties()) {
        String identifier = entry.getKey();
        ThingModelDefinition.PropertySpec spec = definition.properties().get(identifier);
        if (spec == null) { metrics.count(RESULT_UNKNOWN_IDENTIFIER); continue; }
        String valueText = ThingModelParamValidator.normalize(spec, entry.getValue());
        if (valueText == null) { metrics.count(RESULT_UNKNOWN_IDENTIFIER); continue; }
        propertyLatestMapper.upsertIfNewer(device.getId(), identifier, spec.type(), valueText,
                record.receivedAt());
        // T-21：同一份归一化样本追加进历史列表，循环结束后批量落库（不额外解析）。
        historySamples.add(new PropertyHistoryService.Sample(identifier, spec.type(), valueText,
                record.receivedAt()));
        metrics.count(RESULT_PROPERTY);
        applied.add(identifier);
        samples.add(new AlertEvaluationService.PropertySample(identifier, valueText, record.receivedAt()));
        ruleSamples.add(new RuleEvaluationService.PropertySample(identifier, valueText, record.receivedAt()));
    }
    // T-16：上报收敛。回读权威库合并进影子 reported，异常只记 WARN。
    applyReported(device, applied);
    // T-17：阈值告警旁路，复用已归一化的属性样本。
    evaluateProperties(device, samples);
    // T-19：消息规则旁路。
    evaluateRules(device, ruleSamples);
    // T-21：属性历史旁路，复用同一份归一化样本，批量追加。
    appendHistory(device, historySamples);
}

/** 属性历史旁路（T-21 设计文档 §4.4）；异常只记 WARN，不冒泡到解析链路。 */
private void appendHistory(Device device, List<PropertyHistoryService.Sample> samples) {
    if (samples.isEmpty()) return;
    try {
        propertyHistoryService.append(device.getId(), samples);
    } catch (Exception e) {
        log.warn("属性历史写入失败，跳过本批 {} 条: deviceId={}", samples.size(), device.getId(), e);
    }
}
```

要点：

- **复用同一份归一化样本**：`valueText` / `dataType` / `reportedAt` 全部取自循环内已有变量，**不重复解析、不额外查询物模型**。
- **批量落库**：与 T-14 `flushEvents` 的 `insertBatch` 同款；`append` 内部单次 `INSERT ... VALUES (...),(...)`。
- **顺序**：放在 `evaluateRules` 之后，保证即便前序旁路异常（已各自吞掉）历史仍会写入；历史写入异常也**不影响**前三者。
- **总开关**：`app.property-history.enabled=false` 时 `append` 直接短路返回（用于压测 / 极端降级），无异常。

### 4.5 乱序旧包与「末值」口径

- **历史表是追加而非覆盖**：与 `device_property_latest.upsertIfNewer` 的**时间戳守卫语义不同**，历史表**不加守卫**——乱序到达的旧包**照常落库**（时序保真，保留设备真实的上报顺序信息）。
- 乱序的影响被限制在**展示层**：聚合按 `reported_at` 分桶，同一桶内的乱序样本先聚合后展示，对 `min/max/avg/count` 无影响；若未来需要「末值」，需按 `reported_at DESC, id DESC` 取（本任务不做，见 §2.2）。
- 「当前值」的权威来源仍是 `device_property_latest`（有守卫），**不复用历史表推导当前值**，避免两套口径。

### 4.6 看板为什么单独建表

- 看板是**用户配置**而非设备数据，生命周期与设备无关（设备删了看板可能还在，只是面板空数据），**不能**挂在 `device` / `product` 上。
- 配置是**自由结构**（面板数组、每个面板各自的设备集合与粒度），用 JSON 列承载比关系化拆表更贴合，且改动不触发迁移。
- 归属**使用者**：`user_id` 外键指向 `sys_user`，`ON DELETE CASCADE`。
- 数量上限由配置约束（`app.dashboard.max-count`），避免滥用。

## 5. 数据模型

### 5.1 `device_property_history`（V10）

列风格与索引风格沿用 `V4__thing_model.sql` 的 `device_property_latest`（`DATETIME(3)`、`value_text TEXT`、`ON DELETE CASCADE`）：

```sql
-- 设备属性历史（追加写，时序数据，T-21）
-- 说明：只加表，不改既有列；无逻辑删除字段（历史由保留巡检按 reported_at 硬删除）。
CREATE TABLE IF NOT EXISTS device_property_history (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    device_id BIGINT NOT NULL COMMENT '设备ID',
    identifier VARCHAR(64) NOT NULL COMMENT '属性标识符',
    data_type VARCHAR(16) NOT NULL COMMENT '数据类型（落库时的物模型定义）',
    value_text TEXT COMMENT '属性值（统一文本存储，按 data_type 解释）',
    reported_at DATETIME(3) NOT NULL COMMENT '设备上报时间（毫秒精度）',
    created_at DATETIME(3) DEFAULT CURRENT_TIMESTAMP(3) COMMENT '入库时间',
    INDEX idx_device_identifier_time (device_id, identifier, reported_at),
    INDEX idx_reported_at (reported_at),
    CONSTRAINT fk_prop_history_device FOREIGN KEY (device_id) REFERENCES device(id) ON DELETE CASCADE
) COMMENT='设备属性历史（追加写，时序数据）';
```

- `idx_device_identifier_time`：聚合查询的主索引（设备 + 属性 + 时间范围）；
- `idx_reported_at`：保留清理 `DELETE ... WHERE reported_at < ?` 的扫描索引；
- **无 `UNIQUE`**：同一 `(device_id, identifier, reported_at)` 允许重复（设备可能瞬时重复上报），历史不做去重。

### 5.2 `dashboard`（V10）

```sql
-- 可保存看板（T-21）：看板配置为 JSON，归属创建者
CREATE TABLE IF NOT EXISTS dashboard (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    user_id BIGINT NOT NULL COMMENT '创建者（sys_user.id）',
    name VARCHAR(64) NOT NULL COMMENT '看板名称',
    config JSON NOT NULL COMMENT '看板配置（面板数组，见 §5.3）',
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    INDEX idx_user (user_id),
    CONSTRAINT fk_dashboard_user FOREIGN KEY (user_id) REFERENCES sys_user(id) ON DELETE CASCADE
) COMMENT='可保存看板';
```

`config` 结构（JSON）：

```json
{
  "panels": [
    {
      "title": "1# 温室温度",
      "deviceIds": [1, 2],
      "identifier": "temperature",
      "bucket": "5m",
      "rangeDays": 1,
      "chartType": "line",
      "aggregation": "avg"
    }
  ]
}
```

### 5.3 实体与字段命名

- `entity/DevicePropertyHistory.java`：`@TableName("device_property_history")`，字段 `deviceId / identifier / dataType / valueText / reportedAt / createdAt`，**不含** `deleted`（表无该列，故不受 `logic-delete-field: deleted` 影响；既有 `DevicePropertyLatest` 同为无 `deleted` 实体的先例）。
- `entity/Dashboard.java`：`@TableName("dashboard")`，`config` 用 `String` 承载原始 JSON（读写时由服务层用 `ObjectMapper` 解析为 `DashboardConfig`，避免实体耦合 Jackson 注解）。

### 5.4 保留清理口径

- 单条 SQL：`DELETE FROM device_property_history WHERE reported_at < #{threshold} LIMIT #{batchSize}`（分批循环，直到影响行数 < `batchSize` 或达到单轮上限）。
- 阈值 = `now - retention-days`；`batchSize` 用于避免长事务 / 大范围锁。
- 保留天数默认 **30 天**，与 `app.rule.execution-retention-days` 的既有先例一致；该值即 R5 门槛复核时的输入参数。

## 6. 接口设计

### 6.1 属性序列聚合查询

`GET /properties/history`

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `deviceIds` | string（逗号分隔 Long） | 是 | 1~N 台设备，逐一做归属校验 |
| `identifiers` | string（逗号分隔） | 是 | 1~N 个属性标识符，逐一做物模型校验 |
| `startTime` | string `yyyy-MM-dd HH:mm:ss` | 是 | 起始（含） |
| `endTime` | string `yyyy-MM-dd HH:mm:ss` | 是 | 结束（**不含**，半开区间） |
| `bucket` | string | 是 | 时间桶，白名单：`1m` / `5m` / `15m` / `30m` / `1h` / `6h` / `1d` |

### 7.2 聚合 SQL 设计（`DevicePropertyHistoryMapper.xml`）

分桶与聚合一次完成（**不用** `GROUP_CONCAT`，见 §2.2）：

```xml
<select id="aggregateByBucket" resultType="com.mqtt.cloud.dto.response.PropertyHistoryAggregate">
  SELECT
    h.device_id AS deviceId,
    h.identifier AS identifier,
    FROM_UNIXTIME(FLOOR(UNIX_TIMESTAMP(h.reported_at) / #{bucketSeconds}) * #{bucketSeconds}) AS time,
    COUNT(*) AS sampleCount,
    <choose>
      <when test="numeric">
        MIN(CAST(h.value_text AS DECIMAL(30,10))) AS minValue,
        MAX(CAST(h.value_text AS DECIMAL(30,10))) AS maxValue,
        AVG(CAST(h.value_text AS DECIMAL(30,10))) AS avgValue
      </when>
      <otherwise>
        NULL AS minValue, NULL AS maxValue, NULL AS avgValue
      </otherwise>
    </choose>
  FROM device_property_history h
  WHERE h.reported_at &gt;= #{startTime}
    AND h.reported_at &lt; #{endTime}
    AND h.device_id IN
    <foreach collection="deviceIds" item="id" open="(" separator="," close=")">#{id}</foreach>
    AND h.identifier IN
    <foreach collection="identifiers" item="it" open="(" separator="," close=")">#{it}</foreach>
  GROUP BY h.device_id, h.identifier, time
  ORDER BY h.device_id ASC, h.identifier ASC, time ASC
</select>
```

要点：

- **列别名与投影字段一一对应**：SQL 用 `sampleCount` / `minValue` / `maxValue` / `avgValue`（**避开** `count` / `min` / `max` / `avg` 这些 SQL 保留函数名做别名），`resultType` 指向投影 `PropertyHistoryAggregate`；服务层再把 `sampleCount→count`、`minValue→min`、`maxValue→max`、`avgValue→avg` 映射进对外 VO `PropertyHistoryPoint`（§6.1）。**投影与对外模型分离**，避免把 SQL 层命名泄露到接口契约。

- **数值与非数值分流**：是否生成 `min/max/avg` 由服务层按物模型 `PropertySpec.type` 判定后以 `numeric` 传入（`<choose>` 控制列生成），**非数值类型不产生误导性的 `CAST` 结果**，也避免对文本列做无谓计算（见 §4.4 类型口径）。
- **只会走 `idx_device_identifier_time`**：`device_id IN (...) AND identifier IN (...) AND reported_at` 范围，均为索引前导列组合。
- **无需 `countQuery`**：本查询是聚合（分组）结果，**不分页**，因此不涉及 T-20 里 UNION 场景下 MP 自动 count 不可靠的问题。
- **`bucketSeconds` 由服务层从白名单映射而来**（`1m→60`、`5m→300`、`15m→900`、`30m→1800`、`1h→3600`、`6h→21600`、`1d→86400`），SQL 内不做字符串解析。
- 其余两个方法：`insertBatch`（`INSERT INTO ... VALUES (...),(...)`）与 `purgeBefore`（`DELETE ... WHERE reported_at < #{threshold} LIMIT #{batchSize}`）为纯 XML 语句。

> 关于注解式 SQL：本 Mapper 的查询语句**统一放 XML**（与既有 `MessageMapper` / `DeviceLogMapper` 一致）。若未来改为注解式，务必注意仓库既有注释——`<script>` 前缀判定与 `&gt;` / `&lt;` 转义。

### 7.3 服务层流程（`PropertyHistoryServiceImpl`）

**写入 `append(deviceId, samples)`：**

1. 若 `app.property-history.enabled=false` → 直接返回；
2. 组装行（`deviceId` / `identifier` / `dataType` / `valueText` / `reportedAt`）；
3. `insertBatch(rows)`；异常由调用方（`appendHistory`）的 `try/catch` 兜底。

**查询 `query(dto)`：**

1. `requireUserId()` 由 Controller 传入；
2. **设备归属校验**：逐 `deviceId` `selectById` → 空 = `2002`；`owner_id != userId` → `2003`；
3. **标识符校验**：按各设备的 `productId` 经 `ThingModelService.getForProduct(productId)` 取定义；`identifiers` 中存在未建模者 → `6226`；同时记录每个标识符的 `type` 与是否 `numeric`；
4. **参数归一化**：`startTime` / `endTime` 解析（非法格式 → `6225`）、跨度校验（> `max-range-days` → `6225`）、`bucket` 白名单（非法 → `6227`）、序列数（> `max-series` → `6225`）、桶数（> `max-points` → `6227`）；
5. **按 `numeric` 分组调用 `aggregateByBucket`**（数值型与非数值型各一次，避免 `<choose>` 在同一 SQL 内难以兼容混合类型）；若 `identifiers` 全为同一类型则只调用一次；
6. **组装序列**：把 `PropertyHistoryAggregate` 行投影按 `(deviceId, identifier)` 分组、按 `time ASC` 排序，逐行映射为 `PropertyHistoryPoint`（`sampleCount→count` 等）后填入 `points`；未出现在结果中的组合补 `points: []`；
7. 返回 `List<PropertySeriesVO>`。

> 第 5 步的类型分流：一次请求内 `identifiers` 可能混合数值/非数值（看板面板通常单一属性，但接口允许混用）。实现上按 `numeric` 拆成两次 Mapper 调用，结果合并；若混合则两次都查、否则一次。

### 7.4 为什么不复用 `device_property_latest` 的 Mapper

`DevicePropertyLatestMapper` 只有 `upsertIfNewer`（时间戳守卫的覆盖写）与 `selectByIdentifiers`（取最新值）——**它根本不保留历史**，没有可聚合的多行。属性趋势需要同一 `(device, identifier)` 的**多时刻样本**，与「只留最新一条」的语义正交。因此新增独立的 `DevicePropertyHistoryMapper`，`DevicePropertyLatestMapper` **零改动**。

    cleanup-enabled: ${PROPERTY_HISTORY_CLEANUP_ENABLED:true}      # 是否启用过期历史清理

## 12. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 属性历史表**写入放大**（每属性样本一行），长期体量增长 | 存储膨胀、聚合变慢 | 保留清理巡检（默认 30 天）+ `enabled` 开关可整体关闭 + 批量删；按路线图 §6 与 `scripts/r5-trigger-check.*` 联动复核，必要时触发 R5 改造评估 |
| 非数值文本被 `CAST AS DECIMAL` 参与聚合 | 误导性 `min/max/avg` | 服务层按物模型类型判定 `numeric`，非数值型以 `<otherwise>` 输出 `NULL`，前端只画 `count` |
| 物模型在历史周期内**被修改**（属性类型变更 / 删除） | 同一标识符历史类型不一致 | `data_type` **落库时快照**（历史行自带类型），聚合以当前物模型类型判定 `numeric`；类型变更后仍可 `count`，数值聚合以当前定义为准（可接受，风险记录在案） |
| 乱序 / 重复上报 | 序列出现尖刺 | 历史追加不去重（时序保真）；聚合按 `reported_at` 分桶天然平滑；「当前值」仍以有守卫的 `device_property_latest` 为准 |
| 大时间窗 + 小桶 → 数据点爆炸 | 响应体过大、前端卡顿 | `max-points` 上限校验（超限 → `6227`）+ `max-range-days` 上限 + 前端粒度下拉默认随范围联动 |
| 看板 `config` 为客户端 JSON | 注入 / 脏配置 | 服务层解析为强类型 `DashboardConfig` 并逐字段白名单校验（`bucket` / `chartType` / `aggregation` / 数量），非法 → `6229`；落库为 JSON（MyBatis `#{}` 参数化，无拼接） |
| 看板越权访问 | 信息泄露 | `user_id` 服务端注入 + 非本人一律 `6228`（不区分「不存在」与「无权限」） |
| 巡检删除与查询并发 | 偶发查询范围被裁剪 | 清理按 `reported_at < 阈值` 且分批 + 索引 `idx_reported_at`；属既有 TTL 同类行为，可接受 |
| `FLOOR(UNIX_TIMESTAMP(...)/?)` 时区口径 | 桶对齐偏差 | 与既有 `DATE(sent_at)` / `DATE_SUB(NOW(), ...)` 的库时区口径一致（沿用 `application.yml` 连接时区设置），不引入应用层时区换算 |
