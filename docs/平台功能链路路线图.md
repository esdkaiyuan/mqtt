# 平台功能链路路线图

> 版本：v1.2　创建日期：2026-10-02　状态：进行中（L1 / T-14、L2 / T-15 已交付）
> 定位：对标主流 IoT/MQTT 平台的能力域，把「还差什么」拆成可逐项交付的**功能链路**，作为 T-14 及后续子任务的排期依据。

---

## 1. 目的与对标基线

本平台已完成「产品 / 一机一密 / 上行摄取 / 历史查询 / SSE 实时 / 开放 API / Webhook」这条**通信与接入**主线（T-01 ~ T-13），但在「设备建模 → 数据语义化 → 云端控制 → 状态同步 → 业务编排」这条**平台能力**主线上基本空白，这正是与真正商用平台的差距所在。

对标对象与取用重点：

| 平台 | 取用重点 |
|------|----------|
| **ThingsCloud** | 主基线。产品/设备模型、消息规则（属性上报 → 更新云端属性 / 下发命令 / 转发外部 MQTT 与 URL）、零代码自动化 [$TRAE_REF](https://www.thingscloud.xyz/docs/guide/rules/overview.html)[$TRAE_REF](https://www.thingscloud.xyz/docs/guide/rules/attrs-rpt.html) |
| **阿里云 IoT 平台** | 物模型 TSL（属性 / 事件 / 服务）、Alink JSON 上下行格式、设备影子（desired/reported）、服务调用记录查询 [$TRAE_REF](https://help.aliyun.com/zh/iot/developer-reference/list-of-operations-by-function)[$TRAE_REF](https://help.aliyun.com/en/iot/user-guide/device-properties-events-and-services) |
| **ThingsBoard** | 规则引擎（Rule Chain：过滤 / 变换 / 路由 / 动作）、RPC 下行 [$TRAE_REF](https://thingsboard.io/docs/paas/eu/user-guide/rule-engine/) |

**交付原则**：每条功能链路必须**端到端可用**（数据模型 + 后端接口 + 前端页面 + 测试 + 文档），不做只有后端没有入口的半成品；顺序上沿用既有约定「先补齐功能缺口，再动底层架构」。

## 3. 功能链路清单（逐项）

每条链路标注：**目标 / 范围 / 依赖 / 验收口径**。

### 一期：设备建模与控制主线（P0）

#### L1 · 物模型与数据解析（T-14）— ✅ 已交付
- **目标**：产品拥有结构化设备模型（TSL：属性 / 事件 / 服务），上行数据按模型解析为有语义的属性值与事件记录。
- **范围**：TSL 数据结构与校验规则；`product` 物模型字段与版本；物模型 CRUD + 导入 / 导出接口；前端物模型编辑器；上行 Alink JSON 解析 → 属性最新值表 + 事件记录表；非 Alink 载荷兼容直存。
- **依赖**：无（基础链路）。
- **验收**：为产品定义物模型后，设备按 Alink JSON 上报属性，`device_property_latest` 与 `device_event_record` 正确落库；非法载荷 / 未定义标识符有明确处置且不丢消息；前端可增删改查并导入导出 TSL。
- **交付（2026-10-02）**：迁移 `V4__thing_model.sql`（产品三列 + 两张派生表）；`ThingModelValidator`（V1~V16 规则）与进程内缓存（TTL + 主动失效）；`ProductController` 物模型六端点；上行解析作为 `IngestDispatcher` 落库后**第三路旁路**（逐条隔离失败、不进死信）；只读查询接口（属性最新值 / 事件分页）；前端产品管理页 + 物模型编辑器（递归类型编辑 / 导入导出 / 脏确认）与设备详情属性 / 事件区块。门禁：后端 `mvn -B verify` 全绿、前端 `lint` 0 error / `test` 106 全绿 / `build` 通过。

#### L2 · 命令下发与服务调用（T-15）— ✅ 已交付
- **目标**：云端可对设备下发属性设置与服务调用，全链路可追踪（记录 + 回执）。
- **范围**：**修正命令主题与 ACL 冲突**（`device/{deviceKey}/command` → 含 `/cmd/` 的主题）；命令 / 服务记录表；参数按物模型校验；同步（等待回执，超时失败）与异步两种调用方式；设备回执主题接入；前端「设备控制」面板与命令记录列表；开放 API 同步对齐。
- **依赖**：L1（服务入参 / 出参定义、属性 set 目标）。
- **验收**：控制台下发命令后设备收到且可回执，记录状态从 `PENDING → SENT → ACKED/FAILED/TIMEOUT` 正确流转；非 `cmd/` 主题不再产生 ACL 拒绝；越权调用返回明确错误码。
- **交付（2026-10-02）**：下行主题修正为 `device/{deviceKey}/cmd/down`、回执主题 `device/{deviceKey}/reply`（**ACL 规则与授权回调一行未改**，仅修正主题即修复「下发必被拒」存量缺陷）；迁移 `V5__device_command.sql`（`device_command_record` + 状态机，条件更新保证终态不可覆盖）；`ThingModelParamValidator` 上下行共用同一套 `dataType` 校验；同步调用用**轮询本表**而非进程内 `Future`（多副本下回执可能落到其他副本），配 `CommandTimeoutSweeper` 定时巡检兜底异步超时；回执以共享订阅 `$share/{group}/device/+/reply` 接入摄取**第四路旁路**更新状态；控制台三端点（能力查询 / 下发 / 记录分页）+ 开放 API 新契约（删除 `SendCommandRequest`）；前端设备控制面板（属性设置 / 服务调用动态表单 + 同步异步）与命令记录列表（分页 / 状态着色 / JSON 详情）。门禁：后端 `mvn -B verify` 220 全绿、前端 `lint` 0 error / `test` 131 全绿 / `build` 通过。

#### L3 · 设备影子（拟 T-16）
- **目标**：以 desired / reported / delta 三份状态描述设备，支持离线命令缓存与重连补发。
- **范围**：`device_shadow` 表与版本号；属性上报自动更新 reported；属性设置写入 desired；delta 计算与查询；设备离线时命令入 desired，上线后补发；前端设备详情影子视图。
- **依赖**：L1（属性标识符）、L2（命令通道）。
- **验收**：设备离线时下发期望值不丢失，设备上线后收到并上报，reported 收敛到 desired、delta 清空；影子版本号单调递增。

#### L4 · 告警中心（拟 T-17）
- **目标**：对属性阈值、设备离线、事件上报三类来源产出告警并通知。
- **范围**：告警规则（阈值 / 离线 / 事件）；告警记录表与状态流转（触发 / 恢复 / 确认）；通知出口复用 Webhook；前端告警规则配置与告警列表；顶栏通知中心接入（T-13 遗留占位）。
- **依赖**：L1（属性标识符）、L2（可选：告警联动下发命令）。
- **验收**：属性越限后产生告警记录并回调 Webhook；恢复正常自动置「已恢复」；重复告警按规则去重（抑制窗口）。

#### L5 · 设备分组与标签（拟 T-18）
- **目标**：设备可按分组树与标签组织，支持按分组 / 标签批量操作。
- **范围**：`device_group` 分组树 + `device_tag` 标签；设备与分组 / 标签关联；列表按分组 / 标签过滤；批量下发命令与批量禁用。
- **依赖**：L2（批量下发复用命令链路）。
- **验收**：分组树可增删改移动；按标签筛选结果正确；批量下发对分组内设备逐一生成命令记录。

### 二期：数据价值与运维（P1）

#### L6 · 消息规则 / 规则引擎（拟 T-19）
- **目标**：以可配置规则对上行数据做过滤、变换与转发，替代当前写死的 Webhook 逻辑。
- **范围**：规则模型（触发源 + 条件 + 动作）；动作至少覆盖「更新云端属性 / 下发命令 / 转发外部 MQTT / 转发 HTTP」；规则执行记录与失败重试；前端规则编排（先做表单式，暂不做可视化拖拽）。
- **依赖**：L1（数据语义）、L2（下发动作）。
- **验收**：配置「温度 > 阈值 → 转发 HTTP」后，真实上行触发且转发成功；规则动作失败不影响主摄取链路。

#### L7 · 设备日志与诊断（拟 T-20）
- **目标**：提供设备上下行全链路日志视图（含命令、事件、连接事件）。
- **范围**：统一日志查询接口（按设备 / 类型 / 时间过滤）；命令与事件记录接入；前端设备日志页（时间线视图）。
- **依赖**：L1、L2。
- **验收**：单设备一次命令下发可在日志中串起「下发 → 回执」两条记录。

#### L8 · 属性时序与可视化（拟 T-21）
- **目标**：属性级时序存储与聚合查询，支撑趋势图与看板。
- **范围**：属性历史表（或复用 `message` + 物模型解析）；聚合接口（min/max/avg/count，按时间桶）；前端属性趋势图与可保存看板。
- **依赖**：L1。
- **验收**：指定属性与时间范围返回正确聚合序列；数据量与保留策略与 R5 门槛联动评审。

### 三期：生态与扩展（P2）

#### L9 · OTA 固件升级（拟 T-22）
- **目标**：固件包管理、按产品 / 分组 / 标签批次升级、进度回传。
- **范围**：固件包表与对象存储 / 静态托管；升级任务与批次；进度与结果回传；前端固件与升级任务页。
- **依赖**：L5（按分组 / 标签下发）、L2（下发通道）。
- **验收**：创建升级任务后设备收到固件地址，进度可回传并在任务详情可见。

#### L10 · 自动化 / 场景联动（拟 T-23）
- **目标**：零代码配置「多设备联动」场景。
- **范围**：场景模型（触发 → 条件 → 动作流，含延时）；执行记录；前端场景编排。
- **依赖**：L2、L6。
- **验收**：配置「设备 A 上报某事件 → 延时 5s → 设备 B 下发命令」可自动执行。

#### L11 · 多协议接入（拟 T-24）
- **目标**：MQTT 之外的接入方式（HTTP 上报 / Modbus 网关）。
- **范围**：HTTP 上报端点与鉴权；边缘网关协议适配方案（评估后定）；统一入摄取管线。
- **依赖**：L1（统一按物模型解析）。
- **验收**：HTTP 上报数据与 MQTT 上报在属性最新值上等价。

#### L12 · 认证方式扩展（拟 T-25）
- **目标**：落地 X.509 / JWT 认证与产品级 Topic 模板。
- **范围**：X.509 证书签发与吊销；JWT 认证；`topic_prefix` 模板变量化。
- **依赖**：无（但需存量设备刷机窗口）。
- **验收**：三种认证方式并存，EMQX 认证回调按产品 `auth_mode` 分派。

## 5. 首条链路：T-14 → T-15 → T-16

一期前三项构成一条完整主线，是本路线图的**首个交付单元**：

```
T-14 物模型与数据解析   →   T-15 命令下发与服务调用   →   T-16 设备影子
（设备有了语义模型）        （云端能控制设备）              （状态双向同步 / 离线补发）
```

> **进度**：T-14（L1）、T-15（L2）均已于 2026-10-02 交付；下一步为 **T-16 设备影子**（L3），落点即「离线设备可控制」这一商用平台标志性能力。下述两项存量问题已随 T-15 修复。

**为什么是这个顺序**：
1. 物模型是一切的前提 —— 命令的参数、影子的属性标识符、告警的阈值对象都依赖它；
2. 命令下发是**当前唯一的已知缺陷**（`ExternalApiController` 的命令主题不含 `/cmd/`，与 `AclEvaluator` 平台发布规则冲突），越早修越好；
3. 设备影子依赖前两者，且是「离线设备可控制」这一商用平台标志性能力的落点。

**T-15 已处理的存量问题**（2026-10-02 修复）：
- `AclEvaluator.allowPlatform` 要求平台发布主题 `contains("/cmd/")`，而旧命令主题为 `device/{deviceKey}/command`，**必然被拒** —— 已修正为 `device/{deviceKey}/cmd/down`（ACL 规则一行未改）；
- 设备禁止发布自身 `cmd/` 前缀（`allowDevice`），故命令回执**不能**走 `cmd/` —— 已另设上行回执主题 `device/{deviceKey}/reply`。

## 6. 附：与 R5 触发式改造的边界

本路线图全部为**功能补齐**，不触碰 R5 触发式改造（`message` 分区、Kafka 分区、时序库、Maven 多模块拆分）。当 L8（属性时序）落地后，属性历史数据量将成为 R5 门槛的新评估项，届时随 `scripts/r5-trigger-check.*` 一并复核。
