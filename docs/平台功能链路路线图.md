# 平台功能链路路线图

> 版本：v1.7　创建日期：2026-10-02　状态：进行中（L1 / T-14、L2 / T-15、L3 / T-16、L4 / T-17、L5 / T-18、L6 / T-19、L7 / T-20 已交付）
> 定位：对标主流 IoT/MQTT 平台的能力域，把「还差什么」拆成可逐项交付的**功能链路**，作为 T-14 及后续子任务的排期依据。

---

## 1. 目的与对标基线

本平台已完成「产品 / 一机一密 / 上行摄取 / 历史查询 / SSE 实时 / 开放 API / Webhook」这条**通信与接入**主线（T-01 ~ T-13），但在「设备建模 → 数据语义化 → 云端控制 → 状态同步 → 业务编排」这条**平台能力**主线上基本空白，这正是与真正商用平台的差距所在。

对标对象与取用重点：

| 平台 | 取用重点 |
|------|----------|
| **ThingsCloud** | 主基线。产品/设备模型、消息规则（属性上报 → 更新云端属性 / 下发命令 / 转发外部 MQTT 与 URL）、零代码自动化 [$TRAE_REF](https://www.thingscloud.xyz/docs/guide/rules/overview.html)[$TRAE_REF](https://www.thingscloud.xyz/docs/guide/rules/attrs-rpt.html) |
| **阿里云 IoT 平台** | 物模型 TSL（属性 / 事件 / 服务）、Alink JSON 上下行格式、设备影子（desired/reported）、服务调用记录查询 [$TRAE_REF](https://help.aliyun.com/zh/iot/developer-reference/list-of-operations-by-function)[$TRAE_REF](https://help.aliyun.com/en/iot/user-guide/device-properties-events-and-services) |
| **ThingsBoard** | 规则引擎（Rule Chain：过滤 / 变换 / 路由 / 动作）、RPC 下行 [$TRAE_REF](https://thingsboard.io/docs/paas/eu/user-guide/rule-engine/) |

**交付原则**：每条功能链路必须**端到端可用**（数据模型 + 后端接口 + 前端页面 + 测试 + 文档），不做只有后端没有入口的半成品；顺序上沿用既有约定「先补齐功能缺口，再动底层架构」。

## 3. 功能链路清单（逐项）

每条链路标注：**目标 / 范围 / 依赖 / 验收口径**。

### 一期：设备建模与控制主线（P0）

#### L1 · 物模型与数据解析（T-14）— ✅ 已交付
- **目标**：产品拥有结构化设备模型（TSL：属性 / 事件 / 服务），上行数据按模型解析为有语义的属性值与事件记录。
- **范围**：TSL 数据结构与校验规则；`product` 物模型字段与版本；物模型 CRUD + 导入 / 导出接口；前端物模型编辑器；上行 Alink JSON 解析 → 属性最新值表 + 事件记录表；非 Alink 载荷兼容直存。
- **依赖**：无（基础链路）。
- **验收**：为产品定义物模型后，设备按 Alink JSON 上报属性，`device_property_latest` 与 `device_event_record` 正确落库；非法载荷 / 未定义标识符有明确处置且不丢消息；前端可增删改查并导入导出 TSL。
- **交付（2026-10-02）**：迁移 `V4__thing_model.sql`（产品三列 + 两张派生表）；`ThingModelValidator`（V1~V16 规则）与进程内缓存（TTL + 主动失效）；`ProductController` 物模型六端点；上行解析作为 `IngestDispatcher` 落库后**第三路旁路**（逐条隔离失败、不进死信）；只读查询接口（属性最新值 / 事件分页）；前端产品管理页 + 物模型编辑器（递归类型编辑 / 导入导出 / 脏确认）与设备详情属性 / 事件区块。门禁：后端 `mvn -B verify` 全绿、前端 `lint` 0 error / `test` 106 全绿 / `build` 通过。

#### L2 · 命令下发与服务调用（T-15）— ✅ 已交付
- **目标**：云端可对设备下发属性设置与服务调用，全链路可追踪（记录 + 回执）。
- **范围**：**修正命令主题与 ACL 冲突**（`device/{deviceKey}/command` → 含 `/cmd/` 的主题）；命令 / 服务记录表；参数按物模型校验；同步（等待回执，超时失败）与异步两种调用方式；设备回执主题接入；前端「设备控制」面板与命令记录列表；开放 API 同步对齐。
- **依赖**：L1（服务入参 / 出参定义、属性 set 目标）。
- **验收**：控制台下发命令后设备收到且可回执，记录状态从 `PENDING → SENT → ACKED/FAILED/TIMEOUT` 正确流转；非 `cmd/` 主题不再产生 ACL 拒绝；越权调用返回明确错误码。
- **交付（2026-10-02）**：下行主题修正为 `device/{deviceKey}/cmd/down`、回执主题 `device/{deviceKey}/reply`（**ACL 规则与授权回调一行未改**，仅修正主题即修复「下发必被拒」存量缺陷）；迁移 `V5__device_command.sql`（`device_command_record` + 状态机，条件更新保证终态不可覆盖）；`ThingModelParamValidator` 上下行共用同一套 `dataType` 校验；同步调用用**轮询本表**而非进程内 `Future`（多副本下回执可能落到其他副本），配 `CommandTimeoutSweeper` 定时巡检兜底异步超时；回执以共享订阅 `$share/{group}/device/+/reply` 接入摄取**第四路旁路**更新状态；控制台三端点（能力查询 / 下发 / 记录分页）+ 开放 API 新契约（删除 `SendCommandRequest`）；前端设备控制面板（属性设置 / 服务调用动态表单 + 同步异步）与命令记录列表（分页 / 状态着色 / JSON 详情）。门禁：后端 `mvn -B verify` 220 全绿、前端 `lint` 0 error / `test` 131 全绿 / `build` 通过。

#### L3 · 设备影子（T-16）— ✅ 已交付
- **目标**：以 desired / reported / delta 三份状态描述设备，支持离线命令缓存与重连补发。
- **范围**：`device_shadow` 表与版本号；属性上报自动更新 reported；属性设置写入 desired；delta 计算与查询；设备离线时命令入 desired，上线后补发；前端设备详情影子视图。
- **依赖**：L1（属性标识符）、L2（命令通道）。
- **验收**：设备离线时下发期望值不丢失，设备上线后收到并上报，reported 收敛到 desired、delta 清空；影子版本号单调递增。
- **交付（2026-10-02）**：迁移 `V6__device_shadow.sql`（`device_shadow` 表：`desired`/`reported`/`delta` 三份 JSON + `version` 单调递增 + 唯一键 `device_id`、外键级联删除）；`DeviceShadowService` 以「读-改-写 + CAS（`WHERE device_id=? AND version=?`，冲突重读重算最多 `app.shadow.cas-retry` 次，耗尽仅 WARN 放弃）」维护三份状态与 `delta` 重算（只在 `desired` 键上生成，`reported` 追平即移除）；reported 由 `ThingModelInterpretService` 在属性 upsert 后**回读权威库**驱动（继承 `upsertIfNewer` 时间戳守卫，乱序旧包天然不污染影子）；命令状态机扩展 `QUEUED`（待补发）——离线 / 发布异常且 `type=property_set` 时置 `QUEUED` + `next_attempt_at=now` 且写 `desired`；上线补发为 `IngestDispatcher` **第五路旁路** `ShadowDeliveryService.onIngest`（`data`/`heartbeat` 视为上线，先 `countQueued` 短路再 `flushQueued`，逐条隔离异常）；`ShadowRetrySweeper` 定时巡检按指数退避（`retry-base-delay-ms` → `retry-max-delay-ms` 封顶）重试，次数耗尽置 `FAILED`（`error_message='补发重试次数耗尽'`）；控制台两端点（`GET /devices/{deviceKey}/shadow`、`PUT .../shadow/desired`，新增错误码 `6206`）+ 开放 API 对称端点；前端 `DeviceShadowPanel.vue`（三列对照 + delta 高亮 + 一键补发）+ 命令记录 `QUEUED`「待补发」标注。门禁：后端 `mvn -B verify` 251 全绿（含 ArchUnit）、前端 `lint` 0 error / `test` 143 全绿 / `build` 通过。

#### L4 · 告警中心（T-17）— ✅ 已交付
- **目标**：对属性阈值、设备离线、事件上报三类来源产出告警并通知。
- **范围**：告警规则（阈值 / 离线 / 事件）；告警记录表与状态流转（触发 / 恢复 / 确认）；通知出口复用 Webhook；前端告警规则配置与告警列表；顶栏通知中心接入（T-13 遗留占位）。
- **依赖**：L1（属性标识符）、L2（可选：告警联动下发命令）。
- **验收**：属性越限后产生告警记录并回调 Webhook；恢复正常自动置「已恢复」；重复告警按规则去重（抑制窗口）。
- **交付（2026-10-02）**：迁移 `V7__alert_center.sql`（`alert_rule` + `alert_record`，**只加表**，应用版本可安全回滚）；三类来源共用评估核心四步（查活动告警 → 新建 / 抑制窗口内计数累加去重 / 超窗再次通知 → 回落恢复）；阈值按 `BigDecimal.compareTo`、`EQ`/`NE` 按归一化文本，不可解析值跳过；**不新增 MQTT 主题、不改 ACL** —— 数据来源为已落库的 `device_property_latest` / `device_event_record` 与设备运行态，`onProperties` / `onEvents` 作为 `ThingModelInterpretService` 内的旁路调用（不新增 `IngestDispatcher` fan-out 路），离线由 `AlertSweeper` 定时**拉**巡检（上线 / 规则删除自动恢复）；通知复用 `WebhookDispatcher` 投递 `alert.triggered` / `alert.recovered`（载荷含 `alertId/ruleId/severity/triggerCount` 等）；控制台 10 端点（`/alerts`，含未读数 / 最近活动告警）+ 开放 API 4 个只读端点（`/external/v1/alerts*`），新增错误码 `6207`~`6211`；前端 `AlertRules.vue`（按来源动态表单）+ `AlertList.vue`（过滤 / 分页 / 详情 / 确认 / 恢复）+ `TopBar` 通知中心（未读角标 + 最近 10 条 + 「查看全部」）。门禁：后端 `mvn -B verify` **311 全绿**（含 ArchUnit）、前端 `lint` 0 error / `test` 全绿 / `build` 通过。

#### L5 · 设备分组与标签（T-18）— ✅ 已交付
- **目标**：设备可按分组树与标签组织，支持按分组 / 标签批量操作。
- **范围**：`device_group` 分组树 + `device_tag` 标签；设备与分组 / 标签关联；列表按分组 / 标签过滤；批量下发命令与批量禁用。

- **验收**：分组树可增删改移动；按标签筛选结果正确；批量下发对分组内设备逐一生成命令记录。
- **交付（2026-10-03）**：迁移 `V8__device_group_and_tag.sql` 新建四张表（`device_group` 自引用树 + `device_tag` + `device_group_relation` / `device_tag_relation` 两张多对多关联表，**只加表、可安全回滚**，关联表为物理行）；`DeviceGroupService` / `DeviceTagService` / `DeviceBatchService`（接口不依赖 Mapper，持久化细节在 `impl`）；分组「按分组筛选含所有后代」由 `DeviceGroupMapper.selectDescendantIds`（MySQL 8 递归 CTE）实现，`DeviceMapper.pageQuery` 增加 `groupId`（`EXISTS ... ### 二期：数据价值与运维（P1）

#### L6 · 消息规则 / 规则引擎（T-19）— ✅ 已交付
- **目标**：以可配置规则对上行数据做过滤、变换与转发，替代当前写死的 Webhook 逻辑。
- **范围**：规则模型（触发源 + 条件 + 动作）；动作至少覆盖「更新云端属性 / 下发命令 / 转发外部 MQTT / 转发 HTTP」；规则执行记录与失败重试；前端规则编排（先做表单式，暂不做可视化拖拽）。
- **依赖**：L1（数据语义）、L2（下发动作）。
- **验收**：配置「温度 > 阈值 → 转发 HTTP」后，真实上行触发且转发成功；规则动作失败不影响主摄取链路。
- **交付（2026-10-03）**：迁移 `V9__rule_engine.sql` 新建两张表（`rule_definition` 规则定义 + `rule_execution` 执行记录，**只加表、可安全回滚**）；规则条件判定作为 `ThingModelInterpretService` 内**第三处内部旁路**（`onProperties` / `onEvents` 调用 `RuleEvaluationService`，不新增 `IngestDispatcher` fan-out 路，逐条隔离异常、**旁路异常不冒泡**）；`RuleConditionMatcher` 数值按 `BigDecimal.compareTo`、`EQ`/`NE` 按归一化文本、不可解析值不命中；四类动作出口——`UPDATE_PROPERTY` 复用 `DevicePropertyLatestMapper.upsertIfNewer`（继承时间戳守卫）、`SEND_COMMAND` 复用 `DeviceCommandService.invoke`（`source=RULE`、强制异步）、`FORWARD_MQTT` 新增独立 Paho 组件 `RuleMqttForwarder`（出站第三方 Broker，`app.rule.mqtt.enabled` 默认 `false`）、`FORWARD_HTTP` 新增 `RuleHttpForwarder`（HMAC `X-Signature` + `X-Execution-Id`）；动作投递走**独立线程池** `ruleExecutor`、执行记录落 `rule_execution` 并由 `RuleSweeper` 定时**指数退避重试**（耗尽置 `FAILED`）+ 终态记录保留清理；冷却窗口用进程内 `ConcurrentHashMap` 冷却锚点（不在摄取线程额外读写库）；控制台 10 端点（`/rules`，含试运行干跑），新增错误码 `6218`~`6222`；前端规则中心 `RuleCenter.vue`（规则定义 / 执行记录两页签）+ 规则编辑抽屉 + 执行记录详情与手动重试。门禁：后端 `mvn -B verify` **498 全绿**（含 ArchUnit：规则服务接口不得直依赖 mapper）、前端 `lint` 0 error / `test` 231 全绿 / `build` 通过；A4（真实上行触发转发）/ A6（动作失败不影响主摄取）现场未逐条实测（详见 `总督促文档.md`）。

#### L7 · 设备日志与诊断（T-20）— ✅ 已交付
- **目标**：提供设备上下行全链路日志视图（含命令、事件、连接事件）。
- **范围**：统一日志查询接口（按设备 / 类型 / 时间过滤）；命令与事件记录接入；前端设备日志页（时间线视图）。

- **验收**：单设备一次命令下发可在日志中串起「下发 → 回执」两条记录。
- **交付（2026-10-03）**：**无新表、无新迁移、无写入路径改动、无 MQTT 主题 / ACL 改动** —— 查询时 `UNION ALL` 聚合四张既有表（`message` / `device_command_record` / `device_event_record` / `device_status_history`，分别映射 `MESSAGE` / `COMMAND` / `EVENT` / `STATUS`，时间列 `sent_at` / `created_at` / `reported_at` / `timestamp`），各段投影统一为 `log_type / ref_id / occurred_at / seq / title / detail` 并按 `occurred_at DESC, seq DESC` 排序；命令与回执的关联键 `correlationId` 在 **Java 侧**回填（命令取 `command_id` + `role=REQUEST`，仅 `/reply` 主题的报文从 `payload.id` 解析 + `role=REPLY`；`message.payload` 为 TEXT 且可能非 JSON，故不在 SQL 侧 `JSON_EXTRACT`）；服务层做归属校验（仅本人设备，ADMIN 旁路）、时间窗（半开区间、默认上限 31 天）、类型白名单与关键字过滤、分页（默认 20 / 上限 100）；控制台单端点 `GET /devices/{deviceId}/logs`，新增错误码 `6223`（时间范围非法）/ `6224`（不支持的日志类型）；前端 `DeviceLog.vue` + `DeviceLogTimeline.vue`（类型筛选 / 时间范围默认近 24 小时 / 分页 / 条目展开）+ `useDeviceLog` 组合式函数，路由 `/workbench/devices/:id/logs`，设备详情页头部提供入口。门禁：后端 `mvn -B verify` **523 全绿**（含 ArchUnit：服务接口不直依赖 mapper）、前端 `lint` 0 error / `test` **265 全绿** / `build` 通过；A1 / A3 / A4 / A5 经真实 HTTP 接口实测通过，A2（命令下发串起「下发 → 回执」）以真实接口 + 构造数据验证关联正确，**现场真实设备配合的 A2 实测未做**（详见 `总督促文档.md` §3.13）。

## 5. 首条链路：T-14 → T-15 → T-16

一期前三项构成一条完整主线，是本路线图的**首个交付单元**：

```
T-14 物模型与数据解析   →   T-15 命令下发与服务调用   →   T-16 设备影子
（设备有了语义模型）        （云端能控制设备）              （状态双向同步 / 离线补发）
```

> **进度**：T-14（L1）、T-15（L2）、T-16（L3）、T-17（L4）均已于 2026-10-02 交付，T-18（L5）、T-19（L6）、T-20（L7）已于 2026-10-03 交付。一期（设备建模与控制主线 P0）五项全部落地，形成「设备有语义模型 → 云端能控制设备 → 状态双向同步 / 离线补发 → 异常可感知与告警 → 设备可组织与批量操作」的完整闭环；二期首项 **L6 / T-19 消息规则 / 规则引擎**已交付，形成「上行数据按可配置规则过滤、变换与转发」的编排能力；**L7 / T-20 设备日志与诊断**已交付，补齐「一台设备到底发生了什么」的统一只读视图（消息 / 命令 / 事件 / 连接状态单一时间线）；下一步为 **L8 / T-21 属性时序与可视化**。下述两项存量问题已随 T-15 修复。

**为什么是这个顺序**：
1. 物模型是一切的前提 —— 命令的参数、影子的属性标识符、告警的阈值对象都依赖它；
2. 命令下发是**当前唯一的已知缺陷**（`ExternalApiController` 的命令主题不含 `/cmd/`，与 `AclEvaluator` 平台发布规则冲突），越早修越好；
3. 设备影子依赖前两者，且是「离线设备可控制」这一商用平台标志性能力的落点。

**T-15 已处理的存量问题**（2026-10-02 修复）：
- `AclEvaluator.allowPlatform` 要求平台发布主题 `contains("/cmd/")`，而旧命令主题为 `device/{deviceKey}/command`，**必然被拒** —— 已修正为 `device/{deviceKey}/cmd/down`（ACL 规则一行未改）；
- 设备禁止发布自身 `cmd/` 前缀（`allowDevice`），故命令回执**不能**走 `cmd/` —— 已另设上行回执主题 `device/{deviceKey}/reply`。
