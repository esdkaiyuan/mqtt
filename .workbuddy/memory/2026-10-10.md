## T-30 商用化重构方案（新建）
- 用户诉求：平台要扩成商用 MQTT 站点，设备接入不能只绑ESP，文档/日志/API 要对标国内一线厂商。
- 派三路代码级调研（可观测性/ API协议文档 / 多协议设备接入），关键发现：
  1. `Product` 实体**无 protocol_type 字段**，纯 Modbus 设备今天就能登记——卡点不在登记，在"网关=代连 MQTT"而非"边缘驱动"。
  2. 平台侧 Modbus 主站是 T-24 **主动划出的边界**（`T-24_设计文档.md:130-133`），不是遗漏；推翻它=新建子系统。
  3. 文档问题不是缺内容而是缺权威单一源；日志层最薄弱（0 个 logback-spring.xml、0 个 MDC/traceId）。
  4. 合规风险：前端 `apiEndpoints.js:169` 宣称 429 限流，后端 `RateLimit` grep 零命中——不实承诺。
  5. 死信表有 REPLAYED/DISCARDED 状态但 Controller 只有查询、无写路径。
- 产出：`docs/T-30_商用化重构_开放接入与平台工程化_方案.md`，三阶段（工程化补欠账→文档收敛→接入扩展），
  核心待拍板项为「强化边缘(路线A) vs 平台侧Modbus主站(路线B)」。
- 经验：这类平台级规划，先用 Explore 子agent 做代码级现状调研（含"为什么没做"的决策依据），再出方案，
  比直接读文档更准——文档断言与代码事实有多处偏差（如 DEPLOYMENT.md 的 ACC 编号实为功能验收表非部署清单）。

### 踩坑记录（重要）
1. **Spring Boot 4 包路径**：`ServiceImpl` 在 `com.baomidou.mybatisplus.spring.service.impl`，不是 `.extension.`。
2. **Jackson 3**：用 `tools.jackson.databind.ObjectMapper`（非 `com.fasterxml`）。
3. **logback-spring.xml 两处坑**：① 注释内不能出现 `*/`（我误写导致后续全被吞进注释）；
   ② 同一 appender 不能在顶层与 springProfile 内重复定义（FileCollisionAnalyser 判定文件冲突
   并跳过初始化 → ApplicationContext 加载失败）。正确结构：appender 全在顶层定义一次，
   profile 内只切 root 的 appender-ref。
4. **循环依赖**：`IngestPipeline → IngestDeadLetterService → IngestPipeline`（重放需要管线）。
   用 `ObjectProvider<IngestPipeline>` 延迟获取打断，项目原本无 @Lazy 先例。
5. **数据源库名硬编码**：`application.yml` 的 jdbc url 里库名写死 `mqtt_cloud`，
   导致 `DB_NAME` 环境变量无效、测试连不上。已参数化为 `${DB_NAME:mqtt_cloud}`。
6. **测试环境**：`MqttCloudApplicationTests`/`SecurityConfigFilterOrderTest` 需要真实 MySQL
   （无 testcontainers、无 test resources）。验证须起 MySQL 容器并`--network host` +
   `-e DB_HOST/DB_NAME=...` 才能跑通，否则报Communications link failure。
