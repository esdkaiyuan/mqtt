### 关键设计决策（后续改动勿推翻）

1. **`refreshCounters` 必须保留 `PAUSED` / `ABORTED` 不被聚合覆盖** —— 这两个状态由运维操作产生而非记录聚合。若被重算，暂停会被下一次设备回传改回 `RUNNING`、终止被改回 `SUCCESS`，**两个操作直接失效**。
2. **`dispatched_count` 排除 `SKIPPED`，`skipped_count` 单列不并入 `failed_count`** —— 终止是运维主动行为，读成「升级失败」是误导；计入已下发会让终止任务进度条虚高到 100%。
3. **灰度推进判定读记录表（`NOT EXISTS`）而非 `ota_upgrade_batch.status`** —— 后者仅在 `refreshBatchCounters` 被调用时刷新，收口后未被刷新会让本该推进的批次多压一轮巡检。
4. **非法 `batchMode` 一律拒绝，绝不静默归到 `ALL`** —— 静默降级会让运维以为在做灰度、实际全量下发，正是灰度要防的事故。
5. **`fileMd5` 取值非法按「未回传」处理，不丢弃整条报文** —— 与 `progress` 非法即丢弃刻意不同：md5 是新增可选字段，老设备不应因它卡死升级。但**回传了且不一致一律判失败**。
6. **互斥冲突设备保持 `PENDING` 而不置终态** —— 否则对方任务一旦失败，这些设备就永远升级不上。
7. **互斥查询 `excludeTaskId` 必须传非空占位**（建任务时新任务尚无 id，传 `0L`）—— SQL 是 `task_id <> #{id}`，传 `null` 因三值逻辑恒为 false，会把所有设备判成冲突。
8. **巡检顺序固定为补投 → 推进 → 超时** —— 超时放最前会把「刚下发、设备还没回传」误判为超时。

### 踩坑

- **MyBatis-Plus 的 Wrapper 参数是惰性渲染的**：`eq()` / `in()` 把值挂在 `appendSqlSegments` 的 supplier 上，**必须先调 `getSqlSegment()` / `getSqlSet()` 才会填进 `paramNameValuePairs`**。在 `mock.selectList(any())` 的 answer 里直接读参数表会拿到空 Map。`getSqlSet()` 只含列名与 `#{}` 占位符，实际值要去 `paramNameValuePairs().values()` 取。
- **`refreshBatchCounters` 不能用 batchId 定位**：写成 `(SELECT task_id FROM ota_upgrade_batch WHERE id = ?)` 会撞 MySQL 的 `You can't specify target table 'ota_upgrade_batch' for update in FROM clause`。改用 `(task_id, batch_no)` 复合键，唯一键保证命中单行且规避该限制。
- **构造器签名变更会打断既有测试 `setUp`**：新增 `OtaUpgradeBatchMapper` 等依赖后，既有 `OtaUpgradeServiceImplTest` / `OtaProgressServiceImplTest` 报 `NoSuchMethod '<init>'`，需同步 `setUp` 与 fixture（`task()` 补灰度列、`record()` 补 `batchNo` 与 `verifyStatus`）。
- **mock 的 `selectById` 恒返回初始值**：`pause()` / `resume()` 内部 `return detail(...)` 会重新读库，mock 下拿到的仍是旧状态。断言应针对**实际下发的 UPDATE**，而非 `detail` 投影。
- **`'A'` 是合法十六进制**：`"A".repeat(32)` 经 `toLowerCase()` 后是合法 md5，不能用来构造「非十六进制」用例，得用 `'g'`。
- `vite build` 验证用 `--outDir dist-t32check`，避免清空既有 `dist/` 触发 safe-delete 守卫；验证后需清理。

## T-33：规则多条件与多动作（交付，补 G-6-7）

补齐对标清单 P1 追赶段倒数第二项。详见 `docs/T-33_规则多条件与多动作_实施计划.md`。

### 核心设计决策（后续勿推翻）

1. **JSON 可选列 + 旧列回落，而非子表**。依据：规则评估是「按 `user_id` 拉全量 → 内存匹配」
   （`selectEnabledByUser`），条件与动作**从不作为 SQL 过滤条件**，故 JSON 不损失任何查询能力，
   而 `rule_condition`/`rule_action` 子表只会带来 JOIN 与双写一致性成本。写入策略为
   「**多值优先、单值回填**」：数组非空时以数组为准，首项回填旧列，供仍读 `identifier`/`action_type`
   的存量路径使用。存量行两列为 NULL → 自动回落，**零数据改写**。
2. **单条件规则代码路径一行未改**。`RuleMultiSpec` 负责解析与回落，`hasMultipleConditions` 决定走哪个分支。
   非法 JSON 一律回落单值而非抛异常 —— 一条规则的配置问题不应让同一用户所有规则停摆。
3. **多条件求值范围是「一次上报批」而非单个样本**。三条语义：同一条件多次上报取**任一满足**
   （取交集会漏报偶发尖峰）；`AND` 下缺值判不满足**并终止求值**；`OR` 下缺值不贡献命中。
4. **多动作 = 执行粒度即动作粒度**。一次命中落 N 条独立 `rule_execution` 并各带 `action_config_snapshot`，
   使重试/巡检重放/手动重试（三条共用 `execute(executionId)` 入口）天然按动作隔离，
   `FORWARD_HTTP` 不会重复投递，且执行器无需多入口。
5. **执行器分派判据必须是「快照是否存在」而不是「快照优先于规则」**。快照非空 = 多动作（按记录分派）；
   为空 = 单动作，**保持按规则分派**（T-19 既有语义：记录上的 action_type 只是触发当时的快照）。
   同一判据同时控制 `readConfig` 与 `switch`，两处不分叉。
6. **冷却锚点每次触发只占一次**。放进动作循环会把第二个动作挡掉，多动作退化成单动作。
7. **试运行诚实降级**：多条件下即使首条件满足也判未命中并写明原因；多动作诊断追加「只诊断了第一个」。
   宁可显示未命中，也不给误导性的「已命中」。

### 踩坑

- **`AND` 缺值写成 `continue` 是真 bug**：注释写「缺值不算命中」而代码是跳过继续，导致另一条件满足时
  `anySatisfied=true` 整条规则误命中。由 `RuleMultiMatcherTest.missing_value_is_not_a_hit_under_and` 抓到。
  多条件求值的短路分支要逐个想清楚 AND/OR 各自该不该终止。
- **不能无脑把执行器改成「按执行记录分派」**：`RuleActionExecutorImplTest` 8 个用例失败，
  因其 `pendingExecution()` 把 `action_type` 硬编码为 `UPDATE_PROPERTY` 而规则是 `SEND_COMMAND` ——
  测试守的正是「单动作以规则为准」这条既有语义。
- Vue `v-model` 不能绑定表达式（`v-model="a || b"` 报 `vue/valid-v-model`），须按类型拆成多个输入。
- 脚本 `replace('<style scoped>', …)` 时若新内容也以该串收尾会产生 `</style scoped>`。
- 实体用 `import com.baomidou.mybatisplus.annotation.*;` 通配符时，按精确类名插入 import 会失败。
- `vite build` 的 `--outDir dist-xxxcheck` 目录删除会撞 safe-delete 守卫（156 文件 > 阈值 50），
  需显式授权删除；`rm -rf dist-t32check`（151 文件）同理。

## T-34：命令级权限与调用配额（交付，补 G-4-1，P1 追赶段收口）

**P1 追赶段至此全部清空**（T-32 三项 + T-33 一项 + T-34 一项）。详见 `docs/T-34_命令级权限与调用配额_实施计划.md`。

### 发现的核心洞

`POST /devices/{deviceKey}/commands` 与 `POST /devices/batch/commands` **改造前只做设备归属校验，
SecurityConfig 中没有任何角色限制 —— VIEWER 可以下发命令**。这是 G-4-1 里最直接的一个问题，
比清单里「按用户/角色限定可下发设备与命令」的措辞更具体。

### 三层约束（各管一件事，互不牵制）

1. **角色闸门**（`SecurityConfig`，路径级）：`POST` 两条命令端点限定 ADMIN/OPERATOR。
   **只拦 POST** —— GET（命令记录查询）保留 `authenticated()`，VIEWER 仍有只读排查能力。
   刻意不动 `/devices/batch/**` 下的 enable/disable/groups/tags（属设备管理权限链路，避免范围蔓延）。
2. **标识符 / 类型权限**（`CommandGuardService`）：危险标识符黑名单（大小写不敏感，默认
   `factory_reset`，角色可豁免且豁免不串角色）+ 角色→命令类型矩阵（缺省即不限）。
   **只作用于 `CONSOLE` / `OPEN_API`**。
3. **调用配额**（`CommandQuotaService`）：按 `operatorId` 的 Redis 固定窗口，**覆盖全部来源**。

### 关键决策（后续勿推翻）

- **权限只管外部来源，配额覆盖全部来源**，看似矛盾实则两件事：
  规则/OTA/场景的 `operatorId` 是「谁配置的这条自动化」，套角色判定会导致
  「VIEWER 配的规则再也执行不了」；但规则风暴同样要打爆 Broker，配额必须覆盖它们。
- **判定必须在 `insert` 之前**：否则被拒命令留下无主记录，用户看到「明明拒绝了却有下发记录」会把排障带偏。
- **配额默认关闭 + `failOpen=true`**：与 `app.rate-limit` 一致；`enabled=false` 时零 Redis 读写。
- **TTL 只在首次 INCR 设置**（返回值为 1 时）：每次都重设会把窗口无限续期，退化成「从首次调用起永不释放的累计上限」。
- `CommandProperties` 是**扩展**不是新建 —— `app.command` 前缀 T-15 已占用。

### 踩坑

- **注释里的路径通配 `/devices/*/commands` 会提前关闭块注释**（`*/` 被当成注释结束符），
  报错是「类声明处需要 class/interface/enum」这种完全指不到问题的位置。注释内改用路径模板写法
  `/devices/{deviceKey}/commands`。**这是本项目第二次栽在注释写法上，写含通配符的路径注释时务必检查。**
- `@RequiredArgsConstructor` 的**参数顺序 = 字段声明顺序**；把新字段插到中间后，
  测试里按直觉追加到末尾会报「不兼容的类型」（ShadowProperties 无法转换为 CommandGuardService）。
- 手写大文件时容易漏大括号（`isDenied` 的 if 块漏了 `}`）。

## T-35：开放 API 补齐（X-1 批次一）—— P2 规模化首项

`/external/v1` 端点数 **14 → 26**，新增 12 个**只读**端点覆盖 7 个此前完全未开放的能力域。
详见 `docs/T-35_开放API补齐_实施计划.md`。

### 核心决策

1. **零业务逻辑重写**：全部转发既有服务，控制器只做「API Key → userId 转换 + 响应裁剪」。
2. **归属隔离交给服务层，不在控制器重复判断**：既有服务方法本就以 userId 校验并抛 2003，
   复用即自动继承隔离；重复判断会造成两处规则漂移，其中一处漏改就是数据泄露。
   仅设备维度端点额外走 `requireOwnedDevice`（设备是数据入口锚点）。
3. **严格只读，不开放写操作**：写操作的审计 / 回滚 / 幂等语义远比读复杂，控制台已完整覆盖；
   第三方需要写能力时走既有命令 / 影子写端点。
4. **响应显式投影**：规则 / 场景用 `toRuleMap` / `toSceneMap` 挑字段，
   不外泄 `target_json`、`condition_config` 等内部 JSON 原文（否则第三方会依赖上未来可能变的内部格式）。
5. **补上这个控制器缺失的单测**：此前**零覆盖**，而它是 API Key 天然跨账号、最需要守护的面。
   14 项重心在「非归属设备一律 2003 且 `verify(never())` 下游未触达」——
   校验失败但数据已从服务读出，等于没校验。

### 踩坑

- **写转发代码前必须打开 DTO 看真实字段**：`PropertyHistoryQueryDTO.bucket` 是白名单字符串
  （`1m`/`5m`/…）而非秒数；`HistoryQueryDTO` 用 `deviceId` 且**没有 `messageType`**。先编译报错才暴露。
- `UserPrincipal` 构造签名是 `(userId, username, role, apiKeyId)`；
  照抄别处的 `(userId, null, List.of())` 会报「List 与 String 不兼容」。

## T-36：导出与实时推送（X-2 完成 + X-3 部分）

**P2 规模化收尾**。详见 `docs/T-36_导出与实时推送_实施计划.md`。

### X-2 CSV 导出（完成）

4 个端点（设备日志 / 属性时序 / 命令记录 / 告警记录）+ `ExportService` + `ExportController` +
`CsvWriter`（common 包纯函数）。与既有分页查询**并列**而非替代。

`CsvWriter` 收敛三个「不处理就会直接坑到用户」的细节：

1. **UTF-8 BOM** —— 不加则 Excel 打开中文乱码；文件名走 `ContentDisposition` 的 UTF-8 编码。
2. **公式注入防护** —— `=`/`+`/`-`/`@`（及 tab/CR）开头的单元格前置单引号。
   设备上报的 payload **完全不可控**，`=HYPERLINK("http://evil","点我")` 是经典凭据钓鱼手法。
   ⚠️ **判定顺序必须「先判公式注入、再判加引号」** —— 反过来的话 `"=x"` 加了引号就逃掉了。
3. **RFC 4180 转义**。

**导出必须有行数上限**：不分页的导出天然无界，十万行一次性拼进 StringBuilder 再编码成 byte[]，
峰值内存是结果的数倍。默认 1 万 / 上限 10 万，并在响应头 `X-Export-Truncated` **如实标注截断**。

属性时序的列按**分桶聚合口径**给（桶起点/样本数/最小值/最大值/均值）——
`PropertyHistoryPoint` 没有「value」列，非数值型属性的桶里它根本不存在，不要臆造。

### X-3 实时推送（部分）

- **SSE 由单主题扩为多主题**：`device-data`（既有）/ `device-log`（预留）/ `property-trend`（新增）。
  `Subscriber` 带 topics，**空集合 = 全订阅** → 既有 `subscribe(userId, admin)` 行为逐位等价
  （既有 12 项测试零修改即通过）。新增 `publishEvent(ownerId, eventName, payload)`。
- **属性趋势流挂在 `PropertyHistoryService.append`** —— 它是属性历史**唯一写入点**，不漏推不重推。
  整段 `try/catch` 静默：**SSE 失败绝不能让摄取主链路的落库失败**，否则触发摄取重试。
- **开关与落库开关分离**：`PROPERTY_HISTORY_STREAM_ENABLED`（默认关闭）。
  压测关掉落库时往往仍想保留已有历史可查。
- **设备日志实时流刻意未做**：日志是查询时聚合消息/事件/命令/状态四路的 union，**没有单一写入点**，
  挂钩需动摄取旁路，风险与收益不成比例。`device-log` 主题名与订阅能力已就位。

### 踩坑（重要）

- **`mvn -q compile` 的输出会骗人**：中文编译器报错格式不含 `java:` / `符号:` 字样，
  `grep -aE "ERROR.*java:|符号:"` 会漏掉**全部**错误而误判成功。
  **判断编译成功必须看 exit code**，不能只看 grep 有没有输出。这次因此多花了三轮。
- Python heredoc 里写 `\r\n` 转义层数极易出错导致 `replace` 静默不生效，连续踩两次。
  **替换后必须回读确认**。
- 放宽可见性时 `private long subscriberCount()` 实际是 `private int`，替换没匹配上；
  `lastRecipientUserIds` 是字段不是方法。
