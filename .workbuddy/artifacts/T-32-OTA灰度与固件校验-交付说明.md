## 一句话

把 OTA 从「**一经创建即全量即时下发、进度以设备自报为准、同一台设备可被多个任务同时升级**」改造为主流平台形态 —— 可分批灰度、可暂停 / 终止、可校验固件完整性、设备级互斥。

---

## 改造前 → 改造后

| 维度 | 改造前（T-22） | 改造后（T-32） |
|---|---|---|
| 下发 | 建任务即**全量即时下发** | `BATCHED` 策略**只下发首批**，后续批次按条件推进；`ALL` 策略行为不变 |
| 推进 | 无 | 巡检自动推进（「上一批已收口 + 间隔到期」）或控制台手动推进 |
| 控制 | 只有重投 | 暂停 / 恢复 / 终止 / 手动推进四个端点 |
| 终止语义 | 无 | 未下发记录置 `SKIPPED`，**不计入失败**（终止是主动行为，不是设备故障） |
| 完整性 | 进度**以设备自报为准**，md5 从未比对 | 设备可回传 `fileMd5`，不一致**直接判失败** |
| 设备并发 | 同一设备可在多个 `RUNNING` 任务中重复升级 | 建任务期 + 下发期两处互斥，同一设备只会被一个任务占用 |

## 五条核心设计（后续改动勿推翻）

1. **`refreshCounters` 必须保留 `PAUSED` / `ABORTED`**
   这两个状态由**运维操作**产生而非记录聚合。若被聚合重算，暂停中的任务会被下一次设备回传立刻改回 `RUNNING`、终止中的会被改回 `SUCCESS` —— **两个操作直接失效**。

2. **`dispatched_count` 排除 `SKIPPED`；`skipped_count` 单列不并入失败**
   `SKIPPED` 是「终止时从未下发」，计入已下发会让终止任务的进度条虚高到 100%；并入失败会让运维读成「这批设备升级失败」。

3. **灰度推进判定读记录表（`NOT EXISTS`）而非批次 `status`**
   批次 `status` 仅在 `refreshBatchCounters` 被调用时刷新；批次刚收口但尚未刷新时它仍是 `RUNNING`，会让本该推进的批次多压一轮巡检。

4. **非法 `batchMode` 一律拒绝，绝不静默归到 `ALL`**
   静默降级会让运维以为在做灰度、实际全量下发 —— 正是灰度要防的事故。

5. **互斥冲突设备保持 `PENDING` 而不置终态**
   否则对方任务一旦失败，这些设备就永远升级不上了。待对方收口后由补投巡检自然重投。

## 兼容性

- **零下行协议改动** —— 仍经 `cmd/down` 的 `thing.service.ota_upgrade` 下发 `{url, version, md5, size}`，**存量设备零改动即可继续升级**。
- **零 ACL 改动、零新主题** —— 校验复用既有 `device/{key}/ota` 上行。
- **存量数据语义诚实** —— V19 把存量记录 `verify_status` 回填为 `NOT_REPORTED` 而非 `PASSED`：改造前「进度以设备自报为准」，回填 PASSED 是虚增可信度。

## 新增接口与配置

**端点**：`GET /ota/tasks/{id}/batches`、`POST /ota/tasks/{id}/{pause|resume|abort|advance}`

**错误码**：`6293` 目标设备全部被其他升级任务占用 · `6294` 灰度批次参数非法

**配置**（`app.ota`，已透传 `.env.example` 与 `docker-compose.yml`）：

| 变量 | 默认 | 作用 |
|---|---|---|
| `OTA_DEVICE_CONFLICT_POLICY` | `SKIP` | 互斥策略：`SKIP` 静默剔除 / `REJECT` 整单拒绝 |
| `OTA_BATCH_INTERVAL_MS` | `0` | 灰度自动推进间隔；`0` = 仅手动推进 |
| `OTA_BATCH_ADVANCE_BATCH_SIZE` | `5` | 单轮最多推进几个批次 |
| `OTA_DEFAULT_BATCH_SIZE` | `10` | 灰度默认每批台数 |
| `OTA_VERIFY_REQUIRED` | `false` | 设备未回传 md5 时是否判失败（默认放行以兼容老设备） |
