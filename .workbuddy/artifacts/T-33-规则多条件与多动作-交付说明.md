# T-33 · 规则多条件与多动作 —— 交付说明

> 交付日期：2026-10-11　状态：**已交付，门禁全绿**
> 对应缺口：**G-6-7**（P1 追赶段倒数第二项）

## 一句话

把规则模型从「一条规则只能有一个触发条件、一个动作」扩为「多条件 AND/OR + 多动作」，且**存量规则行为逐位不变**。

---

## 改造前 → 改造后

| 维度 | 改造前（T-19） | 改造后（T-33） |
|---|---|---|
| 触发条件 | 一个标识符 + 一个比较符 | 最多 10 个条件，`AND`（全部满足）/ `OR`（任一满足） |
| 执行动作 | 一个动作 | 最多 5 个动作，命中后依次执行 |
| 失败隔离 | 单动作，重试即重投 | **每动作一条执行记录**，一个失败只重试它自己 |
| 求值范围 | 单个属性样本 | **一次上报批**（多条件天然分散在多个样本里） |
| 存量规则 | — | **代码路径一行未改**，JSON 列为空即自动回落 |

---

## 五条核心设计

### 1. 用「JSON 可选列 + 旧列回落」，不建子表

规则评估是「按 `user_id` 拉全量规则 → 内存匹配」（`selectEnabledByUser`），**条件与动作从不作为 SQL 过滤条件**。
所以 JSON 列在本架构下**不损失任何查询能力**，而 `rule_condition` / `rule_action` 子表只会换来 JOIN、双写一致性维护和孤儿清理成本。

写入策略是「**多值优先、单值回填**」：数组非空时以数组为准，同时把首项回填到 `identifier` / `action_type` 旧列，
使任何仍读旧列的存量路径（列表筛选、导出、旧版前端）继续拿到合理值。存量行两列为 `NULL` → 自动走旧列，**零数据改写**。

### 2. 多条件的三条语义

求值范围是**一次上报批**而非单个样本 —— 「温度 > 30 且 湿度 < 60」天然需要设备同时报两个属性。

- **同一条件多次上报取「任一满足」** —— 设备一批里重复上报，只要有一次越限就应触发，取交集会漏报偶发尖峰
- **`AND` 下缺值 = 判不满足并终止求值** —— 本批没带的属性就是没上报，不能因「没数据」就判定命中
- **`OR` 下缺值不贡献命中**，但所有条件都缺值时整体不命中 —— 否则永不满足的规则会被别的条件的缺值误触发

### 3. 多动作 = 执行粒度即动作粒度

一次命中按动作数落 **N 条独立 `rule_execution`**，各带 `action_config_snapshot`。

重试 / 巡检重放 / 手动重试三条路径共用 `execute(executionId)` 这一个入口，按动作拆记录后天然隔离：
**一个动作失败只重试它自己，`FORWARD_HTTP` 不会重复投递**（外部副作用），执行器也无需开第二个入口。

### 4. 分派判据是「快照是否存在」，不是「快照优先于规则」

- 快照非空 = 多动作 → 按执行记录分派（否则 N 条记录会全执行成规则行上那个占位 `action_type`，即第一个动作）
- 快照为空 = 单动作 → **保持按规则分派**（记录上的 `action_type` 只是触发当时的快照，规则后来改过时以规则为准，这是 T-19 既有语义）

同一判据同时控制 `readConfig` 与 `switch`，两处不会分叉。

### 5. 冷却锚点每次触发只占一次

`acquireCooldown` 保持在 `trigger()` 里判一次，**不放进动作循环** —— 否则第二个动作会被刚占的锚点直接挡掉，多动作退化成单动作。

## 踩坑（都是测试抓出来的）

| 坑 | 表现 | 修正 |
|---|---|---|
| **`AND` 缺值写成 `continue`** | 注释写「缺值不算命中」，代码却是跳过继续；另一条件满足时整条规则误命中 | `AND` 下缺值必须**终止**求值 |
| **执行器改成「按记录分派」** | 8 个既有用例失败 —— 测试守的正是「单动作以规则为准」 | 分界改用「快照是否存在」 |
| Vue `v-model` 绑表达式 | `v-model="a.url \|\| a.topic"` 报 `vue/valid-v-model` | 按动作类型拆成多个输入 |
